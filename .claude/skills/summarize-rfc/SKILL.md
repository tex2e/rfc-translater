# RFCの要約作成

翻訳済みのRFCについて、対訳HTMLの冒頭に表示する要約を作成します。

## 実行モード

- 全工程を確認なしで実行します。
- 要約はあなた自身が本文を読んで書きます。外部の要約サービスやAPIは使いません。
- コミットやPRの作成は、依頼されたときだけ行います（translate-new-rfc から呼ばれたときは、呼び出し元の手順に従います）。

## 1. 対象の決定

引数でRFC番号が指定されていれば、それらを対象にします。指定がなければ、要約が未作成のRFCを対象にします。

```sh
python3 main.py --list-unsummarized --begin 9000   # 翻訳済みで要約がないRFC番号（昇順）
```

- 対象がなければ「要約対象なし」と報告して終了します。
- 要約がすでにあるRFCは、作り直すよう依頼されたときだけ上書きします。

以降の手順を、対象のRFCごとに行います。

## 2. 本文を読む

翻訳ファイル `data/<帯>/rfcN-trans.json`（`<帯>` はRFC番号の千の位未満を切り捨てた値。例: 9446 → `data/9000/`）から、要約に必要な範囲を読みます。

```sh
python3 main.py --rfc N --trans-export --include-translated --offset 0 --limit 60
```

- 概要（Abstract）と導入（Introduction）は必ず読みます。
- それだけでは「何を規定するか」が具体的に書けないときは、目次を見て中心となる節（プロトコルの動作、データ形式、IANAへの登録内容など）も読みます。
- 冒頭のヘッダ（raw の段落）にある `Obsoletes` `Updates` `Category` は `data/<帯>/rfcN-trans.json` の最初の段落で確認します。

タイトルや一般知識だけで書かず、必ず本文の記述に基づきます。本文にない機能や経緯を書き足しません。

## 3. 要約を書く

2〜3文で、次の内容を含めます。

1. このRFCが何を規定・定義するか（対象の技術と、その位置づけ）
2. どんな課題を解決するか、または何を可能にするか（仕組みの要点）
3. 既存の仕様との関係（更新・廃止するRFC、拡張する対象）や、文書の種別（実験的、情報提供など）が読者にとって重要な場合はそれ

書き方の規則は次のとおりです。

- ですます調で書きます。1文は200文字以内にします。
- 強調の `**`、バッククォート、バックスラッシュは使いません。
- プロトコル名・フィールド名などの識別子は原文の表記のまま書きます。略語は初出で「正式名称（略語）」または「略語（日本語の説明）」とします。
- 訳語は翻訳ファイルの訳文と `AGENTS.md` の「9. 用語集」に合わせます。
- 「このRFCは重要な仕様です」のような、どのRFCにも当てはまる文は書きません。

## 4. ファイルの作成

`data/<帯>/rfcN-summary.json` を次の形式で作成します（インデントは2、配列の要素は4）。

```json
{
  "number": 9446,
  "model": "claude-sonnet-5-5",
  "created_at": "2026-02-15T00:00:00.000000",
  "summary": [
    "1文目。",
    "2文目。"
  ]
}
```

- `number`: RFC番号（整数）
- `model`: 自分のモデルID
- `created_at`: 今日の日付。時刻は `00:00:00.000000` とします
- 既存の要約を修正したときも `model` と `created_at` を更新します

## 5. 検証とHTMLへの反映

```sh
python3 main.py --rfc N --summary-check   # 形式の検証（複数のときは --rfc 9446,9447）
python3 main.py --rfc N --make            # 対訳HTMLに要約を反映
```

- `--summary-check` がエラーを表示したら、要約を直して再実行します。
- `html/rfcN.html` の差分が要約の部分だけであることを確認します。

## 6. 報告

要約を作成したRFCの番号と、それぞれの要約文を報告します。
