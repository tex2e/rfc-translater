Protocol-Specific Profiles for JSContact
JSContact のプロトコル固有のプロファイル
Abstract
概要

This document defines the "JSContact Profiles" registry, an IANA registry for named subsets of JSContact elements. The document aims to facilitate using JSContact in the context of contact data exchange protocols or other use cases in which supporting all JSContact semantics might be inappropriate.

この文書は、JSContact 要素の名前付きサブセットの IANA レジストリである「JSContact Profiles」レジストリを定義します。このドキュメントは、連絡先データ交換プロトコルのコンテキストや、すべての JSContact セマンティクスをサポートすることが不適切な可能性があるその他のユースケースのコンテキストで JSContact を使用しやすくすることを目的としています。

1. Introduction
1. はじめに

The JSContact [RFC9553] contact card data model and format are designed for use in address book applications and directory services. Intended as an alternative to the prevalent vCard [RFC6350] data format, JSContact covers vCard core semantics and extensions, and it provides a rich model for personal names, postal addresses, and localization. All JSContact elements are relevant for some contact card use cases, and similar to vCard, implementations are expected to support these elements when exchanging contact card information using protocols such as CardDAV [RFC6352] and the JSON Meta Application Protocol (JMAP) for Contacts [RFC9610].

JSContact [RFC9553] 連絡先カードのデータ モデルと形式は、アドレス帳アプリケーションとディレクトリ サービスで使用するために設計されています。JSContact は、普及している vCard [RFC6350] データ形式の代替として意図されており、vCard のコア セマンティクスと拡張機能をカバーし、個人名、住所、およびローカリゼーションのための豊富なモデルを提供します。すべての JSContact 要素は一部の連絡先カードのユースケースに関連しており、vCard と同様に、CardDAV [RFC6352] や連絡先用の JSON Meta Application Protocol (JMAP) [RFC9610] などのプロトコルを使用して連絡先カード情報を交換する際、実装はこれらの要素をサポートすることが期待されます。

In contrast, other protocols and document specifications might require exchanging _some_ contact card information, but not all of what JSContact provides. Section 1.7.4 of [RFC9553] outlines how JSContact implementations may ignore unknown JSContact elements, but this only applies to future extensions of [RFC9553]; they are still expected to implement all elements of the core specification. Also, the extensibility of JSContact and the requirement to preserve arbitrary contact elements might not be adequate for some protocols.

対照的に、他のプロトコルやドキュメント仕様では、連絡先カード情報の一部を交換する必要がある場合がありますが、JSContact が提供するすべての情報を交換する必要はありません。[RFC9553] のセクション 1.7.4 では、JSContact 実装が未知の JSContact 要素を無視する方法について概説していますが、これは [RFC9553] の将来の拡張にのみ適用されます。それでも、コア仕様のすべての要素を実装することが期待されています。また、JSContact の拡張性と、任意の連絡先要素を保持する要件は、一部のプロトコルでは適切ではない可能性があります。

To make use of JSContact under these circumstances, this document defines a new IANA registry for JSContact that allows registration of named subsets of JSContact elements. These subsets are referred to as "JSContact profiles" and are meant to bring the following benefits:

このような状況で JSContact を利用するために、この文書では JSContact 要素の名前付きサブセットの登録を可能にする JSContact 用の新しい IANA レジストリを定義します。これらのサブセットは「JSContact プロファイル」と呼ばれ、次の利点をもたらすことを目的としています。

* Protocol designers might be encouraged to use JSContact rather than coming up with their own contacts format. This facilitates cross-protocol data exchange and migration.

* プロトコル設計者は、独自の連絡先形式を考え出すのではなく、JSContact を使用することをお勧めします。これにより、クロスプロトコルのデータ交換と移行が容易になります。

* Different protocols use the same IANA registry to express which JSContact elements they support. This facilitates understanding their commonalities and reusing existing profiles.

* 異なるプロトコルは、同じ IANA レジストリを使用して、サポートする JSContact 要素を表現します。これにより、それらの共通点を理解し、既存のプロファイルを再利用することが容易になります。

* A central registry provides implementors of JSContact libraries with a consistent format documenting which profile supports what elements rather than having to look up that information from possibly distinctly organized Internet-Drafts.

* 中央レジストリは、JSContact ライブラリの実装者に、どのプロファイルがどの要素をサポートするかを文書化する一貫した形式を提供します。明確に編成されたインターネット ドラフトから情報を検索する必要はありません。

This document is organized as follows. Section 3 defines JSContact profiles; Section 4 discusses the new "JSContact Profiles" registry created by IANA; and Appendix A illustrates JSContact profiles using an example.

この文書は次のように構成されています。セクション 3 では JSContact プロファイルを定義します。セクション 4 では、IANA によって作成された新しい「JSContact Profiles」レジストリについて説明します。付録 A では、例を使用して JSContact プロファイルを説明します。

3. JSContact Profiles
3. JS連絡先プロフィール

A JSContact profile is a named and versioned set of JSContact elements, such as properties, types, and values. The JSContact elements MUST be registered in the IANA "JSContact" registry group [IANA.jscontact]. A profile MAY define additional restrictions for these elements as outlined in Section 3.3, but a profile MUST NOT loosen restrictions. This document creates an IANA registry for JSContact profiles (see Section 4).

JSContact プロファイルは、プロパティ、タイプ、値などの、名前とバージョンが付けられた JSContact 要素のセットです。JSContact 要素は、IANA "JSContact" レジストリ グループ [IANA.jscontact] に登録されなければなりません (MUST)。セクション 3.3 で概説されているように、プロファイルはこれらの要素に対して追加の制限を定義してもよい (MAY) が、制限を緩めてはなりません (MUST NOT)。この文書は、JSContact プロファイル用の IANA レジストリを作成します (セクション 4 を参照)。

A JSContact object complies with a profile if all its properties are in the set of properties defined by that profile and the property values comply with the profile restrictions for that property. A JSContact object MAY comply with multiple profiles. Accordingly, this document does not specify any means for JSContact data to communicate which profiles it complies with, e.g., it does not define a "profile" property for the Card object.

JSContact オブジェクトは、そのすべてのプロパティがそのプロファイルによって定義されたプロパティのセットに含まれており、プロパティ値がそのプロパティのプロファイル制限に準拠している場合、プロファイルに準拠しています。JSContact オブジェクトは複数のプロファイルに準拠してもよい (MAY)。したがって、このドキュメントでは、JSContact データがどのプロファイルに準拠しているかを通信するための手段は指定されていません。たとえば、Card オブジェクトの「プロファイル」プロパティは定義されていません。

All properties and values of a JSContact object that complies with a profile MUST also be valid (Section 1.7 of [RFC9553]). Handling JSContact data that is valid but that does not comply with the expected profile is protocol-specific. This document deliberately does not define such non-compliant data as invalid. Profile designers decide on their own strategies for handling non-compliant data, one of which may be to reject it as invalid. JSContact data that complies with a profile may still not be valid in the context of that protocol; the protocol specification MAY define additional restrictions that a profile cannot express.

プロファイルに準拠する JSContact オブジェクトのすべてのプロパティと値も有効でなければなりません (MUST) ([RFC9553] のセクション 1.7)。有効ではあるが、予期されるプロファイルに準拠していない JSContact データの処理はプロトコル固有です。この文書では、このような非準拠データを無効であるとは意図的に定義していません。プロファイル設計者は、準拠していないデータを処理するための独自の戦略を決定します。その戦略の 1 つは、データを無効として拒否することです。プロファイルに準拠する JSContact データは、そのプロトコルのコンテキストではまだ有効ではない可能性があります。プロトコル仕様は、プロファイルでは表現できない追加の制限を定義してもよい(MAY)。

Section 3.1 defines how to name a JSContact profile; Section 3.2 defines how to version it; Section 3.3 defines how to specify the properties supported by that profile; and Section 3.4 describes how to determine the supported properties.

セクション 3.1 では、JSContact プロファイルに名前を付ける方法を定義します。セクション 3.2 ではバージョン管理方法を定義しています。セクション 3.3 では、そのプロファイルでサポートされるプロパティを指定する方法を定義します。セクション 3.4 では、サポートされるプロパティを決定する方法について説明します。

3.1. Profile Name
3.1. プロファイル名

A JSContact profile has a unique name. The name MUST only contain ASCII lowercase alphabetic and numeric characters, optionally separated by hyphens. It MUST start with an alphabetic character, and it MUST be of at least 1 character and at most 255 characters in size. Formally, it MUST be a valid "profile-name" defined in Figure 1.

JSContact プロファイルには一意の名前が付いています。名前には、ASCII の小文字の英数字のみを含める必要があり、必要に応じてハイフンで区切ることもできます。英字で始まらなければならず、サイズは少なくとも 1 文字、最大 255 文字である必要があります。正式には、図 1 で定義された有効な「プロファイル名」でなければなりません。 

   profile-name = lalpha *( ["-"] lalpha / DIGIT )
                  ; at most 255 characters in size

   lalpha       = %x61-7A ; a-z

Figure 1: ABNF Rule for JSContact Profile Name

図 1: JSContact プロファイル名の ABNF ルール

3.2. Profile Version
3.2. プロファイルのバージョン

A JSContact profile has a current version, and each profile is versioned independently. The version MUST be a positive integer, and it MUST increase whenever the profile properties (see Section 3.3) change. The initial version value is 1.

JSContact プロファイルには最新バージョンがあり、各プロファイルは個別にバージョン管理されます。バージョンは正の整数でなければならず (MUST)、プロファイルのプロパティ (セクション 3.3 を参照) が変更されるたびに増加しなければなりません (MUST)。初期バージョン値は 1 です。

3.3. Profile Properties
3.3. プロファイルのプロパティ

A profile defines a list of property entries that together determine the set of properties supported by that profile, as described in Section 3.4. The list MUST NOT be empty.

プロファイルは、セクション 3.4 で説明されているように、そのプロファイルでサポートされるプロパティのセットを決定するプロパティ エントリのリストを定義します。リストは空であってはなりません (MUST NOT)。

Each property entry consists of the following elements:

各プロパティ エントリは次の要素で構成されます。

Property Name:

プロパティ名:

This is the name of the JSContact property that this entry refers to. This MUST be a property name registered in the "JSContact Properties" registry. A property name MAY occur multiple times in the property entry list if the profile-specific restrictions for that property cannot be expressed with a single entry, but such multiple entries MUST NOT result in conflicting restrictions for the same property. This field MUST NOT be empty.

これは、このエントリが参照する JSContact プロパティの名前です。これは、「JSContact Properties」レジストリに登録されているプロパティ名でなければなりません (MUST)。プロパティのプロファイル固有の制限を 1 つのエントリで表現できない場合、プロパティ エントリ リスト内でプロパティ名が複数回出現してもよい (MAY)。ただし、そのような複数のエントリが同じプロパティに対して競合する制限を生じさせてはなりません (MUST NOT)。このフィールドは空であってはなりません (MUST NOT)。

Property Context:

プロパティコンテキスト:

This is a comma-separated list of JSContact object types that support this property in this profile. Each of these types MUST also be listed in the Property Contexts for this property in the "JSContact Properties" registry, but a profile MAY only support the property in a subset of these contexts. This field MUST NOT be empty.

これは、このプロファイルでこのプロパティをサポートする JSContact オブジェクト タイプのカンマ区切りのリストです。これらの各タイプは、「JSContact Properties」レジストリ内のこのプロパティのプロパティ コンテキストにもリストされなければなりません（MUST）が、プロファイルはこれらのコンテキストのサブセット内のプロパティのみをサポートしてもよい（MAY）。このフィールドは空であってはなりません (MUST NOT)。

Restricted Attributes:

制限された属性:

This restricts the attributes of the property. This specification only defines how to restrict the attributes such that a property becomes mandatory in the listed Property Contexts, despite the property originally being defined to be optional in the same contexts. The verbatim value "mandatory" (without quotes) indicates that it is mandatory in this profile; the absence of any value indicates that this profile does not restrict the property attributes of the original definition.

これにより、プロパティの属性が制限されます。この仕様は、プロパティが同じコンテキスト内で元々オプションであるように定義されていたにもかかわらず、リストされたプロパティ コンテキスト内でプロパティが必須になるように属性を制限する方法のみを定義します。逐語的な値「mandatory」(引用符なし) は、このプロファイルでは必須であることを示します。値が存在しない場合は、このプロファイルが元の定義のプロパティ属性を制限しないことを示します。

Restricted Property Type:

制限されたプロパティの種類:

This restricts the property value type in the listed Property Contexts. It allows a profile to restrict the allowed types to the original type definition such that future changes to JSContact do not extend the allowed types of the property for this profile, and it allows a profile to restrict the allowed types to a subset of the original type definition. The absence of any value indicates that this profile does not restrict the property value type of the original definition or any future extensions of the value type.

これにより、リストされたプロパティ コンテキスト内のプロパティ値のタイプが制限されます。これにより、プロファイルは、JSContact への今後の変更によってこのプロファイルのプロパティの許可された型が拡張されないように、許可される型を元の型定義に制限することができ、プロファイルは許可される型を元の型定義のサブセットに制限することができます。値が存在しないことは、このプロファイルが元の定義のプロパティ値タイプまたは値タイプの将来の拡張を制限しないことを示します。

If set, the restricted value type MUST exactly match the original definition at the time when the profile is defined, or the original value type MUST contain some type signature in the form "A|B" and the restricted value type MUST resemble the original except that some of the original "A|B" forms now only allow a subset of the original choices. Restricted property types MUST NOT redefine the "defaultType" attribute (Section 1.3.3 of [RFC9553]); the rules about when to set the "@type" property (Section 1.3.4 of [RFC9553]) of the original type definition still apply.

設定されている場合、制限された値のタイプは、プロファイルが定義された時点での元の定義と正確に一致しなければなりません (MUST)。または、元の値のタイプには「A|B」形式の型署名が含まれていなければならず (MUST)、制限された値のタイプは、元の「A|B」形式の一部が元の選択肢のサブセットのみを許可することを除いて、元のものに似ていなければなりません(MUST)。制限されたプロパティ タイプは、「defaultType」属性 ([RFC9553] のセクション 1.3.3) を再定義してはなりません (MUST NOT)。元の型定義の "@type" プロパティ ([RFC9553] のセクション 1.3.4) を設定するタイミングに関する規則は引き続き適用されます。

As an example of restricting the type definition to prevent future type extensions in the profile, one might restrict the type definition of the "addresses" property of the Card object to "Id[Address]", which matches the original definition as of this writing.

プロファイルで将来の型拡張を防ぐために型定義を制限する例として、Card オブジェクトの "addresses" プロパティの型定義を、この記事の執筆時点での元の定義と一致する "Id[Address]" に制限することができます。

As an example of restricting the type to a subset of the original value, one might want to restrict the "date" property of the Anniversary object to only allow partial dates as values. To do so, the original value type "PartialDate|Timestamp" can be restricted to "PartialDate". Note that the original value type need not be exactly in form "A|B". For example, the type signature "Id[A|B|C]" could be restricted to any of "Id[A|B]", "Id[A|C]", "Id[B|C]", "Id[A]", "Id[B]", "Id[C]", and the type signature "(A|B)[]" could be restricted to one of "A[]" or "B[]".

型を元の値のサブセットに制限する例として、Anniversary オブジェクトの「date」プロパティを制限して、部分的な日付のみを値として許可することができます。これを行うには、元の値の種類「PartialDate|Timestamp」を「PartialDate」に制限できます。元の値の型が正確に「A|B」の形式である必要はないことに注意してください。たとえば、型シグネチャ「Id[A|B|C]」は「Id[A|B]」、「Id[A|C]」、「Id[B|C]」、「Id[A]」、「Id[B]」、「Id[C]」のいずれかに制限でき、型シグネチャ「(A|B)[]」は「A[]」または「B[]」のいずれかに制限できます。

Restricted Enum Values:

制限された列挙値:

This restricts the enumerated values defined for this property to a subset of those values. The values MUST be listed in the "JSContact Enum Values" registry for this property and context. Allowed values are separated by a comma; the absence of any value indicates that all enumerated values are allowed. A profile MAY exclude the default enumerated value of a property, in which case all instances of the object MUST have this property set to one of the allowed values.

これにより、このプロパティに定義された列挙値がそれらの値のサブセットに制限されます。値は、このプロパティとコンテキストの「JSContact Enum Values」レジストリにリストされていなければなりません (MUST)。許可される値はカンマで区切られます。値が存在しない場合は、すべての列挙値が許可されることを示します。プロファイルは、プロパティのデフォルトの列挙値を除外してもよく (MAY)、その場合、オブジェクトのすべてのインスタンスは、このプロパティを許可された値の 1 つに設定しなければなりません (MUST)。

Restricted PatchObject:

制限されたパッチオブジェクト:

This restricts the PatchObject value of this property such that each JSON Pointer key in the PatchObject MUST consist of exactly one JSON Pointer reference token (Section 3 of [RFC6901]). For example, with this restriction, the "localizations" property of the Card object can only patch properties of the Card object by replacing their values entirely. The verbatim value "yes" (without quotes) indicates that this profile restricts PatchObject keys to a single token; the absence of any value indicates that it does not restrict them. This MUST NOT be set to "yes" if the property value type is not a PatchObject.

これにより、このプロパティの PatchObject 値が制限され、PatchObject 内の各 JSON Pointer キーが 1 つだけの JSON Pointer 参照トークンで構成されなければなりません (MUST) ([RFC6901] のセクション 3)。たとえば、この制限により、Card オブジェクトの「localizations」プロパティは、値を完全に置き換えることによってのみ Card オブジェクトのプロパティにパッチを適用できます。逐語的な値「yes」(引用符なし) は、このプロファイルが PatchObject キーを単一のトークンに制限することを示します。値が存在しない場合は、制限がないことを示します。プロパティ値のタイプが PatchObject でない場合、これを「yes」に設定してはなりません (MUST NOT)。

All profiles MUST support "@type" and "version"; therefore, profiles MUST NOT include entries for these properties.

すべてのプロファイルは「@type」と「version」をサポートしなければなりません (MUST)。したがって、プロファイルにはこれらのプロパティのエントリを含めてはなりません (MUST NOT)。

3.4. Supported Properties
3.4. サポートされているプロパティ

The supported properties of a JSContact profile are determined by the profile's property entries and the contents of the IANA "JSContact Properties" registry, which are referred to here as "IANA-registered properties" for short. The "version" property of the Card object and the "@type" property of any object type are always supported.

JSContact プロファイルでサポートされるプロパティは、プロファイルのプロパティ エントリと IANA「JSContact Properties」レジストリの内容によって決まります。ここでは、これらを略して「IANA 登録プロパティ」と呼びます。Card オブジェクトの「version」プロパティと任意のオブジェクト タイプの「@type」プロパティは常にサポートされます。

A Card object complies with the profile if all its properties are part of the supported properties and all property values are valid according to the restrictions defined in the applicable property entries. A PatchObject MUST NOT patch properties that are not supported in that profile.

Card オブジェクトは、そのすべてのプロパティがサポートされているプロパティの一部であり、すべてのプロパティ値が該当するプロパティ エントリで定義された制限に従って有効である場合、プロファイルに準拠します。PatchObject は、そのプロファイルでサポートされていないプロパティにパッチを適用してはなりません (MUST NOT)。

The following describes the steps to determine the supported properties:

以下に、サポートされているプロパティを決定する手順を説明します。

1. Initialize the set with all properties of the Card object for which a property entry contains "Card" in the Property Context of the profile. If no such entry exists, then initialize the set with all IANA-registered properties of the Card object.

1. プロファイルのプロパティ コンテキストのプロパティ エントリに「Card」が含まれる Card オブジェクトのすべてのプロパティを使用してセットを初期化します。そのようなエントリが存在しない場合は、Card オブジェクトのすべての IANA 登録プロパティを使用してセットを初期化します。

2. For every property in the set having either an object type as the value type or a list, map, or union of object types, add all properties for which a property entry contains those object types in the Property Context of the profile. If no such property entry exists, then add all IANA-registered properties for the object types.

2. 値の型としてオブジェクト タイプ、またはオブジェクト タイプのリスト、マップ、または共用体を持つセット内のすべてのプロパティについて、プロパティ エントリにそれらのオブジェクト タイプが含まれるすべてのプロパティをプロファイルのプロパティ コンテキストに追加します。そのようなプロパティ エントリが存在しない場合は、オブジェクト タイプの IANA 登録プロパティをすべて追加します。

3. Repeat the previous step until all object types that are value types of properties in the set have been considered.

3. セット内のプロパティの値タイプであるすべてのオブジェクト タイプが考慮されるまで、前の手順を繰り返します。

Appendix A.4 describes how to determine the supported properties of the example profile in Appendix A.

付録 A.4 では、付録 A のサンプル プロファイルでサポートされているプロパティを確認する方法について説明します。
