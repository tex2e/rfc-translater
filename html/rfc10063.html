Abstract

概要

This document specifies Near Real Time Mirroring version 4 (NRTMv4): a one-way synchronization protocol for Internet Routing Registry (IRR) records. NRTMv4 is based on files that are distributed over HTTPS. The protocol allows instances of IRR Database servers to mirror IRR records, specified in the Routing Policy Specification Language (RPSL), between each other.

本文書は、Near Real Time Mirroring バージョン4 (NRTMv4) を規定します。NRTMv4 は、Internet Routing Registry (IRR) レコードのための一方向の同期プロトコルです。NRTMv4 は、HTTPS で配布されるファイルに基づいています。このプロトコルにより、IRRデータベースサーバのインスタンス同士が、Routing Policy Specification Language (RPSL) で記述されたIRRレコードを相互にミラーリングできます。

1. Introduction

1. はじめに

The Internet Routing Registry (IRR) consists of several IRR Databases, each representing objects in the Routing Policy Specification Language (RPSL) [RFC2622]. About a dozen larger IRR Databases are well known and widely used, operated by different organizations such as Regional Internet Registries and some large network operators. IRR objects serve many purposes ranging from manual research by operators to automated network configuration and filtering.

Internet Routing Registry (IRR) は複数のIRRデータベースで構成され、それぞれが Routing Policy Specification Language (RPSL) [RFC2622] でオブジェクトを表現します。Regional Internet Registry や一部の大規模ネットワーク事業者など、さまざまな組織が運用する十数個の比較的大きなIRRデータベースが広く知られ、利用されています。IRRオブジェクトは、運用者による手作業での調査から、自動化されたネットワーク設定やフィルタリングまで、多くの目的に使われています。

Most of these well-known IRR Databases mirror IRR objects from some others so that queries run against these instances provide a comprehensive view. Some parties also mirror IRR Databases to private IRR server instances to reduce latency when replying to queries, analyze IRR objects, or other purposes.

これらの著名なIRRデータベースの多くは、他のデータベースからIRRオブジェクトをミラーリングしており、これらのインスタンスに対するクエリが包括的な結果を返せるようになっています。また、クエリへの応答時の遅延を減らす、IRRオブジェクトを分析するなどの目的で、IRRデータベースを自前のIRRサーバインスタンスにミラーリングする関係者もいます。

NRTM version 4 (NRTMv4) is a protocol for IRR mirroring and is designed to address issues in existing IRR Database mirroring protocols. In NRTMv4, IRR Databases publish their records on an HTTPS [STD97] endpoint with periodic Snapshot Files and regular Delta Files. Signing allows integrity checks. By only generating files once and publishing them over HTTPS, scalability is improved. NRTMv4 borrows some concepts from the Resource Public Key Infrastructure (RPKI) Repository Delta Protocol [RFC8182], as there are overlaps between the two protocols.

NRTM バージョン4 (NRTMv4) はIRRミラーリングのためのプロトコルであり、既存のIRRデータベースミラーリングプロトコルが抱える問題に対処するよう設計されています。NRTMv4 では、IRRデータベースは、定期的な Snapshot File と通常の Delta File を伴って、レコードを HTTPS [STD97] エンドポイントで公開します。署名により完全性の確認が可能になります。ファイルを一度だけ生成して HTTPS で公開することで、スケーラビリティが向上します。NRTMv4 は Resource Public Key Infrastructure (RPKI) Repository Delta Protocol [RFC8182] といくつかの概念が重なっているため、そこからいくつかの概念を借用しています。

Reliable and secure distribution of IRR data is important for global routing operations since network operators depend on IRR objects for route filtering and network configuration. Prior mirroring protocols lack integrity verification, have no formal specification, and scale poorly. NRTMv4 addresses these shortcomings by providing a formally specified, scalable, and integrity-protected mirroring protocol. Of earlier NRTM versions, none were formally specified, but NRTMv3 [NRTMv3] was widely deployed. Some comparisons are made in Section 11.

IRRデータは、ネットワーク運用者が経路フィルタリングやネットワーク設定にIRRオブジェクトを依存しているため、グローバルなルーティング運用において、信頼性が高く安全に配布されることが重要です。従来のミラーリングプロトコルには完全性の検証がなく、正式な仕様もなく、スケーラビリティも低いものでした。NRTMv4 は、正式に規定され、スケーラブルで、完全性が保護されたミラーリングプロトコルを提供することで、これらの欠点に対処します。以前の NRTM のバージョンはいずれも正式には規定されていませんでしたが、NRTMv3 [NRTMv3] は広く展開されていました。いくつかの比較をセクション11で行います。

2. Overview

2. 概要

In NRTMv4, a mirror server is an instance of IRR Database software that has a database of IRR objects and makes them available on an HTTPS endpoint to allow mirroring by others. These objects can be retrieved by mirror clients, which then load them into their local storage.

NRTMv4 において、ミラーサーバとは、IRRオブジェクトのデータベースを持ち、他者によるミラーリングを可能にするためにそれらを HTTPS エンドポイントで利用可能にする、IRRデータベースソフトウェアのインスタンスです。これらのオブジェクトはミラークライアントによって取得され、ミラークライアントはそれらをローカルのストレージに読み込みます。

図1: NRTMv4 プロトコルの概要

Publication consists of three different files:

公開は、次の3種類のファイルで構成されます。

* A single Update Notification File. This specifies the current IRR Database version and locations of the Snapshot File and Delta Files. It is signed to allow verification of the authenticity of the Update Notification File.

* 単一の Update Notification File。現在のIRRデータベースのバージョンと、Snapshot File および Delta File の場所を指定します。Update Notification File の真正性を検証できるよう、署名されています。

* A single active Snapshot File. This contains all published IRR objects at a particular version. The mirror server periodically generates a new snapshot.

* 単一の有効な Snapshot File。特定のバージョンにおいて公開されているすべてのIRRオブジェクトを含みます。ミラーサーバは定期的に新しいスナップショットを生成します。

* Zero or more Delta Files. These contain the changes between two Database versions.

* 0個以上の Delta File。2つのデータベースバージョン間の変更を含みます。

The Update Notification File MUST be in the JSON Web Signature [RFC7515] format, where the payload is in JSON format [RFC8259]. The Snapshot File and Delta Files MUST be in the JSON Text Sequences [RFC7464] format so that each object in large files can be parsed independently. Files MAY be compressed with GZIP [RFC1952].

Update Notification File は、ペイロードが JSON 形式 [RFC8259] である JSON Web Signature [RFC7515] 形式でなければなりません (MUST)。Snapshot File と Delta File は、大きなファイル内の各オブジェクトを個別に解析できるよう、JSON Text Sequences [RFC7464] 形式でなければなりません (MUST)。ファイルは GZIP [RFC1952] で圧縮してもよい (MAY)。

Mirror clients initially retrieve the small Update Notification File and a Snapshot File from which they initialize their local copy of the Database. After that, mirror clients only retrieve the Update Notification File periodically, typically every minute, to determine whether there are any changes, and then retrieve only the relevant Delta Files, if any. This minimizes data transfer. Deltas have sequential versions.

ミラークライアントは、まず小さな Update Notification File と Snapshot File を取得し、そこからデータベースのローカルコピーを初期化します。その後は、ミラークライアントは、変更があるかどうかを判断するために Update Notification File だけを、通常は1分ごとに定期的に取得し、変更がある場合に限り、関連する Delta File だけを取得します。これによりデータ転送が最小限に抑えられます。デルタには連続したバージョンが付きます。

Mirror clients are configured with the URL of an Update Notification File, the name of the IRR Database, and a public signing key. This public key is used to verify the Update Notification File, which, in turn, contains hashes of all the Snapshot and Delta Files.

ミラークライアントには、Update Notification File の URL、IRRデータベースの名前、および公開署名鍵が設定されます。この公開鍵は Update Notification File の検証に使われ、Update Notification File には、すべての Snapshot File と Delta File のハッシュが含まれています。

Upon initialization, the mirror server generates a session identifier (session_id) for the Database (Section 4.2). This allows long-term caching and is used by the client to determine that the Delta Files continue to form a full set of changes allowing an update to the latest version. If the mirror server loses partial history or the mirror client starts mirroring from a different server, the session_id change will force a full reload from the latest Snapshot File, ensuring there are no accidental mirroring gaps.

初期化時に、ミラーサーバはデータベースのセッション識別子 (session_id) を生成します (セクション4.2)。これにより長期的なキャッシュが可能になり、クライアントは、Delta File が引き続き最新バージョンへの更新を可能にする変更の完全な集合を成していることを判断するために、これを使います。ミラーサーバが履歴の一部を失った場合、またはミラークライアントが別のサーバからミラーリングを開始した場合は、session_id の変更により最新の Snapshot File からの完全な再読み込みが強制されるため、意図しないミラーリングの欠落が生じないことが保証されます。

Mirror servers can use caching to reduce their load, particularly because snapshots and deltas are immutable for a given session_id and version number. These are also the largest files. Update Notification Files may not be cached for longer than one minute, but are fairly small.

スナップショットとデルタは、特定の session_id とバージョン番号に対して不変であるため、ミラーサーバはキャッシュを使って負荷を減らすことができます。これらは最も大きなファイルでもあります。Update Notification File は、かなり小さいものの、1分より長くキャッシュしてはなりません。

Note that in NRTMv4, contiguous version numbers are used for the Database version and Delta Files. This is different and unrelated to the serial in NRTMv3. NRTMv3 serials refer to a single change to a single object, whereas an NRTMv4 version refers to one delta, possibly containing multiple changes to multiple objects. NRTMv3 serials can also contain gaps, NRTMv4 versions do not.

NRTMv4 では、データベースのバージョンと Delta File に連続したバージョン番号が使われることに注意してください。これは NRTMv3 の serial とは異なり、無関係です。NRTMv3 の serial は単一のオブジェクトに対する単一の変更を指しますが、NRTMv4 の version は1つのデルタを指し、そのデルタには複数のオブジェクトに対する複数の変更が含まれることがあります。NRTMv3 の serial には欠番が生じることもありますが、NRTMv4 の version には生じません。

3. Terminology

3. 用語

IRR Database:

IRRデータベース:

A logical collection of IRR objects represented in RPSL, grouped by the value in their "source" attribute. That value is the name of the IRR Database. No particular storage technology is implied.

RPSL で表現されたIRRオブジェクトの論理的な集合で、"source" 属性の値によってグループ化されます。その値がIRRデータベースの名前です。特定のストレージ技術を前提とするものではありません。

Snapshot File:

Snapshot File:

A file that reflects the complete contents of the IRR objects in an IRR Database at a particular point in time.

特定の時点におけるIRRデータベース内のIRRオブジェクトの完全な内容を反映するファイルです。

Delta File:

Delta File:

A file that contains all changes for exactly one incremental update of the IRR Database.

IRRデータベースのちょうど1回の増分更新に対するすべての変更を含むファイルです。

Update Notification File:

Update Notification File:

A file generated by the mirror server and used by mirror clients to discover which changes exist between the state of the IRR mirror server and of the mirror client.

ミラーサーバによって生成され、IRRミラーサーバの状態とミラークライアントの状態との間にどのような変更が存在するかをミラークライアントが把握するために使われるファイルです。

Mirror Server:

ミラーサーバ:

An instance of IRR Database software that has a database of IRR objects and makes them available for retrieval on an HTTPS endpoint, to allow mirroring by others.

IRRオブジェクトのデータベースを持ち、他者によるミラーリングを可能にするために、それらを HTTPS エンドポイントで取得可能にする、IRRデータベースソフトウェアのインスタンスです。

Mirror Client:

ミラークライアント:

An instance of IRR Database software that retrieves IRR objects from a mirror server and loads them into its local storage.

ミラーサーバからIRRオブジェクトを取得し、自身のローカルストレージに読み込む、IRRデータベースソフトウェアのインスタンスです。

Version:

Version:

A monotonically increasing positive integer, scoped to a session_id, that identifies a particular state of the IRR Database.

session_idの範囲内で単調増加する正の整数で、IRRデータベースの特定の状態を識別します。

4. Mirror Server Use

4. ミラーサーバの使用

4.1. Key Configuration

4.1. 鍵の設定

When enabling NRTMv4 publication for an IRR Database, the operator MUST generate a JSON Web Key [RFC7517] pair and configure the private key in the mirror server. The operator then provides the corresponding public key, the name of the IRR Database, and publication URL of the Update Notification File to any operators of mirror clients. The published public key MUST be encapsulated following Textual Encoding of Subject Public Key Info Section 13 of [RFC7468], sometimes referred to as "PEM encoding". The process for providing this is not in the scope of this protocol, but a typical case is publication on the operator's known website. Key rotation is described in Section 9.6.

IRRデータベースのNRTMv4公開を有効にする際、オペレータはJSON Web Key [RFC7517] のペアを生成し、秘密鍵をミラーサーバに設定しなければなりません (MUST)。その後、オペレータは、対応する公開鍵、IRRデータベースの名前、およびUpdate Notification Fileの公開URLを、ミラークライアントのオペレータに提供します。公開される公開鍵は、[RFC7468] のSection 13にあるTextual Encoding of Subject Public Key Infoに従ってカプセル化しなければなりません (MUST)。これは「PEMエンコーディング」と呼ばれることもあります。これを提供する方法はこのプロトコルの範囲外ですが、典型的にはオペレータの既知のウェブサイトで公開します。鍵のローテーションについてはSection 9.6で説明します。

It is RECOMMENDED that implementations provide easily accessible tools for operators to generate new signing keys to enter into their configuration and assist with key rotation. All configuration options SHOULD be clearly named to indicate that they are private keys. Clear naming reduces the risk of operator error causing accidental exposure.

実装は、オペレータが設定に入力する新しい署名鍵を生成し、鍵のローテーションを支援するための、容易にアクセスできるツールを提供することが推奨されます (RECOMMENDED)。すべての設定オプションは、それらが秘密鍵であることがわかるように明確に命名すべきです (SHOULD)。明確な命名により、オペレータの誤りによる偶発的な漏えいのリスクが低減されます。

4.2. Snapshot Initialization

4.2. スナップショットの初期化

A mirror server MUST follow the initialization steps upon the first export for an IRR Database by that mirror server, or if the server lost history and can not reliably produce a continuous set of deltas from a previous state.

ミラーサーバは、そのミラーサーバによるIRRデータベースの最初のエクスポート時、またはサーバが履歴を失い、以前の状態からの連続したデルタの集合を確実に生成できない場合に、初期化手順に従わなければなりません (MUST)。

In other words, either the mirror server guarantees that clients following the deltas have a correct and complete view, or the mirror server must reinitialize, which will force clients to reinitialize as well.

言い換えると、ミラーサーバがデルタに従うクライアントに正しく完全なビューを保証するか、ミラーサーバが再初期化しなければならず、その場合はクライアントも再初期化を強いられます。

Initialization consists of these actions:

初期化は次の動作で構成されます。

* The mirror server MUST generate a new session_id. This MUST be a Universally Unique Identifier version 4 (UUIDv4) (Section 5.4 of [RFC9562]) and MUST be the same across all client sessions. The session_id is unique to the IRR Database, so an instance that serves multiple IRR Databases will create a separate session_id for each.

* ミラーサーバは新しいsession_idを生成しなければなりません (MUST)。これはUniversally Unique Identifier version 4 (UUIDv4) ([RFC9562] のSection 5.4) でなければならず (MUST)、すべてのクライアントセッションで同一でなければなりません (MUST)。session_idはIRRデータベースごとに一意であるため、複数のIRRデータベースを提供するインスタンスは、それぞれに別個のsession_idを作成します。

* The server MUST generate a snapshot for version number one. This may contain an empty array of objects if the IRR Database is currently empty.

* サーバはバージョン番号1のスナップショットを生成しなければなりません (MUST)。IRRデータベースが現在空の場合、これにはオブジェクトの空の配列が含まれることがあります。

* The server MUST generate a new Update Notification File with the new session_id, a reference to the new snapshot, and no deltas.

* サーバは、新しいsession_id、新しいスナップショットへの参照を含み、デルタを含まない、新しいUpdate Notification Fileを生成しなければなりません (MUST)。

Note that a publication, and its associated session_ids and versions, always relates to a single specific IRR Database, even if multiple databases are published from one instance. For example, a mirror server that serves two IRR Databases named EXAMPLE and EXAMPLE-NONAUTH will generate two Update Notification Files, referring to two Snapshot Files and two sets of Delta Files. Each set of Delta Files has contiguous version numbers. The two publications are completely independent of each other, with different session IDs, and may be published at different times. This applies even if the same IRR server instance produces both.

公開、およびそれに関連するsession_idとバージョンは、1つのインスタンスから複数のデータベースが公開される場合であっても、常に1つの特定のIRRデータベースに関係することに注意してください。たとえば、EXAMPLEとEXAMPLE-NONAUTHという名前の2つのIRRデータベースを提供するミラーサーバは、2つのUpdate Notification Fileを生成し、それらは2つのSnapshot Fileと2組のDelta Fileを参照します。各組のDelta Fileは連続したバージョン番号を持ちます。2つの公開は互いに完全に独立しており、異なるセッションIDを持ち、異なる時刻に公開されることもあります。これは、同じIRRサーバインスタンスが両方を生成する場合でも当てはまります。

4.3. Publishing Updates

4.3. 更新の公開

After creating the initialization files, the mirror server processes updates by generating Delta Files and, periodically, a new Snapshot File, and placing them on the HTTPS endpoint.

初期化ファイルを作成した後、ミラーサーバは、Delta Fileと、定期的に新しいSnapshot Fileを生成し、それらをHTTPSエンドポイントに配置することで更新を処理します。

4.3.1. Delta Files

4.3.1. Delta File

Changes to IRR objects MUST be recorded in Delta Files. One Delta File can contain multiple changes.

IRRオブジェクトへの変更は、Delta Fileに記録しなければなりません (MUST)。1つのDelta Fileには複数の変更を含めることができます。

Updates are generated as follows:

更新は次のように生成されます。

* A mirror server MUST publish a Delta File approximately every minute if there have been changes to IRR objects in that time frame.

* ミラーサーバは、その時間枠内にIRRオブジェクトに変更があった場合、約1分ごとにDelta Fileを公開しなければなりません (MUST)。

* If a mirror server is lagging in production of Delta Files, such as after an initialization or server downtime, it MUST generate one larger "catch up" Delta File rather than individual Delta Files for every one-minute window.

* 初期化後やサーバのダウンタイム後など、ミラーサーバのDelta File生成が遅延している場合は、1分間隔の時間枠ごとに個別のDelta Fileを生成するのではなく、より大きな「追いつき」用のDelta Fileを1つ生成しなければなりません (MUST)。

* A new Delta File MUST be generated with a new version, one greater than the last Delta File version, or one greater than the last Snapshot File version if there were no prior deltas at all.

* 新しいDelta Fileは、直前のDelta Fileのバージョンより1大きいバージョン、または、それ以前のデルタがまったくない場合は直前のSnapshot Fileのバージョンより1大きいバージョンで生成しなければなりません (MUST)。

* The Delta File MUST include all changes that happened during the time frame in the order in which they occurred. If multiple changes have occurred within the time frame that would cancel each other out, like an addition and immediate deletion of the same object, the mirror server MUST still include all these changes.

* Delta Fileには、その時間枠内に発生したすべての変更を、発生した順序で含めなければなりません (MUST)。同じオブジェクトの追加と直後の削除のように、時間枠内に発生した複数の変更が互いに打ち消し合う場合でも、ミラーサーバはそれらすべての変更を含めなければなりません (MUST)。

* The URL where the Delta File is published MUST contain the session ID and version number so that the content at a given URL is immutable and can be cached indefinitely by HTTP intermediaries. It MUST also contain a random value that can not be predicted before publication to counter negative caching issues.

* Delta Fileが公開されるURLには、特定のURLの内容が不変であり、HTTP中継装置によって無期限にキャッシュできるように、セッションIDとバージョン番号を含めなければなりません (MUST)。また、ネガティブキャッシュの問題に対処するため、公開前に予測できないランダムな値も含めなければなりません (MUST)。

* The Update Notification File MUST be updated to include the new Delta File.

* Update Notification Fileは、新しいDelta Fileを含むように更新しなければなりません (MUST)。

* References to Delta Files older than 24 hours SHOULD be removed from the Update Notification File. This limits the potential length of the Delta chain that clients must process, where a Snapshot refresh may be more efficient, while also preventing overly frequent Snapshot reloads. However, a mirror server MUST NOT remove references to Delta Files with a version higher than the current Snapshot File version, as this would leave clients with no path from the snapshot to the current state. Refer also to Section 9.5.

* 24時間より古いDelta Fileへの参照は、Update Notification Fileから削除すべきです (SHOULD)。これにより、クライアントが処理しなければならないDeltaチェーンの潜在的な長さが制限されます。そのような場合はSnapshotの再取得の方が効率的なことがありますが、同時にSnapshotの過度に頻繁な再読み込みも防ぎます。ただし、ミラーサーバは、現在のSnapshot Fileのバージョンより高いバージョンのDelta Fileへの参照を削除してはなりません (MUST NOT)。削除すると、クライアントにスナップショットから現在の状態へ至る経路がなくなるためです。Section 9.5も参照してください。

* Note that, as Delta Files always contain changes compared to a previous state, there can never be a Delta File with version 1.

* Delta Fileは常に以前の状態と比較した変更を含むため、バージョン1のDelta Fileは決して存在しえないことに注意してください。

Mirror servers with high object churn are RECOMMENDED to generate new Snapshot Files more frequently than the required minimum to limit the length of the Delta chain that clients must traverse on initialization or after a gap. Long Delta chains increase initialization time and resource consumption for mirror clients.

オブジェクトの変動が大きいミラーサーバは、クライアントが初期化時またはギャップの後にたどらなければならないDeltaチェーンの長さを制限するため、必要な最小値よりも高い頻度で新しいSnapshot Fileを生成することが推奨されます (RECOMMENDED)。長いDeltaチェーンは、ミラークライアントの初期化時間とリソース消費を増大させます。

4.3.2. Snapshot Files

4.3.2. Snapshot File

Snapshot Files after initialization are generated as follows:

初期化後のSnapshot Fileは次のように生成されます。

* If there have been no changes to the IRR objects since the last snapshot, the mirror server MUST NOT generate a new snapshot.

* 前回のスナップショット以降にIRRオブジェクトへの変更がなかった場合、ミラーサーバは新しいスナップショットを生成してはなりません (MUST NOT)。

* The mirror server MUST generate a new Snapshot File at least once per day if there have been changes to the IRR objects. Mirror servers should not generate new Snapshot Files more than once per hour, as snapshot generation can be resource-intensive.

* ミラーサーバは、IRRオブジェクトに変更があった場合、少なくとも1日に1回、新しいSnapshot Fileを生成しなければなりません (MUST)。スナップショットの生成はリソースを大量に消費することがあるため、ミラーサーバは1時間に1回を超えて新しいSnapshot Fileを生成しないほうがよいでしょう。

* The version number of the new snapshot MUST be equal to the last Delta File version at the time the server begins generating the snapshot.

* 新しいスナップショットのバージョン番号は、サーバがスナップショットの生成を開始した時点での最新のDelta Fileのバージョンと等しくなければなりません (MUST)。

* The URL where the Snapshot File is published MUST contain the session ID and version number so that the content at a given URL is immutable and can be cached indefinitely by HTTP intermediaries. It MUST also contain a random value that can not be predicted before publication to counter negative caching issues.

* Snapshot Fileが公開されるURLには、特定のURLの内容が不変であり、HTTP中継装置によって無期限にキャッシュできるように、セッションIDとバージョン番号を含めなければなりません (MUST)。また、ネガティブキャッシュの問題に対処するため、公開前に予測できないランダムな値も含めなければなりません (MUST)。

* The Update Notification File MUST be updated to include the new snapshot if one was generated.

* 新しいスナップショットが生成された場合、Update Notification Fileはそのスナップショットを含むように更新しなければなりません (MUST)。

* Snapshot generation may take some time, and in that time, newer changes may occur that are not part of the snapshot in progress. The mirror server MUST continue to produce Delta Files during this window. This means that the server may publish a Snapshot File with a version number older than the most recent Delta File at the time of publication.

* スナップショットの生成には時間がかかることがあり、その間に、進行中のスナップショットに含まれない新しい変更が発生することがあります。ミラーサーバは、この間もDelta Fileを生成し続けなければなりません (MUST)。これは、サーバが、公開時点の最新のDelta Fileよりも古いバージョン番号を持つSnapshot Fileを公開することがあることを意味します。

4.3.3. Update Notification File

4.3.3. Update Notification File

The Update Notification File MUST be updated when a new Delta or Snapshot File is published and at least every 24 hours, even if there have been no changes. The full format and validation rules are specified in Section 6.

Update Notification File は、新しい Delta File または Snapshot File が公開されたときに更新し、変更がない場合でも少なくとも24時間ごとに更新しなければなりません (MUST)。完全な形式と検証規則は第6節で規定されています。

4.3.4. Publication Policy Restrictions

4.3.4. 公開ポリシーの制限

A mirror server MAY have a policy that restricts the publication of certain IRR objects or attributes, or modifies these before publication. Typical scenarios for this include preventing the distribution of certain personal data or password hashes, or excluding objects which do not meet validation rules like RPKI consistency. If objects are modified, it is RECOMMENDED that the mirror server makes it evident to humans reading the object text that the object was modified, for example, by adding remark lines or comments.

ミラーサーバは、特定のIRRオブジェクトや属性の公開を制限したり、公開前にそれらを変更したりするポリシーを持ってもよい (MAY)。典型的な例として、特定の個人データやパスワードハッシュの配布の防止、RPKIとの整合性などの検証規則を満たさないオブジェクトの除外があります。オブジェクトを変更する場合、たとえばremark行やコメントを追加するなどして、オブジェクトのテキストを読む人間にそのオブジェクトが変更されたことが明らかになるようにすることが、ミラーサーバに推奨されます (RECOMMENDED)。

Mirror servers are RECOMMENDED to remove password hashes from the auth lines in mntner objects, as they have little use beyond the authoritative server and their publication may be a security risk.

ミラーサーバは、mntner オブジェクトの auth 行からパスワードハッシュを削除することが推奨されます (RECOMMENDED)。パスワードハッシュは権威サーバ以外ではほとんど用途がなく、その公開はセキュリティ上のリスクとなりうるためです。

If a mirror server has a policy that restricts or modifies object publication, this MUST be applied consistently to Snapshot Files and Delta Files from the moment the policy is enacted or modified.

ミラーサーバがオブジェクトの公開を制限または変更するポリシーを持つ場合、このポリシーは、施行または変更された時点から、Snapshot File と Delta File に一貫して適用されなければなりません (MUST)。

5. Mirror Client Use

5. ミラークライアントの利用

5.1. Client Configuration

5.1. クライアントの設定

Mirror clients are configured with the name of the IRR Database, the URL of the Update Notification File, and the public key currently used for signing the Update Notification File. Key rotation is described in Section 9.6.

ミラークライアントには、IRRデータベース名、Update Notification File のURL、および Update Notification File の署名に現在使用されている公開鍵が設定されます。鍵のローテーションについては第9.6節で説明します。

5.2. Update Notification File Retrieval

5.2. Update Notification File の取得

Mirror clients may retrieve the Update Notification File to check for changes every minute. Mirror clients MUST NOT check more than once per minute.

ミラークライアントは、変更を確認するために Update Notification File を1分ごとに取得してもかまいません。ミラークライアントは、1分間に1回を超えて確認してはなりません (MUST NOT)。

5.3. Initialization from Snapshot

5.3. スナップショットからの初期化

Clients MUST initialize from a Snapshot File when initially configured, or if they are not able to update their local data from the provided Delta Files:

クライアントは、最初に設定されたとき、または提供された Delta File からローカルデータを更新できない場合、Snapshot File から初期化しなければなりません (MUST)。

* The client MUST retrieve the Update Notification File.

* クライアントは Update Notification File を取得しなければなりません (MUST)。

* The client MUST verify that the source attribute in the Update Notification File matches the configured IRR Database name.

* クライアントは、Update Notification File の source 属性が、設定されたIRRデータベース名と一致することを検証しなければなりません (MUST)。

* The client MUST retrieve the Snapshot File and load the objects into its local storage.

* クライアントは Snapshot File を取得し、オブジェクトをローカルストレージに読み込まなければなりません (MUST)。

* The mirror client MUST verify that the calculated SHA-256 [SHS] hash of the Snapshot File matches the hash in the Update Notification File that referenced it. If the Snapshot File was compressed with GZIP, the hash MUST match the compressed data. As the Update Notification File is signed, this hash verification proves the integrity and authenticity for the Snapshot File. In case of a mismatch of this hash, the file MUST be rejected.

* ミラークライアントは、Snapshot File について計算したSHA-256 [SHS] ハッシュが、その Snapshot File を参照する Update Notification File 内のハッシュと一致することを検証しなければなりません (MUST)。Snapshot File がGZIPで圧縮されている場合、ハッシュは圧縮後のデータと一致しなければなりません (MUST)。Update Notification File は署名されているため、このハッシュ検証によって Snapshot File の完全性と真正性が証明されます。このハッシュが一致しない場合、そのファイルは拒否されなければなりません (MUST)。

* The client MUST record the session_id and version of the loaded Snapshot File.

* クライアントは、読み込んだ Snapshot File の session_id と version を記録しなければなりません (MUST)。

* The file MUST be rejected if an Update Notification File or a Snapshot File has an invalid syntax (e.g., missing mandatory parameters). For validating the IRR objects contained in the files, see Section 9.2.

* Update Notification File または Snapshot File の構文が不正である場合（例：必須パラメータの欠落）、そのファイルは拒否されなければなりません (MUST)。これらのファイルに含まれるIRRオブジェクトの検証については、第9.2節を参照してください。

5.4. Processing Delta Files

5.4. Delta File の処理

If a mirror client has previously initialized from a snapshot:

ミラークライアントが以前にスナップショットから初期化済みである場合は、次のとおりです。

* The client MUST retrieve the Update Notification File.

* クライアントは Update Notification File を取得しなければなりません (MUST)。

* The client MUST verify that the source attribute in the Update Notification File matches the configured IRR Database name.

* クライアントは、Update Notification File の source 属性が、設定されたIRRデータベース名と一致することを検証しなければなりません (MUST)。

* The client MUST verify that the session_id matches the previously known session_id. If this does not match, the client MUST reinitialize from the snapshot.

* クライアントは、session_id が以前に把握していた session_id と一致することを検証しなければなりません (MUST)。一致しない場合、クライアントはスナップショットから再初期化しなければなりません (MUST)。

* The client MUST verify that the Update Notification File version is the same or higher than the client's current most recent version. If not, the Update Notification File MUST be rejected. It is RECOMMENDED for the client to distinguish between an Update Notification File that is a single version older, and a much older version, in any status messages. The former can occur from time to time in synchronization issues and the latter is more likely a faulty implementation.

* クライアントは、Update Notification File の version が、クライアントが現在持つ最新の version と同じか、それより高いことを検証しなければなりません (MUST)。そうでない場合、その Update Notification File は拒否されなければなりません (MUST)。クライアントは、ステータスメッセージにおいて、1つだけ古い version の Update Notification File と、はるかに古い version のものとを区別することが推奨されます (RECOMMENDED)。前者は同期の問題で時折発生しうるものであり、後者は実装の不具合である可能性が高いためです。

* The client MUST verify that the Update Notification File contains one contiguous set of Delta File versions after the client's current most recent version up to the latest version in the Update Notification File. If the Delta File versions are not contiguous, the Update Notification File MUST be rejected. If the available Delta File versions do not range from the client's most recent version plus one, the client MUST reinitialize from the snapshot.

* クライアントは、Update Notification File が、クライアントが現在持つ最新の version より後から Update Notification File の最新の version までの、連続した1組の Delta File の version を含むことを検証しなければなりません (MUST)。Delta File の version が連続していない場合、その Update Notification File は拒否されなければなりません (MUST)。利用可能な Delta File の version が、クライアントの最新の version に1を加えた値から始まらない場合、クライアントはスナップショットから再初期化しなければなりません (MUST)。

* The mirror client MUST verify that the hashes of each Delta and Snapshot File have not changed compared to the previous valid Update Notification File for the same file type and version. If a newer Update Notification File contains a different hash for a specific file, this indicates a misconfiguration in the server and the client MUST reject the Update Notification File.

* ミラークライアントは、各 Delta File と Snapshot File のハッシュが、同じファイル種別と version についての直前の有効な Update Notification File と比べて変化していないことを検証しなければなりません (MUST)。より新しい Update Notification File に特定のファイルについて異なるハッシュが含まれている場合、これはサーバの設定ミスを示しており、クライアントはその Update Notification File を拒否しなければなりません (MUST)。

* The client MUST retrieve all Delta Files for versions since the client's last known version, if there are any.

* クライアントは、最後に把握している version 以降の version の Delta File がある場合、そのすべてを取得しなければなりません (MUST)。

* The mirror client MUST verify that the calculated SHA-256 hash of each newly downloaded Delta File matches the hash in the Update Notification File that referenced it. If the Delta File was compressed with GZIP, the hash MUST match the compressed file. As the Update Notification File is signed, this hash verification proves the integrity and authenticity for the Delta File. In case of a mismatch of this hash, the Delta File MUST be rejected.

* ミラークライアントは、新しくダウンロードした各 Delta File について計算したSHA-256ハッシュが、その Delta File を参照する Update Notification File 内のハッシュと一致することを検証しなければなりません (MUST)。Delta File がGZIPで圧縮されている場合、ハッシュは圧縮後のファイルと一致しなければなりません (MUST)。Update Notification File は署名されているため、このハッシュ検証によって Delta File の完全性と真正性が証明されます。このハッシュが一致しない場合、その Delta File は拒否されなければなりません (MUST)。

* The client MUST process all changes in the Delta Files in order: lowest Delta File version number first, and in the order of the changes list in the Delta File.

* クライアントは、Delta File 内のすべての変更を順番どおりに処理しなければなりません (MUST)。すなわち、Delta File の version 番号が最も小さいものから先に、Delta File 内の changes リストの順序で処理します。

* The client MUST update its records of the most recent version to the version of the Update Notification File.

* クライアントは、最新の version の記録を、Update Notification File の version に更新しなければなりません (MUST)。

* If an Update Notification File or a Delta File has an invalid syntax (including missing mandatory parameters), the file MUST be rejected. For validating the IRR objects contained in the files, see Section 9.2.

* Update Notification File または Delta File の構文が不正である場合（必須パラメータの欠落を含む）、そのファイルは拒否されなければなりません (MUST)。これらのファイルに含まれるIRRオブジェクトの検証については、第9.2節を参照してください。

If the Update Notification File or one of the Delta Files is rejected, the mirror client MUST NOT process any newer Deltas than those that are valid and have been successfully verified. If some Delta Files are rejected, it MAY process the valid Delta Files, but MUST NOT skip over any rejected Delta Files while doing so. Additionally, the changes in a specific Delta File MUST be processed either completely, or not at all, i.e., a Delta File must never be partially processed.

Update Notification File または Delta File のいずれかが拒否された場合、ミラークライアントは、有効であり正常に検証された Delta より新しい Delta を処理してはなりません (MUST NOT)。一部の Delta File が拒否された場合、有効な Delta File を処理してもよいですが (MAY)、その際に拒否された Delta File を飛ばしてはなりません (MUST NOT)。さらに、特定の Delta File 内の変更は、完全に処理されるか、まったく処理されないかのどちらかでなければなりません (MUST)。すなわち、Delta File が部分的に処理されることがあってはなりません。

5.5. Error Recovery

5.5. エラーからの回復

When a mirror client fails to retrieve any file due to a transient error, such as a network failure or an HTTP 5xx response, the client SHOULD retry before concluding the retrieval has failed. It is RECOMMENDED that implementations use a bounded exponential backoff strategy, starting from a short initial interval (e.g., a few seconds) up to a capped maximum interval (e.g., several minutes), with a bounded total retry duration. This prevents unnecessary Snapshot imports on clients and can prevent clients overwhelming a server on transient failures. Mirror clients SHOULD log retry and recovery events, including the reason, to assist operators in diagnosing mirroring failures.

ネットワーク障害やHTTP 5xx応答などの一時的なエラーが原因でミラークライアントがいずれかのファイルの取得に失敗した場合、クライアントは、取得が失敗したと結論づける前に再試行すべきです (SHOULD)。実装は、短い初期間隔（例：数秒）から上限付きの最大間隔（例：数分）まで、総再試行時間にも上限を設けた、上限付き指数バックオフ戦略を使用することが推奨されます (RECOMMENDED)。これにより、クライアントでの不要な Snapshot のインポートを防ぎ、一時的な障害時にクライアントがサーバに過剰な負荷をかけることを防ぐことができます。ミラークライアントは、ミラーリングの障害を運用者が診断するのを助けるため、理由を含めて再試行と回復のイベントをログに記録すべきです (SHOULD)。

If a file is rejected, the mirror client MUST NOT load any data from it. If the error may be transient, the mirror client SHOULD retry. After exhausting retries, if the required Delta Files remain unavailable or are still rejected, the mirror client SHOULD reinitialize from the Snapshot File to prevent using stale data. If the Snapshot File itself cannot be retrieved or is rejected after retries, as there is no further fallback, the client SHOULD alert the operator and stop until the issue is resolved.

ファイルが拒否された場合、ミラークライアントはそのファイルからデータを一切読み込んではなりません (MUST NOT)。エラーが一時的なものである可能性がある場合、ミラークライアントは再試行すべきです (SHOULD)。再試行を使い果たした後も、必要な Delta File が入手できないままか、依然として拒否される場合、ミラークライアントは、古いデータの使用を防ぐために Snapshot File から再初期化すべきです (SHOULD)。Snapshot File 自体が取得できない場合、または再試行後も拒否される場合は、これ以上のフォールバックがないため、クライアントは運用者に警告し、問題が解決されるまで停止すべきです (SHOULD)。

5.6. Signature and Staleness Verification

5.6. 署名と陳腐化の検証

Every time a mirror client retrieves a new version of the Update Notification File, it MUST verify the included signature. The signature MUST be valid for the configured public key for the contents of the Update Notification File. If the signature does not match, the mirror client MUST reject the Update Notification File unless a key rotation is in progress as described in Section 9.6.

ミラークライアントは、Update Notification File の新しい version を取得するたびに、そこに含まれる署名を検証しなければなりません (MUST)。署名は、Update Notification File の内容に対して、設定された公開鍵で有効でなければなりません (MUST)。署名が一致しない場合、第9.6節で説明されているように鍵のローテーションが進行中である場合を除き、ミラークライアントは Update Notification File を拒否しなければなりません (MUST)。

A mirror client can use the generation timestamp in the Update Notification File to check whether the file is stale, as the mirror server must update this file at least every 24 hours. If the generation timestamp is more than 24 hours ago, the file is stale and the mirror client SHOULD warn the operator in log messages or other alerting, but MAY continue to process it otherwise.

ミラーサーバはこのファイルを少なくとも24時間ごとに更新しなければならないため、ミラークライアントは、Update Notification File 内の生成タイムスタンプを使って、そのファイルが陳腐化しているかどうかを確認できます。生成タイムスタンプが24時間より前の場合、そのファイルは陳腐化しており、ミラークライアントはログメッセージやその他の警報で運用者に警告すべきですが (SHOULD)、それ以外はそのまま処理を続行してもよい (MAY)。

5.7. Policy Restrictions

5.7. ポリシーの制限

A mirror client MAY have a policy that restricts the processing of objects to certain object classes, or other limitations on which objects it processes.

ミラークライアントは、処理するオブジェクトを特定のオブジェクトクラスに限定するポリシー、または処理対象のオブジェクトに関するその他の制限を持ってもよい (MAY)。

If a mirror client has a policy that restricts object processing, this MUST be applied consistently to Snapshot Files and Delta Files from the moment the policy is enacted or modified.

ミラークライアントがオブジェクトの処理を制限するポリシーを持つ場合、これはポリシーが施行または変更された時点から、Snapshot FileとDelta Fileに一貫して適用されなければなりません (MUST)。

6. Update Notification File

6. Update Notification File

6.1. Purpose

6.1. 目的

The Update Notification File is generated by the mirror server and used by mirror clients to discover whether any changes exist between the state of the IRR mirror server and of the mirror client. It also describes the location of the Snapshot File and incremental Delta Files. Finally, the generation timestamp can be used to detect whether the file is stale.

Update Notification Fileはミラーサーバによって生成され、IRRミラーサーバの状態とミラークライアントの状態との間に変更があるかどうかを発見するために、ミラークライアントによって使用されます。また、Snapshot Fileと増分のDelta Fileの場所も記述します。さらに、生成タイムスタンプを使用して、ファイルが古くなっていないかを検出できます。

The mirror server MUST generate a new Update Notification File every time there are new deltas or snapshots and at least every 24 hours, even if there have been no changes.

ミラーサーバは、新しいデルタまたはスナップショットが生じるたびに、また変更がない場合でも少なくとも24時間ごとに、新しいUpdate Notification Fileを生成しなければなりません (MUST)。

6.2. Cache Concerns

6.2. キャッシュに関する考慮事項

A mirror server may use caching infrastructure to cache the Update Notification File and reduce the load of HTTPS requests.

ミラーサーバは、Update Notification Fileをキャッシュし、HTTPSリクエストの負荷を減らすために、キャッシュ基盤を使用してもかまいません。

However, since this file is used by mirror clients to determine whether any updates are available, the mirror server SHOULD ensure that this file is not cached for longer than one minute. An exception to this rule is that it is better to serve a stale Update Notification File rather than no Update Notification File.

ただし、このファイルはミラークライアントが更新の有無を判断するために使用するため、ミラーサーバは、このファイルが1分を超えてキャッシュされないようにすべきです (SHOULD)。この規則の例外として、Update Notification Fileをまったく提供しないよりも、古いUpdate Notification Fileを提供するほうが望ましいとされます。

Mirror servers SHOULD set the HTTP Cache-Control response header on the Update Notification File to no-cache or max-age=60, consistent with the one-minute caching limit. Mirror servers SHOULD set Cache-Control: immutable on responses for Snapshot Files and Delta Files, as these are immutable for a given session_id and version. Otherwise, clients and intermediaries may unnecessarily refetch large files. Mirror clients MAY use HTTP conditional requests (e.g., using If-None-Match with ETags or If-Modified-Since) when polling the Update Notification File to reduce bandwidth consumption when no changes have occurred.

ミラーサーバは、1分というキャッシュ上限に合わせて、Update Notification FileのHTTP Cache-Controlレスポンスヘッダをno-cacheまたはmax-age=60に設定すべきです (SHOULD)。ミラーサーバは、Snapshot FileとDelta Fileのレスポンスに対して、Cache-Control: immutableを設定すべきです (SHOULD)。これらは、特定のsession_idとversionに対して不変だからです。そうしないと、クライアントや中継装置が大きなファイルを不必要に再取得するおそれがあります。ミラークライアントは、Update Notification Fileをポーリングする際、変更がないときの帯域消費を減らすために、HTTP条件付きリクエスト（例: ETagを用いたIf-None-Match、またはIf-Modified-Since）を使用してもよい (MAY)。

6.3. Payload Format and Validation

6.3. ペイロード形式と検証

An example payload of an Update Notification File is provided below:

Update Notification Fileのペイロードの例を以下に示します。 

   {
     "nrtm_version": 4,
     "timestamp": "2025-12-01T15:00:00Z",
     "type": "notification",
     "next_signing_key": "bnJ0..bXY0",
     "source": "EXAMPLE",
     "session_id": "ca128382-78d9-41d1-8927-1ecef15275be",
     "version": 4,
     "snapshot": {
       "version": 3,
       "url":
   "ca128382-78d9-41d1-8927-1ecef15275be/nrtm-snapshot.3.04759.json.gz",
       "hash": "9a..86"
     },
     "deltas": [
       {
         "version": 2,
         "url":
   "ca128382-78d9-41d1-8927-1ecef15275be/nrtm-delta.2.784a2a6.json",
         "hash": "62..a2"
       },
       {
         "version": 3,
         "url":
   "ca128382-78d9-41d1-8927-1ecef15275be/nrtm-delta.3.0f681f0.json",
         "hash": "25..9a"
       },
       {
         "version": 4,
         "url":
   "ca128382-78d9-41d1-8927-1ecef15275be/nrtm-delta.4.d9c194a.json",
         "hash": "b4..13"
       }
     ],
     "metadata": {}
   }

Note: Hash and key values in this example are shortened because of formatting.

注：この例のハッシュと鍵の値は、書式の都合により短縮されています。

In this example, the overall version is 4, the snapshot is at version 3, and deltas are listed for versions 2, 3, and 4. The deltas at versions 2 and 3 predate the snapshot, but are still within the 24-hour retention window. A new client would initialize from the snapshot at version 3 and then apply only delta 4. An existing client already at version 1 can instead apply deltas 2, 3, and 4 without reinitializing from the snapshot.

この例では、全体のversionは4、スナップショットはバージョン3であり、デルタはバージョン2、3、4について列挙されています。バージョン2と3のデルタはスナップショットより前のものですが、24時間の保持期間内にあります。新規クライアントはバージョン3のスナップショットから初期化し、その後はデルタ4のみを適用します。すでにバージョン1にある既存クライアントは、スナップショットから再初期化することなく、デルタ2、3、4を適用できます。

The following validation rules MUST be observed when creating or parsing Update Notification Files:

Update Notification Fileを作成または解析する際には、次の検証規則を遵守しなければなりません (MUST)。

* The nrtm_version MUST be 4.

* nrtm_versionは4でなければなりません (MUST)。

* The timestamp MUST be in the format specified in [RFC3339] with the time-offset set to "Z".

* timestampは、[RFC3339]で規定される形式で、time-offsetを"Z"に設定したものでなければなりません (MUST)。

* The type MUST be "notification".

* typeは"notification"でなければなりません (MUST)。

* The optional field next_signing_key is used for in-band key rotation. If present, it MUST be a JWK [RFC7517] public key encoded in PEM, which matches the private key the mirror server will start using to sign the Update Notification File in the near future. Key rotation is described in Section 9.6. If there is no next signing key, this key MUST be omitted.

* オプションのフィールドnext_signing_keyは、帯内での鍵ローテーションに使用されます。存在する場合は、PEMでエンコードされたJWK [RFC7517]公開鍵でなければならず (MUST)、近い将来にミラーサーバがUpdate Notification Fileへの署名に使用し始める秘密鍵に対応するものでなければなりません。鍵ローテーションについては9.6節で説明します。次の署名鍵がない場合、この鍵は省略されなければなりません (MUST)。

* The source MUST be a valid IRR object name [RFC2622].

* sourceは、有効なIRRオブジェクト名 [RFC2622]でなければなりません (MUST)。

* The session_id attribute MUST be a UUIDv4 (Section 5.4 of [RFC9562]) unique to this session for this source.

* session_id属性は、このsourceのこのセッションに固有のUUIDv4（[RFC9562]の5.4節）でなければなりません (MUST)。

* The version MUST be an unsigned positive integer and be equal to the highest version of the deltas and snapshot.

* versionは符号なし正整数であり、かつ、デルタとスナップショットのバージョンのうち最大のものと等しくなければなりません (MUST)。

* The file MUST contain exactly one snapshot.

* ファイルには、ちょうど1つのスナップショットを含めなければなりません (MUST)。

* The file MAY contain one or more deltas.

* ファイルには、1つ以上のデルタを含めてもよい (MAY)。

* The deltas MUST have a sequential contiguous set of version numbers.

* デルタは、連続した一続きのバージョン番号を持たなければなりません (MUST)。

* Each snapshot and delta element MUST have a version, URL, and hash attribute. The URL must be relative to the path of the Update Notification File. For example, if the Update Notification File example above is published on https://example.com/nrtm/update-notification-file.jose, the full URL for the referred snapshot is https://example.com/nrtm/ca128382-78d9-41d1-8927-1ecef15275be/ nrtm-snapshot.3.04759.json.gz. If the snapshot or delta file was compressed with GZIP, the filename MUST end in ".gz", and the hash MUST match the compressed data.

* 各スナップショット要素とデルタ要素は、version、URL、hash属性を持たなければなりません (MUST)。URLは、Update Notification Fileのパスからの相対でなければなりません。たとえば、上記のUpdate Notification Fileの例がhttps://example.com/nrtm/update-notification-file.joseで公開されている場合、参照されるスナップショットの完全なURLはhttps://example.com/nrtm/ca128382-78d9-41d1-8927-1ecef15275be/ nrtm-snapshot.3.04759.json.gzになります。スナップショットまたはデルタのファイルがGZIPで圧縮されている場合、ファイル名は".gz"で終わらなければならず (MUST)、ハッシュは圧縮されたデータと一致しなければなりません (MUST)。

* The hash attribute in snapshot and delta elements MUST be the hexadecimal encoding of the SHA-256 hash of the referenced file. This hash algorithm, used to verify the integrity of the Snapshot and Delta Files, is fixed and independent of the JWS signing algorithm used for the Update Notification File. The mirror client MUST verify this hash when the file is retrieved and reject the file if the hash does not match.

* スナップショット要素とデルタ要素のhash属性は、参照先ファイルのSHA-256ハッシュの16進エンコードでなければなりません (MUST)。このハッシュアルゴリズムは、Snapshot FileとDelta Fileの完全性の検証に使用されるものであり、固定されており、Update Notification Fileに使用されるJWSの署名アルゴリズムとは独立しています。ミラークライアントは、ファイルを取得したときにこのハッシュを検証し、ハッシュが一致しない場合はそのファイルを拒否しなければなりません (MUST)。

* The metadata key MAY be present and is used for metadata produced by the server to aid in tracing and debugging. This can contain information like the name of the host on which the file was generated or the name and version of the software used. Each mirror server may choose which fields to include or choose to not include any metadata. The mirror server SHOULD NOT cause excessive size increases by adding extensive metadata in the Update Notification File, as it is the most frequently retrieved file.

* metadataキーは存在してもよく (MAY)、トレースとデバッグを支援するためにサーバが生成するメタデータに使用されます。ここには、ファイルを生成したホストの名前や、使用したソフトウェアの名前とバージョンなどの情報を含めることができます。各ミラーサーバは、含めるフィールドを選択することも、メタデータをいっさい含めないことも選択できます。ミラーサーバは、Update Notification Fileが最も頻繁に取得されるファイルであるため、大量のメタデータを追加することでサイズを過度に増加させるべきではありません (SHOULD NOT)。

6.4. Encoding and Signature

6.4. エンコードと署名

* The actual Update Notification File content is a JSON Web Signature [RFC7515] using JWS Compact Serialization.

* 実際のUpdate Notification Fileの内容は、JWS Compact Serializationを用いたJSON Web Signature [RFC7515]です。

* The JWS Payload is the JSON [RFC8259] serialization of the structure described in the previous section.

* JWS Payloadは、前節で説明した構造のJSON [RFC8259]シリアライズです。

* The filename of the serialized data MUST be "update-notification-file.jose".

* シリアライズされたデータのファイル名は"update-notification-file.jose"でなければなりません (MUST)。

* Mirror clients MUST implement ES256. Mirror servers MAY use ES256 or other digital signature algorithms from the IANA "JSON Web Signature and Encryption Algorithms" registry [IANA_jose]; the algorithm MUST NOT be "none", a MAC algorithm, or Deprecated or Prohibited. It is RECOMMENDED to use ES256 or other Recommended or Recommended+ algorithms. If a server uses an algorithm other than ES256, it is the server operator's responsibility to ensure their mirror clients support that algorithm.

* ミラークライアントはES256を実装しなければなりません (MUST)。ミラーサーバは、IANAの"JSON Web Signature and Encryption Algorithms"レジストリ [IANA_jose]にあるES256またはその他のデジタル署名アルゴリズムを使用してもよい (MAY)。ただし、そのアルゴリズムは"none"、MACアルゴリズム、またはDeprecatedもしくはProhibitedであってはなりません (MUST NOT)。ES256、またはその他のRecommendedもしくはRecommended+のアルゴリズムを使用することが推奨されます (RECOMMENDED)。サーバがES256以外のアルゴリズムを使用する場合、ミラークライアントがそのアルゴリズムをサポートすることを確実にする責任はサーバ運用者にあります。

7. Snapshot File

7. Snapshot File

7.1. Purpose

7.1. 目的

The Snapshot File reflects the complete and current contents of all IRR objects in an IRR Database. Mirror clients MUST use this to initialize their local copy of the IRR Database. Snapshot Files are not individually signed. Their integrity is verified by comparing the calculated SHA-256 hash with the hash listed in the signed Update Notification File (see Section 6.4).

Snapshot Fileは、IRRデータベース内のすべてのIRRオブジェクトの完全かつ現在の内容を反映します。ミラークライアントは、ローカルのIRRデータベースのコピーを初期化するために、これを使用しなければなりません (MUST)。Snapshot Fileには個別の署名は付されません。その完全性は、計算したSHA-256ハッシュを、署名されたUpdate Notification Fileに記載されたハッシュと比較することで検証されます（6.4節を参照）。

7.2. Cache Concerns

7.2. キャッシュに関する考慮事項

A snapshot reflects the content of the IRR Database at a specific point in time; for that reason, it can be considered immutable data. Snapshot Files are published at a URL that is unique to the specific session and version. The URL also contains a random value that can not be predicted before publication to counter negative caching issues.

スナップショットは特定の時点でのIRRデータベースの内容を反映するため、不変のデータとみなせます。Snapshot Fileは、特定のセッションとバージョンに固有のURLで公開されます。このURLには、ネガティブキャッシュの問題に対処するために、公開前には予測できないランダムな値も含まれています。

Because these files never change, they can be cached. However, as snapshots are large and old snapshots will no longer be referred by newer Update Notification Files, it is RECOMMENDED that a limited cache interval is used.

これらのファイルは決して変化しないため、キャッシュできます。ただし、スナップショットは大きく、古いスナップショットは新しいUpdate Notification Fileからは参照されなくなるため、キャッシュ期間を限定することが推奨されます (RECOMMENDED)。

7.3. File Format and Validation

7.3. ファイル形式と検証

Example Snapshot File, where ␞ (U+241E) represents the record separator control character (U+001E) as specified in [RFC7464]:

レコード区切り制御文字 (U+001E) を [RFC7464] で規定されているとおり ␞ (U+241E) で表した、Snapshot File の例： 

   ␞{
     "nrtm_version": 4,
     "type": "snapshot",
     "source": "EXAMPLE",
     "session_id": "ca128382-78d9-41d1-8927-1ecef15275be",
     "version": 3
   }
   ␞{"object": "route: 192.0.2.0/24\norigin: AS64500\nsource: EXAMPLE"}
   ␞{"object": "route6: 2001:db8::/32\norigin: AS64500\nsource: EXAMPLE"}

Note: IRR object texts in this example are shortened because of formatting.

注：この例のIRRオブジェクトのテキストは、書式の都合により短縮しています。

The file is in JSON Text Sequences [RFC7464] format and MUST contain one or more records (it must contain at least the header). The first record is the file header and the following validation rules MUST be observed when creating or parsing a Snapshot File header:

このファイルは JSON Text Sequences [RFC7464] 形式であり、1つ以上のレコードを含まなければなりません (MUST)（少なくともヘッダを含む必要があります）。最初のレコードはファイルヘッダであり、Snapshot File のヘッダを作成または解析する際には、次の検証規則を遵守しなければなりません (MUST)。

* The nrtm_version MUST be 4.

* nrtm_version は 4 でなければなりません (MUST)。

* The type MUST be "snapshot".

* type は "snapshot" でなければなりません (MUST)。

* The source MUST match the source in the Update Notification File.

* source は、Update Notification File の source と一致しなければなりません (MUST)。

* The session_id attribute MUST match the session_id in the Update Notification File.

* session_id 属性は、Update Notification File の session_id と一致しなければなりません (MUST)。

* The version MUST be an unsigned positive integer, matching the Update Notification File entry for this snapshot.

* version は、このスナップショットに対する Update Notification File のエントリと一致する、符号なし正整数でなければなりません (MUST)。

The remaining records (zero or more) MUST each contain a string representation of an IRR object. The source attribute in the IRR object texts MUST match the source attribute of the Snapshot File.

残りのレコード（0個以上）は、それぞれIRRオブジェクトの文字列表現を含まなければなりません (MUST)。IRRオブジェクトのテキスト内の source 属性は、Snapshot File の source 属性と一致しなければなりません (MUST)。

8. Delta File

8. Delta File

8.1. Purpose

8.1. 目的

A Delta File contains all changes for exactly one incremental update of the IRR Database. It may include new, modified, and deleted objects. Delta Files can contain multiple alterations to multiple objects. Delta Files are not individually signed. Their integrity is verified by comparing the calculated SHA-256 hash with the hash listed in the signed Update Notification File (see Section 6.4).

Delta File には、IRRデータベースのちょうど1回分の増分更新に関するすべての変更が含まれます。新規、変更、削除されたオブジェクトを含むことがあります。Delta File は、複数のオブジェクトに対する複数の変更を含むことができます。Delta File には個別の署名はありません。その完全性は、計算した SHA-256 ハッシュを、署名された Update Notification File に記載されたハッシュと比較することで検証されます（6.4節を参照）。

8.2. Cache Concerns

8.2. キャッシュに関する考慮事項

Deltas reflect the difference in content of the IRR Database from one version to another; for that reason, it can be considered immutable data. Delta Files are published at a URL that is unique to the specific session and version. The URL also contains a random value that can not be predicted before publication to counter negative caching issues.

デルタは、あるバージョンから別のバージョンへのIRRデータベースの内容の差分を反映したものであるため、不変のデータとみなすことができます。Delta File は、特定のセッションとバージョンに固有のURLで公開されます。このURLには、ネガティブキャッシュの問題に対処するため、公開前には予測できないランダムな値も含まれます。

To avoid race conditions where a mirror client retrieves an Update Notification File moments before it's updated, mirror servers SHOULD retain old Delta Files for at least 5 minutes after a new Update Notification File is published that no longer contains these Delta Files.

ミラークライアントが Update Notification File の更新直前にそれを取得してしまう競合状態を避けるため、ミラーサーバは、新しい Update Notification File が公開され、その中に古い Delta File が含まれなくなった後も、少なくとも5分間はそれらの Delta File を保持すべきです (SHOULD)。

8.3. File Format and Validation

8.3. ファイル形式と検証

Example Delta File, where ␞ (U+241E) represents the record separator control character (U+001E) as specified in [RFC7464]:

レコード区切り制御文字 (U+001E) を [RFC7464] で規定されているとおり ␞ (U+241E) で表した、Delta File の例： 

   ␞{
     "nrtm_version": 4,
     "type": "delta",
     "source": "EXAMPLE",
     "session_id": "ca128382-78d9-41d1-8927-1ecef15275be",
     "version": 3
   }
   ␞{
     "action": "delete",
     "object_class": "person",
     "primary_key": "PRSN1-EXAMPLE"
   }
   ␞{
     "action": "delete",
     "object_class": "route",
     "primary_key": "192.0.2.0/24AS64500"
   }
   ␞{
     "action": "add_modify",
     "object": "route6: 2001:db8::/32\norigin: AS64500\nsource: EXAMPLE"
   }

Note: IRR object texts in this example are shortened because of formatting.

注：この例のIRRオブジェクトのテキストは、書式の都合により短縮しています。

The file is in JSON Text Sequences [RFC7464] format and MUST contain two or more records (at least the header and one change). The first record is the file header and the following validation rules MUST be observed when creating or parsing a Delta File header:

このファイルは JSON Text Sequences [RFC7464] 形式であり、2つ以上のレコードを含まなければなりません (MUST)（少なくともヘッダと1件の変更を含みます）。最初のレコードはファイルヘッダであり、Delta File のヘッダを作成または解析する際には、次の検証規則を遵守しなければなりません (MUST)。

* The nrtm_version MUST be 4.

* nrtm_version は 4 でなければなりません (MUST)。

* The type MUST be "delta".

* type は "delta" でなければなりません (MUST)。

* The source MUST match the source in the Update Notification File.

* source は、Update Notification File の source と一致しなければなりません (MUST)。

* The session_id attribute MUST match the session_id in the Update Notification File.

* session_id 属性は、Update Notification File の session_id と一致しなければなりません (MUST)。

* The version MUST be an unsigned positive integer, matching the Update Notification File entry for this delta.

* version は、このデルタに対する Update Notification File のエントリと一致する、符号なし正整数でなければなりません (MUST)。

The remaining records (one or more) MUST each contain a JSON object that represents a change. The JSON object MUST meet the following rules:

残りのレコード（1個以上）は、それぞれ変更を表すJSONオブジェクトを含まなければなりません (MUST)。このJSONオブジェクトは、次の規則を満たさなければなりません (MUST)。

* It has an "action" attribute, which is either "delete" for object deletions or "add_modify" for additions or modifications.

* "action" 属性を持ちます。この値は、オブジェクトの削除の場合は "delete"、追加または変更の場合は "add_modify" のいずれかです。

* If action is "delete": It has an "object_class" attribute with the RPSL object class name, and a "primary_key" attribute with the primary key of the deleted object. For objects that are listed in [RFC2622] and [RFC4012], the primary key is the value of the RPSL field defined as "class key". For object classes that define a pair of attributes as class key, e.g. route, the values of the individual attributes are appended together without separators. For any other objects, the primary key is the value of the RPSL field with the same name as the object class name. The primary key and object class name are not case-sensitive. Therefore, mirror clients MUST use case-insensitive matching against their local database.

* action が "delete" の場合：RPSLオブジェクトクラス名を値とする "object_class" 属性と、削除されたオブジェクトのプライマリキーを値とする "primary_key" 属性を持ちます。[RFC2622] および [RFC4012] に列挙されているオブジェクトでは、プライマリキーは "class key" として定義されているRPSLフィールドの値です。route のように、クラスキーとして属性の組を定義しているオブジェクトクラスでは、個々の属性の値を区切り文字なしで連結します。その他のオブジェクトでは、プライマリキーはオブジェクトクラス名と同じ名前のRPSLフィールドの値です。プライマリキーとオブジェクトクラス名は大文字と小文字を区別しません。したがって、ミラークライアントは、ローカルデータベースに対して大文字と小文字を区別しない照合を使用しなければなりません (MUST)。

* If action is "add_modify": It has an "object" attribute with the RPSL text of the new version of the object.

* action が "add_modify" の場合：オブジェクトの新しいバージョンのRPSLテキストを値とする "object" 属性を持ちます。

9. Operational Considerations

9. 運用上の考慮事項

9.1. Time

9.1. 時刻

IRR clients and servers are RECOMMENDED to use NTP [RFC5905] synchronization to avoid timing discrepancies.

IRRクライアントとサーバは、時刻の不一致を避けるため、NTP [RFC5905] による同期を使用することが推奨されます (RECOMMENDED)。

9.2. IRR Object Validation

9.2. IRRオブジェクトの検証

Throughout the years, various implementations of IRR servers have taken liberties with the various RFCs regarding RPSL. Implementations have introduced different new object classes, attributes, and validation rules. Current IRR Databases also contain legacy objects that were created under different validation rules. In practice, there is no uniformly implemented standard for RPSL, but merely rough outlines partially documented in different places.

長年にわたり、IRRサーバの各種実装は、RPSLに関する各RFCを自由に解釈してきました。実装ごとに、異なる新しいオブジェクトクラス、属性、検証規則が導入されています。現在のIRRデータベースには、異なる検証規則のもとで作成されたレガシーなオブジェクトも含まれています。実際には、RPSLについて一様に実装された標準は存在せず、さまざまな場所に部分的に文書化された大まかな概要があるにすぎません。

This has the potential to create interoperability issues. Some are addressed by NRTMv4, like having a consistent character set when mirroring data between implementations. However, some issues can not be addressed in this way, such as one implementation introducing a new object class that is entirely unknown to another implementation.

これは相互運用性の問題を生じさせる可能性があります。実装間でデータをミラーリングする際の文字集合を一貫させることなど、一部の問題は NRTMv4 で対処されています。しかし、ある実装が、別の実装にはまったく未知の新しいオブジェクトクラスを導入する場合のように、この方法では対処できない問題もあります。

A mirror client SHOULD be able to handle unknown object classes and objects that are invalid according to its own validation rules, which may mean simply discarding them without rejecting remaining objects or preventing future updates.

ミラークライアントは、未知のオブジェクトクラスや、自身の検証規則に照らして無効なオブジェクトを処理できるべきです (SHOULD)。これは、残りのオブジェクトを拒否したり将来の更新を妨げたりすることなく、それらを単に破棄することを意味する場合があります。

It is RECOMMENDED for mirror clients to log these cases, particularly those where an object was discarded due to violating validation rules. These cases create an inconsistency between the IRR objects of the server and client, and logs facilitate later analysis.

ミラークライアントは、これらのケース、特に検証規則違反によりオブジェクトが破棄されたケースを記録することが推奨されます (RECOMMENDED)。これらのケースは、サーバとクライアントのIRRオブジェクトの間に不整合を生じさせるため、ログは後の分析に役立ちます。

It is recommended for mirror clients to be flexible where possible and reasonable when applying their own validation rules to IRR objects retrieved from mirror servers. For example, a route object with an origin attribute that is not a valid AS number can't be usefully interpreted. There is no way for an IRR server to correctly parse and index such an object. However, a route-set object whose name does not start with "RS-" [RFC2622], or an inetnum with an unknown extra "org" attribute, still allows the mirror client to interpret it unambiguously even if it does not meet the mirror client's own validation rules for authoritative records.

ミラークライアントは、ミラーサーバから取得したIRRオブジェクトに自身の検証規則を適用する際、可能で妥当な範囲で柔軟に対応することが推奨されます。たとえば、origin 属性が有効なAS番号ではない route オブジェクトは、有用な形で解釈できません。IRRサーバがそのようなオブジェクトを正しく解析してインデックス化する方法はありません。しかし、名前が "RS-" [RFC2622] で始まらない route-set オブジェクトや、未知の余分な "org" 属性を持つ inetnum は、権威あるレコードに対するミラークライアント自身の検証規則を満たしていなくても、ミラークライアントがあいまいさなく解釈できます。

9.3. Intermediate Mirror Instances

9.3. 中間ミラーインスタンス

An IRR Database generally has a single authoritative source. In some cases, an instance run by a third party will function as a kind of intermediate: both being a mirror client, mirroring IRR objects from the authoritative source, and simultaneously functioning as a mirror server to yet another mirror client.

IRRデータベースには、一般に単一の権威あるソースがあります。場合によっては、第三者が運用するインスタンスが一種の中間として機能し、権威あるソースからIRRオブジェクトをミラーリングするミラークライアントであると同時に、さらに別のミラークライアントに対するミラーサーバとしても機能することがあります。

There are various operational reasons for such a setup, such as the intermediate filtering certain records. Regardless of the reason, the mirror client and server function of an IRR server must be treated as separate processes. In particular, this means they MUST have separate session IDs. The intermediate server MUST NOT republish the same files it retrieved from the authoritative source with the same session ID.

このような構成には、中間サーバが特定のレコードをフィルタリングするなど、さまざまな運用上の理由があります。理由にかかわらず、IRRサーバのミラークライアント機能とミラーサーバ機能は、別々のプロセスとして扱わなければなりません。特に、これらは別々のセッションIDを持たなければなりません (MUST)。中間サーバは、権威あるソースから取得したファイルを、同じセッションIDのまま再公開してはなりません (MUST NOT)。

9.4. Reading from Local Files

9.4. ローカルファイルからの読み取り

In the typical use case for NRTMv4, a mirror client retrieves files from an HTTPS endpoint. However, implementations MAY also support reading from files on the local filesystem instead for when operators want to use a different method to retrieve or distribute the files. When reading from local files, mirror clients SHOULD still follow all validation rules, including the validation of the signature and hashes, to prevent corrupted or tampered data from being loaded.

NRTMv4の典型的な使用例では、ミラークライアントはHTTPSエンドポイントからファイルを取得します。ただし、運用者がファイルの取得や配布に別の方法を使いたい場合に備えて、実装はその代わりにローカルファイルシステム上のファイルからの読み取りもサポートしてもよい (MAY)。ローカルファイルから読み取る場合でも、破損または改ざんされたデータが読み込まれることを防ぐため、ミラークライアントは署名とハッシュの検証を含むすべての検証規則に従うべきです (SHOULD)。

9.5. Storage Considerations

9.5. ストレージに関する考慮事項

After publishing a new Update Notification File and absent local policy, a mirror server SHOULD remove any Snapshot and Delta Files that are no longer referenced, as unreferenced files consume storage unnecessarily. To avoid race conditions where a mirror client retrieves an Update Notification File moments before it is updated, mirror servers SHOULD retain unreferenced files for at least 5 minutes after a new Update Notification File is published.

新しいUpdate Notification Fileを公開した後、ローカルポリシーがない限り、参照されなくなったSnapshot FileとDelta Fileは不必要にストレージを消費するため、ミラーサーバはそれらを削除すべきです (SHOULD)。ミラークライアントがUpdate Notification Fileの更新直前にそれを取得した場合の競合状態を避けるため、ミラーサーバは、新しいUpdate Notification Fileの公開後少なくとも5分間は、参照されなくなったファイルを保持すべきです (SHOULD)。

9.6. Public Key Rotation

9.6. 公開鍵のローテーション

It is recommended that the IRR Database operators rotate the signing key on their mirror server with a frequency that is not disruptive to operations but preserves the familiarity of the practices to accomplish key rotation. Many organizations have settled on annual cycles. The next_signing_key field in the Update Notification File supports in-band key rotation using the following process:

IRRデータベースの運用者は、運用に支障をきたさず、かつ鍵のローテーションを行う手順への習熟が保たれる頻度で、ミラーサーバの署名鍵をローテーションすることが推奨されます。多くの組織は年次サイクルに落ち着いています。Update Notification Fileのnext_signing_keyフィールドは、次の手順によるインバンドの鍵ローテーションをサポートします。

* The server operator generates a new key and configures this in the mirror server implementation as the upcoming new signing key.

* サーバ運用者は新しい鍵を生成し、それを次に使用する新しい署名鍵としてミラーサーバの実装に設定します。

* The mirror server MUST include this key in the next_signing_key field in any Update Notification File generated while the new signing key is configured. Hence, the new signing key will start being propagated to the mirror clients with the next publication of the Notification File, which will take at most 24 hours. Mirror server implementations MAY offer a method to cause the Update Notification File to be refreshed earlier, with the next_signing_key included, and thus start the propagation earlier.

* ミラーサーバは、新しい署名鍵が設定されている間に生成するすべてのUpdate Notification Fileのnext_signing_keyフィールドに、この鍵を含めなければなりません (MUST)。したがって、新しい署名鍵は、次回のNotification Fileの公開とともにミラークライアントへの伝播が始まり、これは長くても24時間以内に行われます。ミラーサーバの実装は、next_signing_keyを含めた状態でUpdate Notification Fileをより早く更新させ、伝播をより早く開始させる方法を提供してもよい (MAY)。

* When mirror clients retrieve the Update Notification File next, they MUST detect the next_signing_key field and store the key in their configuration.

* ミラークライアントは、次にUpdate Notification Fileを取得したときに、next_signing_keyフィールドを検出し、その鍵を自身の設定に保存しなければなりません (MUST)。

* After allowing mirror clients time to have seen the new Update Notification File with the next_signing_key field, the mirror server operator configures the new key as the currently active key and removes the old key. Any Update Notification File generated after this point MUST be signed with this new key and will not contain a next_signing_key field.

* next_signing_keyフィールドを持つ新しいUpdate Notification Fileをミラークライアントが確認できるだけの時間を置いた後、ミラーサーバ運用者は、新しい鍵を現在有効な鍵として設定し、古い鍵を削除します。この時点以降に生成されるUpdate Notification Fileは、この新しい鍵で署名されなければならず (MUST)、next_signing_keyフィールドを含みません。

* The RECOMMENDED period between publication of the upcoming key in the next_signing_key field and removal of the old key is one week. This offers all active clients a reasonable chance to follow the rotation process.

* next_signing_keyフィールドでの次期鍵の公開から古い鍵の削除までの期間は、1週間とすることが推奨されます (RECOMMENDED)。これにより、すべてのアクティブなクライアントがローテーション手順に従うための妥当な機会が確保されます。

* When mirror clients retrieve an Update Notification File and find that the signature does not match, they MUST attempt to verify against a next_signing_key encountered in a previous (valid) file. If the signature matches for this new key, the client MUST update its configuration to use the new key for validation. After this, the client MUST NOT use the old key for validation at any time; a mirror server cannot switch back to an old key.

* ミラークライアントは、Update Notification Fileを取得して署名が一致しないことが分かった場合、以前の(有効な)ファイルで見つけたnext_signing_keyに対して検証を試みなければなりません (MUST)。署名がこの新しい鍵で一致した場合、クライアントは、検証にその新しい鍵を使用するよう設定を更新しなければなりません (MUST)。その後、クライアントは検証に古い鍵をいかなる時点でも使用してはなりません (MUST NOT)。ミラーサーバが古い鍵に戻すことはできないためです。

If a mirror client never retrieves an Update Notification file at any point during the rotation process, it will no longer be able to verify the signature. In that scenario manual recovery is required, similar to a first time configuration of a new mirror client.

ミラークライアントがローテーション手順の間に一度もUpdate Notification fileを取得しなかった場合、そのクライアントは署名を検証できなくなります。その場合は、新しいミラークライアントを初めて設定するときと同様に、手動での復旧が必要です。

9.7. Scalability

9.7. スケーラビリティ

As NRTMv4 uses HTTPS for all file retrieval, mirror servers can use standard HTTP caching infrastructure, horizontal scaling, and CDN integration to handle load. Caching considerations for each file type are discussed in the respective Cache Concerns sections.

NRTMv4はすべてのファイル取得にHTTPSを使用するため、ミラーサーバは、標準的なHTTPキャッシュ基盤、水平スケーリング、CDNとの統合を利用して負荷を処理できます。各ファイル種別のキャッシュに関する考慮事項は、それぞれのCache Concerns節で説明しています。

Delta Files are typically small, as they only contain changes since the previous version. Snapshot Files can be larger, but all files may be compressed with GZIP to reduce storage and bandwidth requirements.

Delta Fileは、前のバージョンからの変更のみを含むため、通常は小さくなります。Snapshot Fileはより大きくなる場合がありますが、すべてのファイルはGZIPで圧縮して、ストレージと帯域幅の要件を減らすことができます。

9.8. NRTMv3 Compatibility

9.8. NRTMv3との互換性

NRTMv4 is a new protocol that is not backwards compatible with NRTMv3. There is no migration path between the two protocols; operators wishing to support both can run them in parallel.

NRTMv4は新しいプロトコルであり、NRTMv3との後方互換性はありません。2つのプロトコル間の移行パスはありません。両方をサポートしたい運用者は、それらを並行して稼働させることができます。

11. Security Considerations

11. セキュリティに関する考慮事項

IRR objects serve many purposes, including automated network configuration and filtering. Manipulation of IRR objects can therefore have a significant security impact. However, security in existing protocols is mostly absent.

IRRオブジェクトは、ネットワーク設定の自動化やフィルタリングなど、多くの目的に使われます。そのため、IRRオブジェクトの改ざんは、セキュリティ上の重大な影響を及ぼす可能性があります。しかし、既存のプロトコルにおけるセキュリティはほとんど存在しません。

Before NRTMv4, the most common protocols for IRR Database mirroring are FTP for retrieving full snapshots and NRTM version 3 for retrieving later changes. There are no provisions for integrity or authenticity and there are various scenarios where mirroring may not be reliable.

NRTMv4以前は、IRRデータベースのミラーリングに最もよく使われるプロトコルは、完全なスナップショットを取得するためのFTPと、その後の変更を取得するためのNRTMバージョン3でした。完全性や真正性に関する規定はなく、ミラーリングが信頼できない可能性のあるシナリオが様々に存在します。

NRTMv4 requires integrity verification. The Update Notification File is signed and clients must verify its signature. The signed Update Notification File contains SHA-256 hashes of all Delta and Snapshot Files, which clients must verify through calculating and comparing hashes on retrieval. Together, the signature and hash verification form a chain of trust from the signing key to each individual file. Additionally, the channel security offered by HTTPS further limits security risks.

NRTMv4は完全性の検証を必要とします。Update Notification Fileは署名され、クライアントはその署名を検証しなければなりません。署名されたUpdate Notification Fileには、すべてのDelta FileおよびSnapshot FileのSHA-256ハッシュが含まれており、クライアントは取得時にハッシュを計算して比較することで、それらを検証しなければなりません。署名とハッシュの検証が合わさって、署名鍵から個々のファイルまでの信頼の連鎖を形成します。さらに、HTTPSが提供するチャネルのセキュリティが、セキュリティ上のリスクをいっそう抑えます。

By allowing publication on any HTTPS endpoint, NRTMv4 allows for extensive scaling and there are many existing techniques and services to protect against denial-of-service attacks. In contrast, NRTMv3 required mirror clients to directly query the IRR server instance with special WHOIS queries. This scales poorly and there are no standard protections against denial-of-service available.

NRTMv4は任意のHTTPSエンドポイントでの公開を認めているため、大規模なスケーリングが可能であり、サービス拒否攻撃から保護するための既存の手法やサービスも数多くあります。対照的に、NRTMv3では、ミラークライアントが特別なWHOISクエリでIRRサーバインスタンスに直接問い合わせる必要がありました。これはスケーラビリティに乏しく、サービス拒否攻撃に対して利用できる標準的な保護もありません。

Since Snapshot and Delta Files may be compressed with GZIP, a maliciously crafted compressed file could expand to a much larger size than expected, potentially exhausting memory or disk resources. Implementations SHOULD enforce limits on the decompressed size of files relative to the compressed size or the expected data volume for the IRR Database. See also the security considerations of [RFC6713].

Snapshot FileとDelta FileはGZIPで圧縮される場合があるため、悪意をもって作成された圧縮ファイルが、想定よりはるかに大きなサイズに展開され、メモリやディスクの資源を使い果たす可能性があります。実装は、圧縮サイズ、またはIRRデータベースで想定されるデータ量に対する、ファイルの展開後サイズの上限を強制すべきです (SHOULD)。[RFC6713]のセキュリティに関する考慮事項も参照してください。

The HTTPS endpoint used for NRTMv4 MUST be configured according to the best practices in [BCP195]. Mirror clients MUST NOT use other protocols than HTTPS, such as HTTP or FTP.

NRTMv4に使用するHTTPSエンドポイントは、[BCP195]のベストプラクティスに従って設定しなければなりません (MUST)。ミラークライアントは、HTTPやFTPなど、HTTPS以外のプロトコルを使用してはなりません (MUST NOT)。
