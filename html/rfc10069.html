Managing Multiple Paths for a QUIC Connection
QUICコネクションのための複数パスの管理
Abstract
概要

This document specifies a multipath extension for the QUIC protocol to enable the simultaneous usage of multiple paths for a single connection. It introduces explicit path identifiers to create, delete, and manage multiple paths. This document does not specify address discovery or management, nor how applications using QUIC schedule traffic over multiple paths.

本文書は、単一のコネクションで複数のパスを同時に利用できるようにするための、QUICプロトコルのマルチパス拡張を規定します。パスの作成、削除、管理を行うために、明示的なパス識別子を導入します。本文書は、アドレスの発見や管理については規定せず、QUICを使用するアプリケーションが複数のパスにまたがってトラフィックをどのようにスケジューリングするかについても規定しません。

1. Introduction
1. はじめに

This document specifies an extension to QUIC version 1 [QUIC-TRANSPORT] to enable the simultaneous usage of multiple paths for a single connection, using the same or different 4-tuples (of source/destination port numbers and source/destination IP addresses).

本文書は、QUICバージョン1 [QUIC-TRANSPORT] に対する拡張を規定します。この拡張により、同一または異なる4タプル (送信元/宛先ポート番号と送信元/宛先IPアドレス) を用いて、単一のコネクションで複数のパスを同時に利用できるようになります。

Connection migration as specified in Section 9 of [QUIC-TRANSPORT] directs a peer to switch sending through a new preferred path and, if successful, to release resources associated with the old path. The multipath extension specified in this document builds on this mechanism but introduces a path identifier, or path ID, to manage connection IDs and packet number spaces per path, enabling the use of multiple paths simultaneously. As such, a path in this extension is defined by its path ID. Note that it therefore is possible to have multiple paths / path IDs for the same 4-tuple.

[QUIC-TRANSPORT] の第9節で規定されるコネクションマイグレーションは、ピアに対して、新しい優先パスを通じた送信への切り替えを指示し、成功した場合には古いパスに関連付けられたリソースを解放させます。本文書で規定するマルチパス拡張はこの仕組みを土台としていますが、パス識別子 (パスID) を導入して、パスごとにコネクションIDとパケット番号空間を管理し、複数のパスの同時利用を可能にします。したがって、この拡張におけるパスは、そのパスIDによって定義されます。このため、同一の4タプルに対して複数のパス / パスIDを持つことが可能である点に注意してください。

The connection ID of a packet binds the packet to a path ID and therefore to a packet number space. That means each connection ID is associated with exactly one path ID but multiple connection IDs are usually issued for each path ID. The same path ID is used in both directions, starting with 0 for the initial path. Path IDs are monotonically increasing and cannot be reused.

パケットのコネクションIDは、そのパケットをパスIDに、したがってパケット番号空間に結び付けます。つまり、各コネクションIDはちょうど1つのパスIDに関連付けられますが、通常は各パスIDに対して複数のコネクションIDが発行されます。同じパスIDが両方向で使用され、最初のパスには0から始まるIDが使われます。パスIDは単調増加し、再利用することはできません。

This extension uses multiple packet number spaces, specifically one for each path. Each path ID-specific packet number space starts at packet number 0. As such, each path maintains distinct packet number states for sending and receiving packets, as in [QUIC-TRANSPORT]. Using multiple packet number spaces enables direct use of the loss detection and congestion control mechanisms defined in [QUIC-RECOVERY] on a per-path basis. However, use of multiple packet number spaces requires non-zero connection IDs in order to identify the path and the respective packet number space, as well as a modified Authenticated Encryption with Associated Data (AEAD) calculation including the path ID (see Section 2.4).

この拡張は複数のパケット番号空間を使用し、具体的にはパスごとに1つずつ使用します。パスID固有の各パケット番号空間は、パケット番号0から始まります。したがって、[QUIC-TRANSPORT] と同様に、各パスはパケットの送信と受信について個別のパケット番号の状態を保持します。複数のパケット番号空間を使用することで、[QUIC-RECOVERY] で定義される損失検出と輻輳制御の仕組みを、パスごとに直接利用できます。ただし、複数のパケット番号空間を使用するには、パスと対応するパケット番号空間を識別するために長さ0ではないコネクションIDが必要であり、さらにパスIDを含む、変更された Authenticated Encryption with Associated Data (AEAD) の計算も必要です (第2.4節を参照)。

As such, this extension specifies a departure from the specification of path management in Section 9 of [QUIC-TRANSPORT] and therefore requires a new transport parameter, as specified in Section 2.1, to indicate support of the multipath extension specified in this document.

このように、この拡張は [QUIC-TRANSPORT] の第9節にあるパス管理の仕様からの逸脱を規定するものであり、したがって、本文書で規定するマルチパス拡張のサポートを示すために、第2.1節で規定する新しいトランスポートパラメータが必要になります。

Further, this document specifies the needed path management mechanisms for path initiation in Section 3.1, handling of per-path connection IDs in Section 3.2, signaling of preferred path usage in Section 3.3, and explicit removal of paths that have been abandoned in Section 3.4. Note that in this extension, a QUIC server does not initiate the creation of a path, but it has to validate a new path created by a client.

さらに、本文書は、必要なパス管理の仕組みとして、第3.1節でのパスの開始、第3.2節でのパスごとのコネクションIDの扱い、第3.3節での優先パス利用のシグナリング、第3.4節での放棄されたパスの明示的な削除を規定します。なお、この拡張では、QUICサーバはパスの作成を開始しませんが、クライアントが作成した新しいパスを検証しなければなりません。

This extension does not cover address discovery and management. The extension specified in this document can be used as is if address management and the actual decision to set up or tear down paths are handled by the application. This document does not prevent future extensions from defining mechanisms to cope with the remaining scenarios.

この拡張は、アドレスの発見と管理を対象としません。アドレス管理と、パスを設定するか解除するかの実際の判断がアプリケーションによって扱われる場合、本文書で規定する拡張はそのまま使用できます。本文書は、残りのシナリオに対処する仕組みを将来の拡張が定義することを妨げるものではありません。

Further, this document does not specify scheduling algorithms that define how multiple, simultaneously open paths are used to send packets. As these differ depending on application requirements, only some basic implementation guidance is discussed in Section 5. This extension can be used with different scheduling algorithms that, e.g., can range from support for failover to simultaneous use of the aggregated capacity across all open paths. There are currently no IETF specifications that define scheduling algorithms for simultaneously (i.e., concurrently) using multiple paths.

さらに、本文書は、同時に開かれた複数のパスをパケット送信にどのように使用するかを定めるスケジューリングアルゴリズムを規定しません。これらはアプリケーションの要件によって異なるため、第5節では基本的な実装上のガイダンスのみを論じます。この拡張は、たとえばフェイルオーバーのサポートから、開いているすべてのパスにまたがる集約された容量の同時利用までの範囲に及び得る、さまざまなスケジューリングアルゴリズムとともに使用できます。現時点では、複数のパスを同時に (すなわち並行して) 使用するためのスケジューリングアルゴリズムを定義するIETFの仕様はありません。

Specifically, while failover between Wi-Fi and mobile networks is a well-known multipath use case, it only temporarily uses two paths at the same time to avoid transmission pauses. Simultaneous path usage generally, however, needs more consideration than specified in this document to avoid negative performance impacts, e.g., when stream data is distributed over multiple paths with different delays.

具体的には、Wi-Fiとモバイルネットワークの間のフェイルオーバーはよく知られたマルチパスのユースケースですが、これは送信の中断を避けるために、一時的に2つのパスを同時に使用するだけです。一方、パスの同時利用全般では、たとえばストリームデータが異なる遅延を持つ複数のパスに分散される場合などに、性能への悪影響を避けるため、本文書で規定する以上の検討が必要です。

The operational considerations for QUIC are addressed in [RFC9312]. They also apply to QUIC connections using the extensions defined in this document. An additional complexity is that applications might use a combination of monitored and non-monitored paths, but that complexity already exists when using path migration as defined in [QUIC-TRANSPORT].

QUICの運用上の考慮事項は [RFC9312] で扱われています。それらは、本文書で定義する拡張を使用するQUICコネクションにも適用されます。追加の複雑さとして、アプリケーションが監視されているパスと監視されていないパスの組み合わせを使用する可能性がありますが、その複雑さは、[QUIC-TRANSPORT] で定義されるパスマイグレーションを使用する場合にもすでに存在します。

2. Connection Lifecycle and Packet Protection
2. コネクションのライフサイクルとパケット保護

This document defines a new transport parameter initial_max_path_id to indicate the support of the multipath extension. If either of the endpoints does not advertise the initial_max_path_id transport parameter, then both endpoints MUST NOT use any frame or mechanism defined in this document. If both endpoints advertise the initial_max_path_id transport parameter, once the handshake is completed, a new AEAD usage applies to all 1-RTT packets, as specified in Section 2.4, and new paths can be used, as specified in Section 3. As specified in Section 4, the new frames defined in this document can only be sent in 1-RTT packets.

本文書は、マルチパス拡張のサポートを示すために、新しいトランスポートパラメータ initial_max_path_id を定義します。いずれかのエンドポイントが initial_max_path_id トランスポートパラメータをアドバタイズしない場合、両方のエンドポイントは、本文書で定義されるいかなるフレームや仕組みも使用してはなりません (MUST NOT)。両方のエンドポイントが initial_max_path_id トランスポートパラメータをアドバタイズした場合、ハンドシェイクが完了すると、第2.4節で規定される新しいAEADの使用がすべての1-RTTパケットに適用され、第3節で規定されるとおり新しいパスを使用できます。第4節で規定されるとおり、本文書で定義される新しいフレームは1-RTTパケットでのみ送信できます。

The transport parameter negotiation enables incremental deployment of implementations of the multipath extension.

トランスポートパラメータのネゴシエーションにより、マルチパス拡張の実装を段階的に展開できます。

initial_max_path_id (パラメータID 0x3e):

Parameter value is a variable-length integer specifying the maximum path ID an endpoint is willing to maintain at connection initiation. This value MUST NOT exceed 2^32-1, which is the maximum allowed value for the path ID due to restrictions on the nonce calculation (see Section 2.4).

パラメータ値は、エンドポイントがコネクション開始時に維持してもよいとするパスIDの最大値を指定する、可変長整数です。この値は 2^32-1 を超えてはなりません (MUST NOT)。これは、ノンス計算上の制限により、パスIDに許される最大値です (第2.4節を参照)。

The initial_max_path_id transport parameter limits the initial maximum number of open paths that can be used during a connection. For example, if initial_max_path_id is set to 1, only connection IDs associated with path IDs 0 and 1 should be issued by the peer. If an endpoint receives an initial_max_path_id transport parameter with value 0, the peer aims to enable the multipath extension without allowing extra paths immediately.

initial_max_path_id トランスポートパラメータは、コネクション中に使用できる、開かれたパスの初期の最大数を制限します。たとえば、initial_max_path_id が1に設定されている場合、パスID 0と1に関連付けられたコネクションIDのみがピアによって発行されるべきです。エンドポイントが値0の initial_max_path_id トランスポートパラメータを受信した場合、ピアは、追加のパスを直ちには許可せずに、マルチパス拡張を有効にすることを意図しています。

Setting initial_max_path_id parameter is equivalent to sending a MAX_PATH_ID frame (Section 4.6) with the same value. As such to allow for the use of more paths later, endpoints can send the MAX_PATH_ID frame to increase the maximum allowed path ID.

initial_max_path_id パラメータの設定は、同じ値を持つ MAX_PATH_ID フレーム (第4.6節) の送信と等価です。したがって、後でより多くのパスを使用できるようにするため、エンドポイントは MAX_PATH_ID フレームを送信して、許可されるパスIDの最大値を引き上げることができます。

If an initial_max_path_id transport parameter value higher than 2^32-1 is received, the receiver MUST close the connection with an error of type TRANSPORT_PARAMETER_ERROR.

2^32-1 より大きい initial_max_path_id トランスポートパラメータ値を受信した場合、受信側は TRANSPORT_PARAMETER_ERROR 型のエラーでコネクションを閉じなければなりません (MUST)。

When advertising the initial_max_path_id transport parameter, endpoints MUST use Source and Destination Connection IDs with non-zero lengths. If an initial_max_path_id transport parameter is received and the carrying packet contains a zero-length connection ID, the receiver MUST treat this as a connection error of type PROTOCOL_VIOLATION and close the connection.

initial_max_path_id トランスポートパラメータをアドバタイズする場合、エンドポイントは、長さが0ではない送信元および宛先コネクションIDを使用しなければなりません (MUST)。initial_max_path_id トランスポートパラメータを受信し、それを運ぶパケットが長さ0のコネクションIDを含んでいる場合、受信側はこれを PROTOCOL_VIOLATION 型のコネクションエラーとして扱い、コネクションを閉じなければなりません (MUST)。

Cipher suites with a nonce shorter than 12 bytes cannot be used together with the multipath extension. If such a cipher suite is selected and the use of the multipath extension is supported, endpoints MUST abort the handshake with an error of type TRANSPORT_PARAMETER_ERROR.

12バイトより短いノンスを持つ暗号スイートは、マルチパス拡張と併用できません。そのような暗号スイートが選択され、かつマルチパス拡張の使用がサポートされている場合、エンドポイントは TRANSPORT_PARAMETER_ERROR 型のエラーでハンドシェイクを中止しなければなりません (MUST)。

The initial_max_path_id parameter MUST NOT be remembered for use in a subsequent connection (Section 7.4.1 of [QUIC-TRANSPORT]).

initial_max_path_id パラメータは、後続のコネクションで使用するために記憶してはなりません (MUST NOT) ([QUIC-TRANSPORT] の第7.4.1節)。

2.2. Relation to Other Transport Parameters
2.2. 他のトランスポートパラメータとの関係

When the QUIC multipath extension is used, the active_connection_id_limit transport parameter [QUIC-TRANSPORT] limits the maximum number of active connection IDs per path. As defined in Section 5.1.1 of [QUIC-TRANSPORT], connection IDs that are issued and not retired are considered active.

QUICマルチパス拡張を使用する場合、active_connection_id_limit トランスポートパラメータ [QUIC-TRANSPORT] は、パスごとのアクティブなコネクションIDの最大数を制限します。[QUIC-TRANSPORT] のセクション5.1.1で定義されているとおり、発行されて廃棄されていないコネクションIDはアクティブとみなされます。

If an endpoint receives a disable_active_migration transport parameter, it is forbidden to establish new paths to the peer's handshake address. However, establishment of additional paths to other peer addresses (e.g., carried by peer's preferred_address) is immediately valid.

エンドポイントが disable_active_migration トランスポートパラメータを受信した場合、そのエンドポイントはピアのハンドシェイクアドレスへの新しいパスを確立することを禁じられます。ただし、ピアの他のアドレス（例：ピアの preferred_address で通知されるもの）への追加パスの確立は、直ちに有効です。

If the server uses the preferred_address transport parameter, clients cannot assume that the initial server address and the addresses contained in this parameter can be simultaneously used for multipath (Section 9.6.2 of [QUIC-TRANSPORT]). Use of the preferred address with the same local address is considered as a migration event that does not change the path ID. A such, the path ID for the connection ID specified in the preferred_address transport parameter is 0.

サーバが preferred_address トランスポートパラメータを使用する場合、クライアントは、最初のサーバアドレスとこのパラメータに含まれるアドレスをマルチパスで同時に使用できると想定してはなりません（[QUIC-TRANSPORT] のセクション9.6.2）。同じローカルアドレスでの preferred address の使用は、パスIDを変更しないマイグレーションイベントとみなされます。したがって、preferred_address トランスポートパラメータで指定されたコネクションIDのパスIDは0です。

2.3. Handling ACK and PATH_ACK in 0-RTT and 1-RTT
2.3. 0-RTTおよび1-RTTにおけるACKとPATH_ACKの扱い

The PATH_ACK frame (see Section 4.1) is used to acknowledge 1-RTT packets. Compared to the ACK frame, as specified in Section 19.3 of [QUIC-TRANSPORT], the PATH_ACK frame additionally contains the path ID to identify the path-specific packet number space. ACK frames when used with the multipath extension acknowledge packets for the path with path ID 0. As multipath support is unknown during the handshake, acknowledgments of Initial and Handshake packets are sent using ACK frames.

PATH_ACK フレーム（セクション4.1参照）は、1-RTTパケットを確認応答するために使用されます。[QUIC-TRANSPORT] のセクション19.3で規定されている ACK フレームと比較して、PATH_ACK フレームはさらに、パスごとのパケット番号空間を識別するパスIDを含みます。マルチパス拡張とともに使用される ACK フレームは、パスID 0のパスのパケットを確認応答します。ハンドシェイク中はマルチパスのサポートが不明であるため、Initial パケットと Handshake パケットの確認応答は ACK フレームを使用して送信されます。

After the handshake concludes with support for the multipath extension, endpoints SHOULD use PATH_ACK frames instead of ACK frames, including for so far unacknowledged 0-RTT packets using path ID 0. Endpoints MUST still process ACK frames that acknowledge 0-RTT packets or 1-RTT packets. For example, a sender could negotiate multipath support for later use and keep only the initial path with path ID 0 for a while. During this single-path period, the sender might prefer to send ACK frames.

マルチパス拡張のサポートを伴ってハンドシェイクが完了した後、エンドポイントは、これまで確認応答されていない0-RTTパケットも含め、パスID 0を用いて ACK フレームの代わりに PATH_ACK フレームを使用すべきです (SHOULD)。エンドポイントは、0-RTTパケットまたは1-RTTパケットを確認応答する ACK フレームを引き続き処理しなければなりません (MUST)。例えば、送信側は、後で使用するためにマルチパスのサポートをネゴシエートしつつ、しばらくの間はパスID 0の初期パスのみを維持することがあります。この単一パスの期間中、送信側は ACK フレームを送信することを選ぶかもしれません。

2.4. Nonce Calculation after Handshake Completion
2.4. ハンドシェイク完了後のナンスの計算

Section 5.3 of [QUIC-TLS] specifies AEAD usage, particularly the use of a nonce, N, formed by combining the packet protection Initialization Vector (IV) with the packet number. When multiple packet number spaces are used, the packet number alone would not guarantee the uniqueness of the nonce. Therefore, the nonce N is calculated for 1-RTT packets if the multipath extension is used by combining the packet protection IV with the packet number and with the 32 bits of the path ID. In order to guarantee the uniqueness of the nonce, the path ID is limited to a max value of 2^32-1, as specified in Section 2.1.

[QUIC-TLS] のセクション5.3は、AEADの使用方法、特に、パケット保護の初期化ベクタ (IV) とパケット番号を組み合わせて作られるナンス N の使用方法を規定しています。複数のパケット番号空間を使用する場合、パケット番号だけではナンスの一意性を保証できません。そのため、マルチパス拡張を使用する場合、1-RTTパケットのナンス N は、パケット保護IVを、パケット番号および32ビットのパスIDと組み合わせて計算されます。ナンスの一意性を保証するため、セクション2.1で規定されているとおり、パスIDの最大値は 2^32-1 に制限されます。

To calculate the nonce, a 96-bit Path-and-Packet-Number (PPN) is composed of the 32 bits of the path ID in network byte order, two zero bits, and the 62 bits of the reconstructed QUIC packet number in network byte order, as illustrated in Figure 1.

ナンスを計算するために、96ビットのPath-and-Packet-Number (PPN) を、ネットワークバイトオーダーの32ビットのパスID、2つのゼロビット、およびネットワークバイトオーダーの62ビットの復元されたQUICパケット番号から構成します。これを図1に示します。 

     PPN {
       Path ID (32),
       Zeroes (2) = 0b00,
       Packet Number (62)
     }

The exclusive OR of the padded packet number and the IV forms the AEAD nonce. An AEAD algorithm where the nonce length is less than 12 bytes cannot be used with the QUIC multipath extension. 2.5. Key Phase Update Process
2.5. Key Phase の更新プロセス

The Key Phase bit update process is specified in Section 6 of [QUIC-TLS]. The general principles of key update are not changed in this specification. Following [QUIC-TLS], the Key Phase bit is used to indicate which packet protection keys are used to protect the packet. The Key Phase bit is toggled to signal each subsequent key update.

Key Phase ビットの更新プロセスは、[QUIC-TLS] のセクション6で規定されています。鍵更新の一般原則は、本仕様では変更されません。[QUIC-TLS] に従い、Key Phase ビットは、パケットの保護にどのパケット保護鍵が使用されるかを示すために使用されます。Key Phase ビットは、以降の鍵更新ごとに反転されて、その更新を通知します。

Because of network delays, packets protected with the older key might arrive later than the packets protected with the new key. However, receivers can solely rely on the Key Phase bit to determine the corresponding packet protection key, assuming that there is a sufficiently large interval between two consecutive key updates (Section 6.5 of [QUIC-TLS]).

ネットワーク遅延のため、古い鍵で保護されたパケットが、新しい鍵で保護されたパケットよりも後に到着することがあります。しかし、連続する2回の鍵更新の間に十分に長い間隔があると仮定すれば、受信側は、対応するパケット保護鍵を判断するために Key Phase ビットのみに依拠できます（[QUIC-TLS] のセクション6.5）。

When this specification is used, endpoints SHOULD wait for at least three times the largest Probe Timeout (PTO) (see Section 6.2 of [QUIC-RECOVERY]) among all the paths before initiating a new key update after receiving an acknowledgment that confirms the receipt of the previous key update. This interval is different from that in [QUIC-TLS], which used three times the PTO of the single path.

本仕様を使用する場合、エンドポイントは、前回の鍵更新の受信を確認する確認応答を受信した後、新たな鍵更新を開始する前に、すべてのパスのうち最大の Probe Timeout (PTO)（[QUIC-RECOVERY] のセクション6.2参照）の少なくとも3倍の時間待つべきです (SHOULD)。この間隔は、単一パスのPTOの3倍を用いていた [QUIC-TLS] の間隔とは異なります。

Since packets that arrive after their decryption key has been discarded will be dropped, the choice of three times the largest PTO is a trade-off: Longer delays reduce the probability of losing packets, but keeping old keys longer can negatively impact the security of the protocol. The use of three times the largest PTO aims to minimize packet lost for all paths and therefore limits the impact on performance.

復号鍵が破棄された後に到着したパケットは破棄されるため、最大PTOの3倍という選択はトレードオフです。遅延を長くすると、パケットを失う確率は下がりますが、古い鍵をより長く保持することは、プロトコルのセキュリティに悪影響を及ぼす可能性があります。最大PTOの3倍を用いることは、すべてのパスについてパケット損失を最小限に抑えることを目的としており、したがって性能への影響を抑えます。

Following Section 5.4 of [QUIC-TLS], the Key Phase bit is protected, so sending multiple packets with the Key Phase bit flipping at the same time should not cause activity across different paths to be linkable by an observer.

[QUIC-TLS] のセクション5.4に従い、Key Phase ビットは保護されているため、Key Phase ビットが同時に反転する複数のパケットを送信しても、異なるパスにまたがるアクティビティが観測者によって関連付けられることはないはずです。

2.6. Connection Closure
2.6. コネクションの終了

CONNECTION_CLOSE frames and their processing are unchanged from [QUIC-TRANSPORT]. They can be sent on any open path. Section 10.2 of [QUIC-TRANSPORT] specifies that the closing and draining connection states "SHOULD persist for at least three times the current PTO". When this specification is used, these states SHOULD instead persist for at least three times the largest PTO among all paths.

CONNECTION_CLOSE フレームとその処理は、[QUIC-TRANSPORT] から変更されません。これらは、開いているどのパスでも送信できます。[QUIC-TRANSPORT] のセクション10.2は、closing 状態と draining 状態のコネクションが「現在のPTOの少なくとも3倍の間は持続すべきである (SHOULD)」と規定しています。本仕様を使用する場合、これらの状態は代わりに、すべてのパスのうち最大のPTOの少なくとも3倍の間は持続すべきです (SHOULD)。

The client can open a new path when both endpoints have issued available connection IDs for at least one unused, common path ID, as the same path ID is used in both directions.

マルチパスのサポートを示すハンドシェイクが完了した後、エンドポイントは複数のパスの使用を開始できます。[QUIC-TRANSPORT] のセクション9に従い、本拡張は、クライアントのみが新しいパスを開くことを可能にします。同じパスIDが両方向で使用されるため、クライアントは、両方のエンドポイントが、未使用で共通の少なくとも1つのパスIDについて利用可能なコネクションIDを発行している場合に、新しいパスを開くことができます。

However, this document does not specify when a client decides to initiate or close a path or how multiple open paths are used for sending.

本書は、パスの開始（セクション3.1参照）、パスごとのコネクションIDの発行と廃棄（セクション3.2参照）、パスステータスの管理（セクション3.3参照）、およびパスの終了（セクション3.4参照）を規定します。ただし、本書は、クライアントがいつパスを開始または終了するか、また、開いている複数のパスを送信にどのように使用するかは規定しません。

3.1. Path Initiation and Validation
3.1. パスの開始と検証

To open a new path, an endpoint MUST use a new connection ID associated with an unused path ID. An endpoint MUST use a connection ID associated to the same path ID as used in the packet received by the endpoint when it intends to send packets on the same path.

新しいパスを開くには、エンドポイントは、未使用のパスIDに関連付けられた新しいコネクションIDを使用しなければなりません (MUST)。エンドポイントは、同じパスでパケットを送信しようとする場合、そのエンドポイントが受信したパケットで使用されていたものと同じパスIDに関連付けられたコネクションIDを使用しなければなりません (MUST)。

A client that wants to use a new path MUST validate the peer's address as described in Section 8.2 of [QUIC-TRANSPORT], unless it has previously validated the 4-tuple used for that path.

新しいパスを使用したいクライアントは、そのパスに使用する4タプルを以前に検証済みである場合を除き、[QUIC-TRANSPORT] のセクション8.2に記載されているとおりにピアのアドレスを検証しなければなりません (MUST)。

After receiving packets from the client on a new path, if the server decides to use the new path, the server MUST validate the peer's address before sending any data as described in (Section 8.2 of [QUIC-TRANSPORT]), unless it has previously validated the 4-tuple used for that path. Until the client's address is validated, the anti-amplification limit from Section 8 of [QUIC-TRANSPORT] applies.

新しいパスでクライアントからパケットを受信した後、サーバがその新しいパスを使用すると決定した場合、サーバは、そのパスに使用する4タプルを以前に検証済みである場合を除き、データを送信する前に、([QUIC-TRANSPORT] のセクション8.2に記載されているとおりに) ピアのアドレスを検証しなければなりません (MUST)。クライアントのアドレスが検証されるまでは、[QUIC-TRANSPORT] のセクション8のアンチ増幅制限が適用されます。

If an endpoint sends a PATH_RESPONSE (Section 19.18 of [QUIC-TRANSPORT]), it MUST be sent on the same path as used by the packet that contained the PATH_CHALLENGE frame (Section 19.17 of [QUIC-TRANSPORT]) using a connection ID associated with the same path ID.

エンドポイントが PATH_RESPONSE（[QUIC-TRANSPORT] のセクション19.18）を送信する場合、それは、PATH_CHALLENGE フレーム（[QUIC-TRANSPORT] のセクション19.17）を含んでいたパケットが使用したものと同じパスで、同じパスIDに関連付けられたコネクションIDを使用して送信しなければなりません (MUST)。

The server might receive packets for a yet unused path ID that do not contain a PATH_CHALLENGE frame. Such packets are valid if they can be properly decrypted given a valid connection ID.

サーバは、PATH_CHALLENGE フレームを含まない、まだ未使用のパスID宛てのパケットを受信することがあります。そのようなパケットは、有効なコネクションIDのもとで適切に復号できる場合、有効です。

Each endpoint MUST also validate that a minimum QUIC packet MTU of 1200 bytes is supported on the path. This can be done during initial path validation or separately later if the amplification limit prevents it initially, as specified in Section 8.2.1 of [QUIC-TRANSPORT].

各エンドポイントは、パス上で最小QUICパケットMTUである1200バイトがサポートされていることも検証しなければなりません (MUST)。これは、[QUIC-TRANSPORT] のセクション8.2.1で規定されているとおり、最初のパス検証中に行うことも、増幅制限によって当初は行えない場合に後から別途行うこともできます。

An endpoint that receives packets on a new path and does not want to establish this path is expected to close the path by sending a PATH_ABANDON on another path, as specified in Section 3.4.

新しいパス上でパケットを受信し、そのパスを確立したくないエンドポイントは、セクション3.4で規定されているとおり、別のパス上で PATH_ABANDON を送信することでそのパスを閉じることが期待されます。

An endpoint that has no active connection ID for this path or lacks other resources to immediately configure a new path could delay sending the PATH_RESPONSE until sufficient resources are available. Long delays might cause the peer to repeat the PATH_CHALLENGE and eventually send a PATH_ABANDON, in which case the procedures specified in Section 3.4 apply.

このパスに対するアクティブなコネクションIDを持たないエンドポイント、または新しいパスを直ちに構成するためのその他のリソースが不足しているエンドポイントは、十分なリソースが利用可能になるまで PATH_RESPONSE の送信を遅らせてもよいでしょう。遅延が長いと、ピアが PATH_CHALLENGE を繰り返し、最終的に PATH_ABANDON を送信する可能性があります。その場合は、セクション3.4で規定されている手順が適用されます。

PATH_ACK frames (see Section 4.1) can be returned on any path. If the PATH_ACK is preferred to be sent on the same path as the acknowledged packet (see Section 5.4 for further guidance), it can be beneficial to bundle a PATH_ACK frame with the PATH_RESPONSE frame during path validation.

PATH_ACK フレーム (セクション4.1を参照) は、任意のパス上で返送できます。PATH_ACK を、確認応答の対象となるパケットと同じパス上で送信することが望ましい場合 (詳細な指針はセクション5.4を参照)、パス検証中に PATH_ACK フレームを PATH_RESPONSE フレームとバンドルすると有益なことがあります。

If validation succeeds, the client can continue to use the path. If validation fails, the client MUST NOT use the path and can remove any status associated to the path initiation attempt. As the used path ID is consumed either way, the endpoint MUST explicitly close the path, as specified in Section 3.4.

検証に成功した場合、クライアントはそのパスの使用を継続できます。検証に失敗した場合、クライアントはそのパスを使用してはならず (MUST NOT)、パスの開始試行に関連付けられた状態を削除してもかまいません。使用されたパスIDはどちらの場合でも消費されるため、エンドポイントは、セクション3.4で規定されているとおり、そのパスを明示的に閉じなければなりません (MUST)。

3.1.2. Relation to Probing and Migration
3.1.2. プロービングおよびマイグレーションとの関係

Section 9.1 of [QUIC-TRANSPORT] introduces the concept of "probing" and "non-probing" frames. A packet that contains at least one "non-probing" frame is a "non-probing" packet. Migration, as specified in Section 9.2 of [QUIC-TRANSPORT], is initiated by sending packets containing non-probing frames on a new (validated) path; however, it uses the same path ID as on the old path. When the multipath extension is negotiated, the reception of any packet (no matter if "probing" or "non-probing") on a new path with a new, so far unused path ID does not impact the path status of any existing path. Therefore, any frame can be sent on a new path with a new path ID at any time as long as the anti-amplification limits (see Section 21.1.1.1 of [QUIC-TRANSPORT]) and the congestion control limits for this path are respected.

[QUIC-TRANSPORT] のセクション9.1では、「プロービング」フレームと「非プロービング」フレームの概念が導入されています。少なくとも1つの「非プロービング」フレームを含むパケットは、「非プロービング」パケットです。[QUIC-TRANSPORT] のセクション9.2で規定されているマイグレーションは、非プロービングフレームを含むパケットを新しい (検証済みの) パス上で送信することで開始されますが、その際には古いパスと同じパスIDを使用します。マルチパス拡張がネゴシエートされている場合、これまで未使用だった新しいパスIDを持つ新しいパス上でのパケット (「プロービング」か「非プロービング」かを問わない) の受信は、既存のどのパスのパス状態にも影響しません。したがって、このパスに対する増幅防止制限 ([QUIC-TRANSPORT] のセクション21.1.1.1を参照) と輻輳制御の制限が守られている限り、新しいパスIDを持つ新しいパス上では、いつでも任意のフレームを送信できます。

An endpoint could receive a packet with a connection ID associated to an active path ID where the packet's 4-tuple does not match the 4-tuple currently used with that path ID. This MUST be treated as path migration, as specified in Section 9.3 of [QUIC-TRANSPORT], with the constraint that all connection IDs used during path migration MUST be associated with the current path ID of the path being migrated.

エンドポイントは、アクティブなパスIDに関連付けられたコネクションIDを持つパケットを受信したものの、そのパケットの4タプルが当該パスIDで現在使用されている4タプルと一致しない場合があります。この場合は、[QUIC-TRANSPORT] のセクション9.3で規定されているとおりパスマイグレーションとして扱わなければなりません (MUST)。ただし、パスマイグレーション中に使用されるすべてのコネクションIDは、マイグレーションされるパスの現在のパスIDに関連付けられていなければならない (MUST) という制約が付きます。

3.1.3. Address Validation Token
3.1.3. アドレス検証トークン

As specified in Section 9.3 of [QUIC-TRANSPORT], the server is expected to send a new address validation token to a client following the successful validation of a new client address. The client will receive several tokens. When considering using a token for subsequent connections, it might be difficult for the client to pick the "right" token among multiple tokens obtained in a previous connection. The client is likely to fall back to the strategy specified in Section 8.1.3 of [QUIC-TRANSPORT], i.e., picking the last received token. To avoid issues when clients make the "wrong" choice, a server SHOULD issue tokens that are capable of validating any of the previously validated addresses. Including more addresses increases the probability that the token will be useful in the future but at the cost of a larger token. Further guidance on token usage can be found in Section 8.1.3 of [QUIC-TRANSPORT].

[QUIC-TRANSPORT] のセクション9.3で規定されているとおり、サーバは、新しいクライアントアドレスの検証に成功した後、新しいアドレス検証トークンをクライアントに送信することが期待されます。クライアントは複数のトークンを受け取ることになります。後続のコネクションでトークンの使用を検討する際、クライアントにとって、以前のコネクションで取得した複数のトークンの中から「正しい」トークンを選ぶことは難しい場合があります。クライアントは、[QUIC-TRANSPORT] のセクション8.1.3で規定されている戦略、すなわち最後に受信したトークンを選ぶ方法にフォールバックする可能性が高いです。クライアントが「誤った」選択をした場合の問題を避けるため、サーバは、以前に検証されたいずれのアドレスも検証できるトークンを発行すべきです (SHOULD)。より多くのアドレスを含めると、そのトークンが将来役立つ確率は高まりますが、トークンのサイズが大きくなるという代償を伴います。トークンの使用に関するさらなる指針は、[QUIC-TRANSPORT] のセクション8.1.3にあります。

3.2. Handling Connection IDs
3.2. コネクションIDの扱い

When the multipath extension is used, endpoints have to use the PATH_NEW_CONNECTION_ID and PATH_RETIRE_CONNECTION_ID frames to indicate the respective path ID together with the associated sequence number (see Section 5.1.1 of [QUIC-TRANSPORT]), at least for all paths with a path ID other than 0. Each path ID has its own connection ID sequence number space whose initial value is 0.

マルチパス拡張が使用される場合、エンドポイントは、少なくともパスIDが0以外のすべてのパスについて、PATH_NEW_CONNECTION_ID フレームと PATH_RETIRE_CONNECTION_ID フレームを使用して、対応するパスIDを関連するシーケンス番号 ([QUIC-TRANSPORT] のセクション5.1.1を参照) とともに示す必要があります。各パスIDは、初期値が0である独自のコネクションIDシーケンス番号空間を持ちます。

Endpoints SHOULD also use PATH_NEW_CONNECTION_ID and PATH_RETIRE_CONNECTION_ID for the initial path with path ID 0. However, the use of NEW_CONNECTION_ID and RETIRE_CONNECTION_ID is still valid and endpoints need to process these frames as corresponding to path ID 0.

エンドポイントは、パスID 0の初期パスについても PATH_NEW_CONNECTION_ID と PATH_RETIRE_CONNECTION_ID を使用すべきです (SHOULD)。ただし、NEW_CONNECTION_ID と RETIRE_CONNECTION_ID の使用も引き続き有効であり、エンドポイントはこれらのフレームをパスID 0に対応するものとして処理する必要があります。

3.2.1. Issuing New Connection IDs
3.2.1. 新しいコネクションIDの発行

In order to let the peer open new paths, it is RECOMMENDED to proactively issue at least one Connection ID for each unused path ID up to the minimum of the peer's and the local maximum path ID limits.

ピアが新しいパスを開けるようにするため、ピアとローカルの最大パスID制限のうち小さいほうの値までの未使用のパスIDそれぞれについて、少なくとも1つのコネクションIDを事前に発行することが推奨されます (RECOMMENDED)。

If an endpoint does not want to issue connection IDs for all unused path IDs for any reason, it SHOULD NOT introduce discontinuity in the issuing of path IDs, as path initiation requires available connection IDs for the same path ID on both sides. For instance, if the maximum path ID limit is 2 and the endpoint wants to provide connection IDs for only one path ID inside range [1, 2], it should select path ID 1 (and not path ID 2).

エンドポイントが何らかの理由で、未使用のすべてのパスIDに対してコネクションIDを発行したくない場合、パスの開始には双方で同じパスIDに対する利用可能なコネクションIDが必要であるため、パスIDの発行に不連続性を持ち込むべきではありません (SHOULD NOT)。たとえば、最大パスID制限が2で、エンドポイントが範囲 [1, 2] の中の1つのパスIDに対してのみコネクションIDを提供したい場合、パスID 2ではなくパスID 1を選択すべきです。

Similarly, endpoints SHOULD consume path IDs in a continuous way, i.e., when creating paths. However, endpoints cannot expect to receive new connection IDs or path initiation attempts with in-order use of path IDs due to out-of-order delivery or path validation failure.

同様に、エンドポイントは、すなわちパスを作成する際に、パスIDを連続的に消費すべきです (SHOULD)。ただし、順序の入れ替わった配信やパス検証の失敗のため、エンドポイントは、パスIDが順番どおりに使用された新しいコネクションIDやパス開始試行を受け取ることを期待できません。

Each endpoint maintains the set of connection IDs received from its peer for each path, any of which it can use when sending packets on that path; see also Section 5.1 of [QUIC-TRANSPORT]. Usually, it is desired to provide at least one additional connection ID for all used paths to allow for (unintentional) migration events (Section 9.5 of [QUIC-TRANSPORT]).

各エンドポイントは、パスごとにピアから受信したコネクションIDの集合を保持しており、そのパス上でパケットを送信するときには、そのいずれも使用できます。[QUIC-TRANSPORT] のセクション5.1も参照してください。通常は、(意図しない) マイグレーションイベント ([QUIC-TRANSPORT] のセクション9.5) に備えて、使用中のすべてのパスに対して少なくとも1つの追加のコネクションIDを提供することが望まれます。

As further specified in Section 5.1 of [QUIC-TRANSPORT], connection IDs cannot be issued more than once on the same connection and therefore are unique for the scope of the connection, regardless of the associated path ID.

[QUIC-TRANSPORT] のセクション5.1でさらに規定されているとおり、コネクションIDは同じコネクション上で複数回発行できないため、関連付けられたパスIDにかかわらず、コネクションの範囲で一意です。

Endpoints MUST NOT issue new connection IDs with path IDs greater than the Maximum Path Identifier field in MAX_PATH_ID frames (see Section 4.6) or the value of initial_max_path_id transport parameter if no MAX_PATH_ID frame was received yet. Receipt of a frame with a greater path ID is a connection error as specified in Section 4.

エンドポイントは、MAX_PATH_ID フレームの Maximum Path Identifier フィールド (セクション4.6を参照)、またはまだ MAX_PATH_ID フレームを受信していない場合は initial_max_path_id トランスポートパラメータの値より大きいパスIDを持つ新しいコネクションIDを発行してはなりません (MUST NOT)。より大きいパスIDを持つフレームの受信は、セクション4で規定されているとおりコネクションエラーです。

When an endpoint cannot open a path because there are no unused path IDs, it SHOULD either send a MAX_PATH_ID frame to increase the maximum path ID limit (when limited by the sender) or a PATHS_BLOCKED frame (see Section 4.7) to inform the peer that its current limit prevented the creation of the new path.

未使用のパスIDがないためにエンドポイントがパスを開けない場合、エンドポイントは、(送信側によって制限されているときは) 最大パスID制限を引き上げるために MAX_PATH_ID フレームを送信するか、現在の制限が新しいパスの作成を妨げたことをピアに知らせるために PATHS_BLOCKED フレーム (セクション4.7を参照) を送信するかの、いずれかを行うべきです (SHOULD)。

3.2.2. Rotating and Retiring Connection IDs
3.2.2. コネクションIDのローテーションと廃棄

Section 5.1.2 of [QUIC-TRANSPORT] indicates that an endpoint can change the connection ID it uses to another available one at any time during the connection. For the extension specified in this document, endpoints MUST only rotate to another connection ID associated with the same path ID. Use of a connection ID associated with another path ID will be considered as an attempt to open a new path instead.

[QUIC-TRANSPORT] のセクション5.1.2は、エンドポイントがコネクションの間いつでも、使用しているコネクションIDを利用可能な別のものに変更できると示しています。本ドキュメントで規定する拡張では、エンドポイントは、同じパスIDに関連付けられた別のコネクションIDにのみローテーションしなければなりません (MUST)。別のパスIDに関連付けられたコネクションIDの使用は、代わりに新しいパスを開く試みとみなされます。

An endpoint is supposed to retire any connection ID that is not being used, and the server is expected to provide replacements, as specified in Section 5.1.2 of [QUIC-TRANSPORT]. As such, when receiving a PATH_RETIRE_CONNECTION_ID frame, an endpoint SHOULD provide new connection IDs for that path, if still open, using PATH_NEW_CONNECTION_ID frames.

エンドポイントは、使用されていないコネクションIDを廃棄することになっており、サーバは、[QUIC-TRANSPORT] のセクション5.1.2で規定されているとおり、その代替を提供することが期待されます。したがって、PATH_RETIRE_CONNECTION_ID フレームを受信した場合、エンドポイントは、そのパスがまだ開いていれば、PATH_NEW_CONNECTION_ID フレームを使用して、そのパスに対する新しいコネクションIDを提供すべきです (SHOULD)。

While it is expected that the peer provides at least one unused connection ID for all active paths using the PATH_NEW_CONNECTION_ID after retirement of an old connection ID, an endpoint MAY send a PATH_CIDS_BLOCKED (see Section 4.7) if it wants to change the connection ID but no unused connection ID for a that path is available. Further, an endpoint MAY also send a PATH_CIDS_BLOCKED frame if it wants to open a new path and has no connection IDs available for an unused path ID, even though the Maximum Path Identifier value would allow for more paths.

古いコネクションIDの廃棄後に、ピアが PATH_NEW_CONNECTION_ID を使用して、すべてのアクティブなパスに対して少なくとも1つの未使用のコネクションIDを提供することが期待されますが、エンドポイントは、コネクションIDを変更したいのに、そのパスに対して未使用のコネクションIDが利用可能でない場合、PATH_CIDS_BLOCKED (セクション4.7を参照) を送信してもよい (MAY)。さらに、エンドポイントは、新しいパスを開きたいのに、未使用のパスIDに対して利用可能なコネクションIDがない場合にも、Maximum Path Identifier の値がより多くのパスを許容しているにもかかわらず、PATH_CIDS_BLOCKED フレームを送信してもよい (MAY)。

Retirement of connection IDs will not retire the path ID that corresponds to the connection ID or any other path resources as the packet number space is associated to the path ID.

パケット番号空間はパスIDに関連付けられているため、コネクションIDの廃棄によって、そのコネクションIDに対応するパスIDやその他のパスリソースが廃棄されることはありません。

The peer that sends the PATH_RETIRE_CONNECTION_ID frame can keep sending data on the path that the retired connection ID was used on but has to use a different connection ID for the same path ID when doing so.

PATH_RETIRE_CONNECTION_ID フレームを送信するピアは、廃棄されたコネクションIDが使用されていたパス上でデータの送信を続けることができますが、その際には同じパスIDに対して別のコネクションIDを使用する必要があります。

3.3. Path Status Management
3.3. パス状態の管理

An endpoint can send PATH_STATUS_BACKUP and PATH_STATUS_AVAILABLE frames (see Section 4.3) to inform the peer that it should send packets on the paths with the preference expressed by these frames. Note that an endpoint might not follow the peer's advertisements, but these frames are still a clear signal of the peer's preference of path usage.

エンドポイントは、PATH_STATUS_BACKUP フレームと PATH_STATUS_AVAILABLE フレーム (セクション4.3を参照) を送信して、これらのフレームで表明された優先度に従ってパス上でパケットを送信すべきであることをピアに知らせることができます。なお、エンドポイントがピアの通知に従わない場合もありますが、これらのフレームは依然として、ピアのパス使用に関する優先度を示す明確なシグナルです。

Each peer indicates its preference of path usage independently of the other peer. That means that peers could have different usage preferences for the same path. Depending on the data sender's decisions, this might lead to usage of paths that have been indicated as "backup" by the peer or non-usage of some locally available paths.

各ピアは、もう一方のピアとは独立して、パス使用に関する優先度を示します。つまり、ピア同士が同じパスに対して異なる使用優先度を持つ可能性があります。データ送信側の判断によっては、これにより、ピアから「バックアップ」として示されたパスが使用されたり、ローカルで利用可能な一部のパスが使用されなかったりすることがあります。

PATH_STATUS_AVAILABLE indicates that a path is "available", i.e., it suggests to the peer to use its own logic to split traffic among available paths.

PATH_STATUS_AVAILABLE は、パスが「利用可能」であること、すなわち、利用可能なパス間でトラフィックを分割する際にピア自身のロジックを使用するよう提案していることを示します。

PATH_STATUS_BACKUP suggests that a path should only be used as backup, i.e., that no traffic should be sent on that path if another path is available and usable. If all established paths are indicated as backup paths, no guidance is provided about which path should be used.

PATH_STATUS_BACKUP は、パスをバックアップとしてのみ使用すべきであること、すなわち、別のパスが利用可能で使用可能な場合には、そのパス上でトラフィックを送信すべきでないことを示唆します。確立されているすべてのパスがバックアップパスとして示されている場合、どのパスを使用すべきかについての指針は提供されません。

Similarly, if no frame indicating a path usage preference was received for a certain path, the preference of the peer is unknown and the sender needs to decide based on its own local logic if the path should be used.

同様に、あるパスについてパス使用の優先度を示すフレームが受信されていない場合、ピアの優先度は不明であり、送信側は、そのパスを使用すべきかどうかを自身のローカルなロジックに基づいて決定する必要があります。

If an endpoint starts using a backup path because it has detected issues on the paths marked as "available", it is RECOMMENDED to update its own path state signaling such that the peer avoids using the broken path. An endpoint that detects a path breakage can also explicitly close the path by sending a PATH_ABANDON frame (see Section 3.4) in order to avoid that its peer keeps using it and enable faster switchover to a backup path. If the endpoints do not want to close the path immediately, as connectivity could be re-established, PING frames can potentially be used to quickly detect connectivity changes and switch back in a timely way.

エンドポイントが、「利用可能」とマークされたパスで問題を検出したためにバックアップパスの使用を開始した場合、ピアが壊れたパスの使用を避けるように、自身のパス状態のシグナリングを更新することが推奨されます (RECOMMENDED)。パスの断絶を検出したエンドポイントは、ピアがそのパスを使い続けることを避け、バックアップパスへのより高速な切り替えを可能にするために、PATH_ABANDON フレーム (セクション3.4を参照) を送信してそのパスを明示的に閉じることもできます。接続性が再確立される可能性があるためにエンドポイントがそのパスをすぐには閉じたくない場合、PING フレームを使用して接続性の変化を素早く検出し、適時に元のパスに切り戻すことが可能です。

The PATH_STATUS_AVAILABLE and PATH_STATUS_BACKUP frames share a common, per-path sequence number space to detect and ignore outdated information, as further described in Section 4.3. This is needed as they might arrive out of order, e.g., if sent using different paths.

PATH_STATUS_AVAILABLE フレームと PATH_STATUS_BACKUP フレームは、古くなった情報を検出して無視するために、パスごとの共通のシーケンス番号空間を共有します。これについては、セクション4.3でさらに説明されています。これらのフレームは、たとえば異なるパスを使って送信された場合などに、順序が入れ替わって到着する可能性があるため、この仕組みが必要です。

3.4. Path Close
3.4. パスのクローズ

At any time in the connection, each endpoint can decide to abandon a path, for example, following changes in local connectivity or local preferences. An endpoint that wants to abandon a path MUST explicitly close the path by sending a PATH_ABANDON frame (see Section 4.2). This is true whether the decision to close the path results from implicit signals such as an idle timeout (see Section 5.9) or packet losses, as well as for any other reason such as management of local resources.

コネクションの任意の時点で、各エンドポイントは、たとえばローカルの接続性の変化やローカルの優先設定に応じて、パスを放棄することを決定できます。パスを放棄しようとするエンドポイントは、PATH_ABANDON フレームを送信して、そのパスを明示的にクローズしなければなりません (MUST)（セクション 4.2 を参照）。これは、パスをクローズするという決定が、アイドルタイムアウト（セクション 5.9 を参照）やパケット損失といった暗黙的なシグナルに起因する場合にも、ローカルリソースの管理など他の理由による場合にも当てはまります。

Endpoints that send a PATH_ABANDON frame MUST treat all connection IDs received from the peer for the path ID indicated in the PATH_ABANDON as immediately retired and subsequently cannot send any packet on that path anymore. Note that while abandoning a path will cause connection ID retirement, the inverse is not true: Retiring the associated connection IDs does not indicate path abandonment (see further Section 3.2).

PATH_ABANDON フレームを送信するエンドポイントは、PATH_ABANDON で示されたパスIDについてピアから受信したすべてのコネクションIDを、直ちに廃棄されたものとして扱わなければならず (MUST)、以降そのパス上でパケットを送信することはできません。パスの放棄はコネクションIDの廃棄を引き起こしますが、その逆は成り立たないことに注意してください。関連するコネクションIDを廃棄しても、パスの放棄を示すことにはなりません（さらにセクション 3.2 を参照）。

PATH_ABANDON frames can be sent on any open path, not only on the path that is intended to be closed. It is RECOMMENDED to send the PATH_ABANDON frames on another open path, especially if connectivity on the to-be-abandoned path is expected to be broken.

PATH_ABANDON フレームは、クローズしようとするパスだけでなく、開いている任意のパス上で送信できます。特に、放棄対象のパスの接続性が失われると予想される場合は、PATH_ABANDON フレームを別の開いているパス上で送信することが推奨されます (RECOMMENDED)。

When an endpoint receives a PATH_ABANDON frame, it MUST send a corresponding PATH_ABANDON frame if it has not already done so and respectively treat all connection IDs received from the peer for that path as immediately retired. While that means retired connection IDs received from the peer cannot be used for sending anymore, packets from the peer might still be in transit. Therefore, knowledge of the connection IDs issued to the peer and of the state of the number space associated to the path SHOULD be retained for 3 PTOs after the PATH_ABANDON frame has been received. This avoids generating spurious Stateless Reset packets, as discussed in Section 3.4.2, and helps acknowledge any potentially reordered, outstanding packets from the peer (see Section 3.4.3).

エンドポイントは PATH_ABANDON フレームを受信したとき、まだ送信していなければ対応する PATH_ABANDON フレームを送信し、同様に、そのパスについてピアから受信したすべてのコネクションIDを直ちに廃棄されたものとして扱わなければなりません (MUST)。これは、ピアから受信した廃棄済みコネクションIDを送信にはもう使用できないことを意味しますが、ピアからのパケットはまだ転送中である可能性があります。そのため、ピアに対して発行したコネクションIDに関する情報と、パスに関連付けられた番号空間の状態は、PATH_ABANDON フレームの受信後 3 PTO の間保持されるべきです (SHOULD)。これにより、セクション 3.4.2 で述べるように、不要な Stateless Reset パケットの生成を避けられ、ピアから届く、順序が入れ替わった可能性のある未処理のパケットに対する確認応答にも役立ちます（セクション 3.4.3 を参照）。

It is also possible that an endpoint will receive a PATH_ABANDON frame before receiving or sending any traffic on a path. For example, if the client tries to initiate a path and the path cannot be established, it will send a PATH_ABANDON frame (see Section 3.1). An endpoint could also decide to abandon an unused path for any other reason, for example, removing a hole from the sequence of path IDs in use. This is not an error.

エンドポイントが、パス上でトラフィックを受信または送信する前に PATH_ABANDON フレームを受信することもあり得ます。たとえば、クライアントがパスの開始を試みてもそのパスを確立できない場合、クライアントは PATH_ABANDON フレームを送信します（セクション 3.1 を参照）。また、エンドポイントは、使用中のパスIDの並びから欠番を取り除くためなど、その他の理由で未使用のパスを放棄すると決定することもあります。これはエラーではありません。

If a peer sends a PATH_ABANDON frame but never receives a corresponding PATH_ABANDON frame, it might not be able to remove path state. It is left to the implementation to handle this unexpected behavior, as it does not impact interoperability. If the endpoint is no longer willing to process the issued connection IDs for the abandoned path, it MAY close the connection but SHOULD wait at least 3 PTOs after sending the PATH_ABANDON frame.

ピアが PATH_ABANDON フレームを送信したにもかかわらず、対応する PATH_ABANDON フレームを受信しない場合、そのピアはパスの状態を削除できないことがあります。この予期しない動作は相互運用性に影響しないため、その扱いは実装に委ねられます。エンドポイントが、放棄されたパスについて発行済みのコネクションIDをもはや処理する意思がない場合は、コネクションをクローズしてもよい (MAY) ですが、PATH_ABANDON フレームの送信後少なくとも 3 PTO は待つべきです (SHOULD)。

After a path is abandoned, the path ID MUST NOT be reused for new paths, as the path ID is part of the nonce calculation (see Section 2.4).

パスが放棄された後は、パスIDがノンス計算の一部であるため、そのパスIDを新しいパスに再利用してはなりません (MUST NOT)（セクション 2.4 を参照）。

If a PATH_ABANDON frame is received for the only open path of a QUIC connection, the receiving peer SHOULD send a CONNECTION_CLOSE frame and enter the closing state. Alternatively, a client MAY instead try to open a new path, if available, and only initiate connection closure if path validation fails or a CONNECTION_CLOSE frame is received from the server. Similarly, the server MAY wait for a short, limited time, such as one PTO, to see if a packet is received on a new path before sending the CONNECTION_CLOSE frame.

QUIC コネクションの唯一の開いているパスに対して PATH_ABANDON フレームを受信した場合、受信側のピアは CONNECTION_CLOSE フレームを送信し、クローズ状態に入るべきです (SHOULD)。あるいは、クライアントは代わりに、利用可能であれば新しいパスの開通を試み、パス検証が失敗した場合、またはサーバから CONNECTION_CLOSE フレームを受信した場合にのみ、コネクションのクローズを開始してもよい (MAY)。同様に、サーバも、CONNECTION_CLOSE フレームを送信する前に、1 PTO など短い限られた時間だけ待って、新しいパス上でパケットが受信されるかどうかを確認してもよい (MAY)。

Note that other explicit closing mechanisms of [QUIC-TRANSPORT] still apply on the whole connection. In particular, the reception of either a CONNECTION_CLOSE (Section 10.2 of [QUIC-TRANSPORT]) or a Stateless Reset (Section 10.3 of [QUIC-TRANSPORT]) closes the connection.

[QUIC-TRANSPORT] の他の明示的なクローズ機構は、コネクション全体に対して引き続き適用されることに注意してください。特に、CONNECTION_CLOSE（[QUIC-TRANSPORT] のセクション 10.2）または Stateless Reset（[QUIC-TRANSPORT] のセクション 10.3）のいずれかを受信すると、コネクションはクローズされます。

3.4.1. Path Closure Example
3.4.1. パスクローズの例

In the example below, the client wants to close the path with path ID 0. It sends the PATH_ABANDON frame to terminate the path with path ID 0 on the path with path ID 1 using the connection ID S1. After receiving the PATH_ABANDON frame for path ID 0, the server also sends a PATH_ABANDON frame with path ID 0 together with a PATH_ACK frame on the same path using connection ID C1.

以下の例では、クライアントはパスID 0 のパスをクローズしようとしています。クライアントは、パスID 0 のパスを終了させるための PATH_ABANDON フレームを、コネクションID S1 を使用してパスID 1 のパス上で送信します。サーバは、パスID 0 の PATH_ABANDON フレームを受信した後、同じパス上でコネクションID C1 を使用して、パスID 0 の PATH_ABANDON フレームを PATH_ACK フレームとともに送信します。 

   Client                                                      Server

   (client tells server to abandon a path with path ID 0)
   1-RTT[X]: DCID=S1 PATH_ABANDON[path ID=0]->
                              (server tells client to abandon a path)
                       <-1-RTT[Y]: DCID=C1 PATH_ABANDON[path ID=0],
                                              PATH_ACK[PATH ID=1, PN=X]
   1-RTT[U]: DCID=S1 PATH_ACK[path ID=1, PN=Y] ->

Figure 5: Example of Closing a Path

図 5: パスをクローズする例

Note that if the PATH_ABANDON frame is instead sent on the to-be-abandoned path, the last acknowledgment still needs to be sent on a different path as no further packets can be sent on the abandoned path after the PATH_ABANDON frame.

PATH_ABANDON フレームを代わりに放棄対象のパス上で送信した場合でも、PATH_ABANDON フレームの後は放棄されたパス上でそれ以上パケットを送信できないため、最後の確認応答は別のパス上で送信する必要があることに注意してください。

3.4.2. Avoiding Spurious Stateless Resets
3.4.2. 不要な Stateless Reset の回避

Due to network delays, packets sent on an abandoned path can arrive well after the connection IDs have been retired. If not recognized as bound to the local connection, such a packet triggers the peer to send a Stateless Reset packet. The requirement to retain knowledge of connection ID and about the packet number space for 3 PTOs after receiving a PATH_ABANDON frame, as specified in Section 3.4 above, is intended to reduce the risk of sending such spurious stateless packets, but it cannot completely avoid that risk.

ネットワーク遅延のため、放棄されたパス上で送信されたパケットが、コネクションIDが廃棄されてからかなり後に到着することがあります。そのようなパケットがローカルのコネクションに対応するものと認識されない場合、ピアが Stateless Reset パケットを送信する契機となります。上記のセクション 3.4 で規定したように、PATH_ABANDON フレームの受信後 3 PTO の間、コネクションIDおよびパケット番号空間に関する情報を保持するという要件は、このような不要な stateless パケットを送信するリスクを減らすことを意図したものですが、そのリスクを完全に避けることはできません。

Section 10.3 of [QUIC-TRANSPORT] specified that the Stateless Reset Tokens associated with retired connection IDs cannot be used to identify Stateless Reset packets. The immediate retirement of connection IDs received from the peer for an abandoned path guarantees that spurious Stateless Reset packets sent by the peer will not cause the closure of the QUIC connection.

[QUIC-TRANSPORT] のセクション 10.3 では、廃棄されたコネクションIDに関連付けられた Stateless Reset Token を、Stateless Reset パケットの識別に使用できないと規定されていました。放棄されたパスについてピアから受信したコネクションIDを直ちに廃棄することで、ピアが送信する不要な Stateless Reset パケットによって QUIC コネクションがクローズされることはなくなります。

3.4.3. Handling PATH_ACK for Abandoned Paths
3.4.3. 放棄されたパスに対する PATH_ACK の処理

When an endpoint sends a PATH_ABANDON frame, there might still be some packets in transit from the peer. Further, if an endpoint receives a PATH_ABANDON frame, it might still receive reordered packets on the abandoned path. Endpoints SHOULD promptly send PATH_ACK frames for all unacknowledged packets received on an abandoned path if path state is still retained to do so.

エンドポイントが PATH_ABANDON フレームを送信したとき、ピアからのパケットがまだ転送中である可能性があります。さらに、エンドポイントが PATH_ABANDON フレームを受信した場合でも、放棄されたパス上で順序が入れ替わったパケットをまだ受信する可能性があります。エンドポイントは、パスの状態がまだ保持されている場合、放棄されたパス上で受信した確認応答未送信のすべてのパケットに対して、速やかに PATH_ACK フレームを送信すべきです (SHOULD)。

PATH_ACK frames have to be sent on a different path than the path being abandoned after sending the PATH_ABANDON frame as connection IDs are immediately retired.

コネクションIDは直ちに廃棄されるため、PATH_ACK フレームは、PATH_ABANDON フレームの送信後、放棄されるパスとは別のパス上で送信しなければなりません。

When an endpoint finally deletes all state associated with the path, the packets sent over the path and not yet acknowledged MUST be considered lost. PATH_ACK frames received with an abandoned path ID are silently ignored, as specified in Section 4.

エンドポイントがそのパスに関連付けられたすべての状態を最終的に削除するとき、そのパス上で送信されたまだ確認応答されていないパケットは、損失したものとみなさなければなりません (MUST)。放棄されたパスIDを持つ PATH_ACK フレームは、セクション 4 で規定されているとおり、黙って無視されます。

4. New Frames
4. 新しいフレーム

All frames defined in this document MUST only be sent in 1-RTT packets. If an endpoint receives a multipath-specific frame in a different packet type, it MUST close the connection with an error of type PROTOCOL_VIOLATION.

本文書で定義されるすべてのフレームは、1-RTTパケットでのみ送信しなければなりません (MUST)。エンドポイントがマルチパス固有のフレームを別のパケットタイプで受信した場合、タイプ PROTOCOL_VIOLATION のエラーでコネクションをクローズしなければなりません (MUST)。

Receipt of multipath-specific frames that use a path ID that is greater than the announced Maximum Paths value in the MAX_PATH_ID frame or in the initial_max_path_id transport parameter, if no MAX_PATH_ID frame was received yet, MUST be treated as a connection error of type PROTOCOL_VIOLATION.

MAX_PATH_ID フレームで通知された Maximum Paths の値、または、まだ MAX_PATH_ID フレームを受信していない場合は initial_max_path_id トランスポートパラメータで通知された値より大きいパスIDを使用するマルチパス固有のフレームを受信した場合は、タイプ PROTOCOL_VIOLATION のコネクションエラーとして扱わなければなりません (MUST)。

If an endpoint receives a multipath-specific frame with a path ID that it cannot process anymore (e.g., because the path might have been abandoned), it MUST silently ignore the frame.

エンドポイントが、もはや処理できないパスID（たとえば、そのパスが放棄された可能性があるため）を持つマルチパス固有のフレームを受信した場合、そのフレームを黙って無視しなければなりません (MUST)。

4.1. PATH_ACK Frame
4.1. PATH_ACK フレーム

The PATH_ACK frame (types 0x3e and 0x3f) is an extension of the ACK frame specified in Section 19.3 of [QUIC-TRANSPORT]. It is used to acknowledge packets that were sent on different paths, as each path has its own packet number space. If the frame type is 0x3f, PATH_ACK frames also contain the sum of QUIC packets with associated Explicit Congestion Notification (ECN) marks received on the acknowledged packet number space up to this point.

PATH_ACK フレーム（タイプ 0x3e および 0x3f）は、[QUIC-TRANSPORT] のセクション 19.3 で規定されている ACK フレームの拡張です。各パスが独自のパケット番号空間を持つため、異なるパス上で送信されたパケットを確認応答するために使用されます。フレームタイプが 0x3f の場合、PATH_ACK フレームには、確認応答対象のパケット番号空間でこの時点までに受信した、Explicit Congestion Notification (ECN) マークが付いた QUIC パケットの合計数も含まれます。

PATH_ACK frames are formatted as shown in Figure 6.

PATH_ACK フレームは、図 6 に示す形式です。 

     PATH_ACK Frame {
       Type (i) = 0x3e..0x3f,
       Path Identifier (i),
       Largest Acknowledged (i),
       ACK Delay (i),
       ACK Range Count (i),
       First ACK Range (i),
       ACK Range (..) ...,
       [ECN Counts (..)],
     }

Figure 6: PATH_ACK Frame Format

図 6: PATH_ACK フレームの形式

Compared to the ACK frame specified in [QUIC-TRANSPORT], the following field is added:

[QUIC-TRANSPORT] で規定されている ACK フレームと比べて、次のフィールドが追加されています。

Path Identifier:

Path Identifier:

The path ID associated with the packet number space of the 0-RTT and 1-RTT packets that are acknowledged by the PATH_ACK frame.

PATH_ACK フレームによって確認応答される 0-RTT パケットおよび 1-RTTパケットのパケット番号空間に関連付けられたパスID。

4.2. PATH_ABANDON フレーム

The PATH_ABANDON frame informs the peer to abandon a path. After the PATH_ABANDON frame is sent on a path, the path can no longer be used for sending.

PATH_ABANDON フレームは、パスを放棄するようピアに通知します。PATH_ABANDON フレームがパス上で送信された後、そのパスは送信にはもう使用できません。

     }

図 7: PATH_ABANDON フレームの形式

PATH_ABANDON frames contain the following fields:

PATH_ABANDON フレームには次のフィールドが含まれます。

Path Identifier:

The path ID associated to the to-be-abandoned path.

放棄対象のパスに関連付けられたパスID。

Error Code:

Error Code:

A variable-length integer that indicates the reason for abandoning this path. NO_ERROR(0x0) indicates that the path is being abandoned without any error being encountered. Other error codes can be found in Section 4.2.1.

このパスを放棄する理由を示す可変長整数です。NO_ERROR(0x0) は、エラーが発生することなくパスが放棄されることを示します。その他のエラーコードについては、セクション 4.2.1 を参照してください。

PATH_ABANDON frames are ack-eliciting. If a packet containing a PATH_ABANDON frame is considered lost, the peer SHOULD repeat it.

PATH_ABANDON フレームはACKを誘発します (ack-eliciting)。PATH_ABANDON フレームを含むパケットが損失したと見なされた場合、ピアはそれを再送すべきです (SHOULD)。

Use of the PATH_ABANDON frame is specified in Section 3.4.

PATH_ABANDON フレームの使用方法は、セクション 3.4 で規定されています。

Path Identifier:

The path ID that the status update corresponds to. All path IDs below the maximum path ID limit can be indicated, even if the path is not in active use yet.

ステータス更新が対応するパスID。パスがまだ実際に使用されていなくても、最大パスID上限未満のすべてのパスIDを指定できます。

Path Status Sequence Number:

A variable-length integer specifying the per-path sequence number assigned for this frame.

このフレームに割り当てられた、パスごとのシーケンス番号を指定する可変長整数です。

The sequence number space is common to the two frame types, and monotonically increasing values MUST be used when sending PATH_STATUS_AVAILABLE or PATH_STATUS_BACKUP frames for a given path ID.

シーケンス番号空間は2種類のフレームで共通であり、特定のパスIDに対して PATH_STATUS_AVAILABLE フレームまたは PATH_STATUS_BACKUP フレームを送信する際には、単調増加する値を使用しなければなりません (MUST)。

シーケンス番号が単調増加するという要件はパスごとのものです。受信側が、異なるパス上の PATH_STATUS_AVAILABLE フレームまたは PATH_STATUS_BACKUP フレームで同じシーケンス番号を受信することは十分にあり得ます。したがって、PATH_STATUS_AVAILABLE フレームまたは PATH_STATUS_BACKUP フレームの受信側は、パスIDごとに個別にシーケンス番号を使用して比較する必要があります。

PATH_STATUS_BACKUP and PATH_STATUS_AVAILABLE frames are ack-eliciting. If a packet containing a PATH_STATUS_BACKUP or PATH_STATUS_AVAILABLE frame is considered lost, the peer SHOULD resend the frame only if it contains the last status sent for that path -- as indicated by the sequence number.

5. Implementation Considerations
5. 実装上の考慮事項

This section provides informational guidance for implementors.

本節では、実装者向けの参考情報を示します。

5.1. Connection ID Changes, Migration, and NAT Rebindings
5.1. コネクションIDの変更、マイグレーション、およびNATリバインディング

With the multipath extension, each path uses a separate packet number space. This is a major difference from [QUIC-TRANSPORT], which only defines three number spaces (Initial, Handshake, and Application data packets).

マルチパス拡張では、各パスが個別のパケット番号空間を使用します。これは、3つの番号空間（Initial、Handshake、およびApplication dataパケット）のみを定義している [QUIC-TRANSPORT] との大きな違いです。

For any given path, connection ID rotation, NAT rebinding, or client-initiated migration as specified in [QUIC-TRANSPORT] might occur like on a single path. These events do not change the path ID and do not affect the packet number space associated with the path.

任意のパスについて、[QUIC-TRANSPORT] で規定されているコネクションIDのローテーション、NATリバインディング、またはクライアント起点のマイグレーションは、単一パスの場合と同様に発生することがあります。これらのイベントは、パスIDを変更せず、そのパスに関連付けられたパケット番号空間にも影響しません。

It is generally preferable to use multipath mechanisms, such as creating a new path and later abandoning the old path rather than doing migration of a single path as specified in [QUIC-TRANSPORT]. This enables a smoother handover and allows a more controlled migration handling at the server side. However, migration of a single path cannot be avoided in case of NAT rebinding or if the server requests migration to a "preferred address" during the handshake.

一般に、[QUIC-TRANSPORT] で規定されている単一パスのマイグレーションを行うよりも、新しいパスを作成して後で古いパスを放棄するといったマルチパスの仕組みを使用する方が望ましいです。これにより、よりスムーズなハンドオーバが可能になり、サーバ側でマイグレーションをより制御しやすく扱えるようになります。ただし、NATリバインディングが発生した場合や、サーバがハンドシェイク中に「preferred address」へのマイグレーションを要求した場合には、単一パスのマイグレーションを避けることはできません。

Section 9.3 of [QUIC-TRANSPORT] allows an endpoint to skip validation of a peer address if that address has been seen recently. However, when the multipath extension is used and an endpoint has multiple addresses that could lead to switching between different paths, it should rather maintain multiple open paths instead.

[QUIC-TRANSPORT] のセクション9.3は、最近確認されたアドレスであれば、エンドポイントがピアアドレスの検証を省略することを認めています。しかし、マルチパス拡張が使用されていて、異なるパス間の切り替えにつながりうる複数のアドレスをエンドポイントが持っている場合は、むしろ複数のオープンなパスを維持すべきです。

Servers observing a 4-tuple change will perform path validation (see Section 9 of [QUIC-TRANSPORT]). If path validation process succeeds, the endpoints reset the path's congestion controller and round-trip time estimator according to Section 9.4 of [QUIC-TRANSPORT].

4タプルの変更を観測したサーバは、パス検証を実行します（[QUIC-TRANSPORT] のセクション9を参照）。パス検証の処理が成功した場合、エンドポイントは [QUIC-TRANSPORT] のセクション9.4に従って、そのパスの輻輳制御器とラウンドトリップ時間推定器をリセットします。

5.2. Using Multiple Paths on the Same 4-tuple
5.2. 同一の4タプルでの複数パスの使用

It is possible to create paths that refer to the same 4-tuple. For example, endpoints might want to create paths that use different Differentiated Service [RFC2475] markings. This could be done in conjunction with scheduling algorithms that match streams to paths so that, for example, data frames for low priority streams are sent over low priority paths. Since these paths use different path IDs, they can be managed independently to suit the needs of the application. (The application would need to manage how client and server use differentiated services on a path. This is not specified in this document.)

同じ4タプルを参照するパスを作成することは可能です。たとえば、エンドポイントが、異なるDifferentiated Service [RFC2475] マーキングを使用するパスを作成したい場合があります。これは、たとえば低優先度ストリームのデータフレームを低優先度パスで送信するように、ストリームをパスに対応付けるスケジューリングアルゴリズムと組み合わせて行うことができます。これらのパスは異なるパスIDを使用するため、アプリケーションのニーズに合わせて独立に管理できます。（アプリケーションは、クライアントとサーバがパス上でどのようにdifferentiated servicesを使用するかを管理する必要があります。これは本文書では規定しません。）

There might be cases in which paths are created with different 4-tuples but end up using the same 4-tuples as a consequence of path migrations. Consider the following example where all paths use the same source and destination ports:

異なる4タプルでパスが作成されたものの、パスマイグレーションの結果として同じ4タプルを使用することになる場合があるかもしれません。すべてのパスが同じ送信元ポートと宛先ポートを使用する次の例を考えます。

* Client starts path 1 from address 192.0.2.1 to server address 198.51.100.1.

* クライアントが、アドレス192.0.2.1からサーバアドレス198.51.100.1へのパス1を開始します。

* Client starts path 2 from address 192.0.2.2 to server address 198.51.100.1.

* クライアントが、アドレス192.0.2.2からサーバアドレス198.51.100.1へのパス2を開始します。

* Both paths are used for a while.

* 両方のパスがしばらくの間使用されます。

* Server sends packet from address 198.51.100.1 to client address 192.0.2.1 with Connection ID indicating path ID 2.

* サーバが、パスID 2を示すコネクションIDを付けて、アドレス198.51.100.1からクライアントアドレス192.0.2.1へパケットを送信します。

* Client receives the packet, recognizes a path migration, and updates the source address of path 2 to 192.0.2.1.

* クライアントはそのパケットを受信し、パスマイグレーションと認識して、パス2の送信元アドレスを192.0.2.1に更新します。

(For simplicity, this example uses IPv4 addresses but would work similarly for IPv6 addresses.)

（簡単のため、この例ではIPv4アドレスを使用していますが、IPv6アドレスでも同様に動作します。）

Such unintentional use of the same 4-tuple on different paths ought to be rare. When they happen, the two paths would be redundant, and the endpoint could want to close one of them.

このような意図しない異なるパスでの同一4タプルの使用は、まれであるはずです。そのような事態が起きた場合、2つのパスは冗長になるため、エンドポイントはそのうちの1つを閉じたいと考えるかもしれません。

5.3. Congestion Control
5.3. 輻輳制御

When the QUIC multipath extension is used, senders manage per-path congestion status as required in Section 9.4 of [QUIC-TRANSPORT]. However, in [QUIC-TRANSPORT], only one active path is assumed and, as such, the requirement is to reset the congestion control status on path migration. With the multipath extension, multiple paths can be used simultaneously. Therefore, separate congestion control state is maintained for each path. This means a sender is not allowed to send more data on a given path than congestion control for that path indicates.

QUICマルチパス拡張を使用する場合、送信者は [QUIC-TRANSPORT] のセクション9.4で要求されているとおり、パスごとの輻輳状態を管理します。ただし、[QUIC-TRANSPORT] ではアクティブなパスが1つだけであると想定しているため、パスマイグレーション時に輻輳制御状態をリセットすることが要件となっています。マルチパス拡張では、複数のパスを同時に使用できます。したがって、パスごとに別々の輻輳制御状態が維持されます。これは、送信者が、あるパスで、そのパスの輻輳制御が示す量を超えるデータを送信することは認められないことを意味します。

When a Multipath QUIC connection uses two or more paths, there is no guarantee that these paths are fully disjoint. When two (or more paths) share the same bottleneck, using a standard congestion control scheme could result in an unfair distribution of the bandwidth with the multipath connection getting more bandwidth than competing single paths connections. Multipath TCP uses the Linked Increases Algorithm (LIA) congestion control scheme specified in [RFC6356] to solve this problem. This scheme can immediately be adapted to Multipath QUIC. Other coupled congestion control schemes have been proposed for Multipath TCP, such as [OLIA]. Designers of congestion control algorithms specialized for Multipath QUIC are advised to follow BCP 133; see Section 7.10 of [RFC9743].

マルチパスQUICコネクションが2つ以上のパスを使用する場合、それらのパスが完全に互いに素である保証はありません。2つ（またはそれ以上）のパスが同じボトルネックを共有しているとき、標準的な輻輳制御方式を使用すると、マルチパスコネクションが、競合する単一パスのコネクションよりも多くの帯域幅を得てしまい、帯域幅の配分が不公平になる可能性があります。Multipath TCPは、この問題を解決するために [RFC6356] で規定されているLinked Increases Algorithm (LIA) 輻輳制御方式を使用しています。この方式は、そのままマルチパスQUICに適用できます。Multipath TCP向けには、[OLIA] など、他の連携型輻輳制御方式も提案されています。マルチパスQUIC向けに特化した輻輳制御アルゴリズムの設計者は、BCP 133に従うことが推奨されます。[RFC9743] のセクション7.10を参照してください。

Section 5.1.2 of [QUIC-TRANSPORT] indicates that an endpoint can change the connection ID it uses to another available one at any time during the connection. As such, a change of the Connection ID without any change in the address does not indicate a path change and the endpoint can keep the same congestion control and RTT measurement state.

[QUIC-TRANSPORT] のセクション5.1.2は、エンドポイントがコネクション中のいつでも、使用するコネクションIDを利用可能な別のものに変更できることを示しています。したがって、アドレスの変更を伴わないコネクションIDの変更はパスの変更を意味せず、エンドポイントは同じ輻輳制御状態とRTT測定状態を維持できます。

5.4. Computing Path RTT
5.4. パスRTTの計算

PATH_ACK frames indicate which path the acknowledged packets were sent on, but they could be received through any open path. If successive acknowledgments are received on different paths, the measured RTT samples can fluctuate widely, which could result in poor performance depending on, for example, the congestion control algorithm.

PATH_ACKフレームは、確認応答されたパケットがどのパスで送信されたかを示しますが、PATH_ACKフレーム自体は任意のオープンなパスを通じて受信される可能性があります。連続する確認応答が異なるパスで受信されると、測定されるRTTサンプルが大きく変動することがあり、たとえば輻輳制御アルゴリズムによっては、性能の低下を招く可能性があります。

Congestion control state as defined in [QUIC-RECOVERY] is kept per path ID. However, depending on which path acknowledgments are sent, the actual RTT of a path cannot be calculated or might not be the right value to be used.

[QUIC-RECOVERY] で定義される輻輳制御状態は、パスIDごとに保持されます。しかし、確認応答がどのパスで送信されるかによっては、パスの実際のRTTを計算できない場合や、実際のRTTが使用すべき正しい値ではない場合があります。

Instead of using the real RTT of a path, it is recommended to consider the sum of two one-way delays: the delay on the packet sending path and the delay on the return path chosen for the acknowledgments. When different paths have different characteristics, the delays can vary widely. For example, consider a multipath transmission using both a terrestrial path with a latency of 50ms in each direction and a geostationary satellite path with a latency of 300ms in each direction. The sum of the two one-way delays will depend on the combination of paths used for the packet transmission and the acknowledgment transmission, as shown in Table 1.

パスの実際のRTTを使用する代わりに、2つの片道遅延、すなわちパケットを送信したパスでの遅延と、確認応答用に選ばれた戻りパスでの遅延の合計を考慮することが推奨されます。パスごとに特性が異なる場合、遅延は大きく変わりえます。たとえば、各方向のレイテンシが50msの地上パスと、各方向のレイテンシが300msの静止衛星パスの両方を使用するマルチパス伝送を考えます。2つの片道遅延の合計は、パケット送信に使用されるパスと確認応答の送信に使用されるパスの組み合わせによって決まります。これを表1に示します。 

            +======================+=============+===========+
            | ACK Path \ Data Path | Terrestrial | Satellite |
            +======================+=============+===========+
            | Terrestrial          | 100ms       | 350ms     |
            +----------------------+-------------+-----------+
            | Satellite            | 350ms       | 600ms     |
            +----------------------+-------------+-----------+

Table 1: Example of ACK Delays Using Multiple Paths

表1: 複数パスを使用した場合のACK遅延の例

The computed values reflect both the state of the network path and the scheduling decisions of the acknowledgment sender. If we assume that the PATH_ACK will be sent over the terrestrial link, because this decision provides the best response time, the computed RTT value for the satellite path will be about 350ms. This is lower than the 600ms that would be measured if the PATH_ACK came over the satellite channel, but it is still the right value for computing, for example, the PTO timeout: If a PATH_ACK is not received after more than 350ms, either the packet or its PATH_ACK were probably lost.

計算された値は、ネットワークパスの状態と、確認応答の送信側によるスケジューリングの判断の両方を反映します。最も応答時間が短くなるという理由でPATH_ACKが地上リンクで送信されると仮定すると、衛星パスについて計算されるRTT値はおよそ350msになります。これは、PATH_ACKが衛星チャネルで届いた場合に測定される600msよりも小さい値ですが、たとえばPTOタイムアウトを計算するためには、これでも正しい値です。350msを超えてもPATH_ACKが受信されない場合、パケットかそのPATH_ACKのいずれかが失われた可能性が高いということになります。

The simplest implementation is to use the delays measured when receiving new packet acknowledgments to compute smoothed_rtt and rttvar per Section 5.3 of [QUIC-RECOVERY] regardless of the path through which PATH_ACK frames are received. This approach will provide good results as long as acknowledgments are sent consistently over one path. If at any time the acknowledgment sender revisits its sending preferences, this can also change the paths that are used to send acknowledgments. However, this is not very different from route changes on a single path. The RTT, RTT variance, and PTO estimates will rapidly converge to reflect the new conditions. There is one exception: the minimum RTT, which is also a known challenge when route changes occurs on a single path. An acknowledgment receiver can, however, remember the path over which the PATH_ACK that produced the minimum RTT was received and restart the minimum RTT computation if that acknowledgment path changes or is abandoned. If acknowledgments are not sent consistently over one path, the acknowledgment receiver can monitor over which path acknowledgments are received and only use samples for acknowledgments received on the same path on which the data was sent, if any.

最も単純な実装は、PATH_ACKフレームがどのパスを通じて受信されたかにかかわらず、新しいパケットの確認応答を受信したときに測定された遅延を使用して、[QUIC-RECOVERY] のセクション5.3に従い smoothed_rtt と rttvar を計算することです。この方法は、確認応答が一貫して1つのパスで送信される限り、良好な結果をもたらします。確認応答の送信側が送信の優先設定を見直した場合、確認応答の送信に使用されるパスも変わる可能性があります。しかし、これは単一パスでの経路変更とそれほど変わりません。RTT、RTT分散、およびPTOの推定値は、新しい状況を反映するように速やかに収束します。例外が1つあり、それは最小RTTです。これは、単一パスで経路変更が起きた場合にも知られている課題です。ただし、確認応答の受信側は、最小RTTを生んだPATH_ACKが受信されたパスを記憶しておき、その確認応答のパスが変更されるか放棄された場合に、最小RTTの計算を再開することができます。確認応答が一貫して1つのパスで送信されない場合、確認応答の受信側は、どのパスで確認応答が受信されるかを監視し、データが送信されたパスと同じパスで受信された確認応答のサンプルだけを使用することができます（そのようなものがあれば）。

Further, congestion control functions that rely on delay estimates need to consider cases where acknowledgments are sent over multiple paths with different delays explicitly.

さらに、遅延推定に依存する輻輳制御機能は、遅延の異なる複数のパスで確認応答が送信されるケースを明示的に考慮する必要があります。

5.5. Packet Scheduling
5.5. パケットスケジューリング

The transmission of packets containing data is limited by the arrival of data from the application and by congestion control. Generally, QUIC packets that increase the number of bytes in flight can only be sent when the congestion window for the selected path allows it.

データを含むパケットの送信は、アプリケーションからのデータの到着と輻輳制御によって制限されます。一般に、実行中のバイト数を増加させるQUICパケットは、選択されたパスの輻輳ウィンドウが許す場合にのみ送信できます。

Most frames, including control frames (PATH_CHALLENGE and PATH_RESPONSE being the notable exceptions), can be sent and received on any open path. As such, a packet scheduler is needed to decide which path to use for sending the next packet, among those paths with an open congestion window. If multiple paths are used to send data frames belonging to the same stream, data delivery will experience the maximum delay of all used paths due to in-order delivery. The scheduling is a local decision based on the preferences of the application and the implementation.

制御フレームを含むほとんどのフレームは、任意のオープンなパスで送受信できます（PATH_CHALLENGEとPATH_RESPONSEは顕著な例外です）。そのため、輻輳ウィンドウに空きのあるパスの中から、次のパケットの送信にどのパスを使用するかを決定するためのパケットスケジューラが必要です。同じストリームに属するデータフレームを送信するために複数のパスが使用される場合、順序どおりの配送のため、データ配送には使用されたすべてのパスの中で最大の遅延が生じます。スケジューリングは、アプリケーションと実装の優先設定に基づくローカルな判断です。

This implies that an endpoint might send and receive PATH_ACK frames on a path different from the one that carried the acknowledged packets. As noted in Section 5.4, RTT estimates computed using the standard algorithm reflect both the characteristics of the path and the scheduling algorithm of PATH_ACK frames. The estimates will converge faster if the scheduling strategy of PATH_ACK frames is stable. Implementations can choose different strategies such as, for instance, sending PATH_ACK frames either simply on the path where the acknowledged packets were received or alternatively the shortest path, which results in shorter control loops and potentially better performance.

これは、エンドポイントが、確認応答されたパケットを運んだパスとは異なるパスでPATH_ACKフレームを送受信する可能性があることを意味します。5.4節で述べたとおり、標準アルゴリズムを使用して計算されたRTT推定値は、パスの特性とPATH_ACKフレームのスケジューリングアルゴリズムの両方を反映します。PATH_ACKフレームのスケジューリング戦略が安定していれば、推定値はより速く収束します。実装は、異なる戦略を選択できます。たとえば、PATH_ACKフレームを、確認応答されたパケットを受信したパスでそのまま送信する方法や、最短のパスで送信する方法があります。後者は制御ループが短くなり、性能が向上する可能性があります。

Since packets that only carry PATH_ACK frames are not congestion controlled (see Section 7 of [QUIC-RECOVERY]), senders should carefully consider the load induced by these packets, especially if the capacity is unknown on that path, e.g., when that path is not used for sending data frames.

PATH_ACKフレームのみを運ぶパケットは輻輳制御の対象ではないため（[QUIC-RECOVERY] のセクション7を参照）、送信者は、特にそのパスの容量が不明な場合（たとえば、そのパスがデータフレームの送信に使用されていない場合など）、これらのパケットによって生じる負荷を慎重に検討すべきです。

5.6. Retransmissions
5.6. 再送

Simultaneous use of multiple paths enables different retransmission strategies to cope with losses such as a) retransmitting lost frames over the same path, b) retransmitting lost frames on a different or dedicated path, and c) duplicate lost frames on several paths (not recommended for general purpose use due to the network overhead). While this document does not preclude a specific strategy, more detailed specification is out of scope.

複数パスの同時使用により、損失に対処するためのさまざまな再送戦略が可能になります。たとえば、a) 失われたフレームを同じパスで再送する、b) 失われたフレームを別のパスまたは専用のパスで再送する、c) 失われたフレームを複数のパスで重複して送信する（ネットワークのオーバーヘッドのため、汎用目的での使用は推奨されません）、などです。本文書は特定の戦略を排除するものではありませんが、より詳細な規定は本文書の範囲外です。

As noted in Section 2.2 of [QUIC-TRANSPORT], STREAM frame boundaries are not expected to be preserved when data is retransmitted. Especially when STREAM frames have to be retransmitted over a different path with a smaller MTU limit, smaller STREAM frames might need to be sent instead.

[QUIC-TRANSPORT] のセクション2.2で述べられているとおり、データが再送される際に、STREAMフレームの境界が保持されることは期待されていません。特に、STREAMフレームを、MTU制限がより小さい別のパスで再送しなければならない場合には、代わりにより小さいSTREAMフレームを送信する必要が生じることがあります。

5.7. PTO Expiration
5.7. PTOの満了

An implementation should follow the mechanism specified in [QUIC-RECOVERY] for detecting packet loss on each individual path. A special case happens when the PTO timer expires. According to [QUIC-RECOVERY], no packet will be declared lost until either the packet sender receives a new acknowledgment for this path or the path itself is finally declared broken. This cautious process minimizes the risk of spurious retransmissions, but it might cause significant delivery delay for the frames contained in these "lost packets".

実装は、個々のパスでのパケット損失の検出について、[QUIC-RECOVERY] で規定されているメカニズムに従うべきです。PTOタイマが満了したときには、特別なケースが発生します。[QUIC-RECOVERY] によれば、パケットの送信者がそのパスについて新しい確認応答を受信するか、パス自体が最終的に故障と宣言されるまでは、どのパケットも損失と宣言されません。この慎重なプロセスは、不要な再送のリスクを最小限に抑えますが、これらの「失われたパケット」に含まれるフレームの配送に、大きな遅延を生じさせる可能性があります。

Endpoints could take advantage of the multipath extension and retransmit the content of the delayed packets on other available paths if the congestion control window on these paths allows.

エンドポイントは、マルチパス拡張を活用し、これらのパス上の輻輳制御ウィンドウが許容するのであれば、遅延したパケットの内容を他の利用可能なパス上で再送してもよいでしょう。

5.8. Paths Having Different PMTU Sizes
5.8. PMTUサイズが異なるパス

An implementation should take care to handle different Path MTU (PMTU) sizes across multiple paths. As specified in Section 14.3 of [QUIC-TRANSPORT], the Datagram Packetization Layer PMTU Discovery (DPLPMTUD) Maximum Packet Size (MPS) is maintained for each combination of local and remote IP addresses. Note that with the multipath extension, multiple paths could use the same 4-tuple but might have different MPS due to other factors (see Section 5.2).

実装は、複数のパスにまたがる異なるパスMTU (PMTU) サイズを扱うよう注意すべきです。[QUIC-TRANSPORT] のセクション14.3で規定されているとおり、Datagram Packetization Layer PMTU Discovery (DPLPMTUD) の最大パケットサイズ (MPS) は、ローカルIPアドレスとリモートIPアドレスの組み合わせごとに維持されます。なお、マルチパス拡張では、複数のパスが同じ4タプルを使用していても、他の要因によりMPSが異なる場合があります (セクション5.2を参照)。

One simple option, if the PMTUs are similar, is to apply the minimum PMTU of all paths to each path, which could also help to simplify retransmission processing.

PMTUが類似している場合の簡単な選択肢の一つは、全パスの最小PMTUを各パスに適用することです。これは再送処理の簡素化にも役立つ可能性があります。

5.9. Idle Timeout and Keep-Alives
5.9. アイドルタイムアウトとキープアライブ

[QUIC-TRANSPORT] defines an idle timeout for closing the connection, which applies in case of multipath usage if no packet is received on any path for the duration of the idle timeout.

[QUIC-TRANSPORT] はコネクションを閉じるためのアイドルタイムアウトを定義しています。マルチパスを使用する場合、このアイドルタイムアウトは、アイドルタイムアウトの期間中どのパスでもパケットを受信しなかったときに適用されます。

This document does not specify per-path idle timeouts. An endpoint can decide to close a path at any time, whether the path is in active use or not. For example, an endpoint might wait to send the initial PATH_ABANDON frame until it sends another frame anyway. Note that the receiver of an initial PATH_ABANDON frame is, however, required to immediately reply (see Section 3.4).

本文書では、パスごとのアイドルタイムアウトは規定しません。エンドポイントは、パスが実際に使用中かどうかにかかわらず、いつでもパスを閉じることを決定できます。たとえば、エンドポイントは、いずれにせよ別のフレームを送信するときまで、最初のPATH_ABANDONフレームの送信を待つことがあります。ただし、最初のPATH_ABANDONフレームの受信側は、直ちに応答することが求められる点に注意してください (セクション3.4を参照)。

If a path is not actively used for a while, it might not be usable anymore, e.g., due to middlebox timeouts. To avoid such path breakage, endpoints can send ack-eliciting packets, such as packets containing PING frames (Section 19.2 of [QUIC-TRANSPORT]) on that path to keep it alive. However, this specification does not recommend sending keep-alives, as it can create unnecessary overhead, especially if there are other actively used paths.

パスがしばらく積極的に使用されない場合、ミドルボックスのタイムアウトなどにより、そのパスが使用できなくなる可能性があります。このようなパスの破損を避けるため、エンドポイントは、そのパス上でPINGフレーム ([QUIC-TRANSPORT] のセクション19.2) を含むパケットなどのack-elicitingパケットを送信して、パスを維持できます。ただし、不要なオーバーヘッドを生じさせる可能性があり、特に積極的に使用されている他のパスがある場合はそうであるため、本仕様はキープアライブの送信を推奨しません。

Section 5.3 of [QUIC-TRANSPORT] defines an optional keep-alive process. This process can be applied to each path separately depending on application needs. Some applications could decide to not keep any not-actively used path alive or keep only one additional path or multiple paths (e.g., for more redundancy) alive. As discussed in Section 10.1.2 of [QUIC-TRANSPORT], the keep-alive interval needs to incorporate timeouts in middleboxes on the path.

[QUIC-TRANSPORT] のセクション5.3は、任意のキープアライブ処理を定義しています。この処理は、アプリケーションの必要に応じて、パスごとに個別に適用できます。アプリケーションによっては、積極的に使用されていないパスを一切維持しないことも、追加のパスを1つだけ、または (冗長性を高めるため) 複数のパスを維持することも決定できるでしょう。[QUIC-TRANSPORT] のセクション10.1.2で議論されているとおり、キープアライブの間隔は、パス上のミドルボックスにおけるタイムアウトを考慮する必要があります。

If a path was not actively used for a while and no keep-alives have been sent, an endpoint can probe it before switching to active use if there are still other paths that are currently usable.

パスがしばらく積極的に使用されておらず、キープアライブも送信されていなかった場合、現在使用可能な他のパスがまだあるのであれば、エンドポイントは、そのパスを積極的な使用に切り替える前にプローブできます。

7. Security Considerations
7. セキュリティに関する考慮事項

The multipath extension retains all security properties of [QUIC-TRANSPORT] and [QUIC-TLS] but requires some additional consideration regarding:

マルチパス拡張は [QUIC-TRANSPORT] および [QUIC-TLS] のすべてのセキュリティ特性を維持しますが、次の点について追加の考慮が必要です。

* potential additional resource usage for per-path connection IDs and multiple concurrent path contexts,

* パスごとのコネクションIDおよび複数の同時パスコンテキストによる、リソース使用量の潜在的な増加、

* a potentially increased amplification risk for denial-of-service attacks if multiple paths are used simultaneously, and

* 複数のパスを同時に使用する場合の、サービス拒否攻撃における増幅リスクの潜在的な増大、および

* changes to the nonce calculation due to the use of multiple packet number spaces.

* 複数のパケット番号空間の使用に起因する、ノンス計算の変更。

7.1. Memory Allocation for Per-Path Resources
7.1. パスごとのリソースのメモリ割り当て

The maximum path ID limit in initial_max_path_id or the MAX_PATH_ID frame limits the number of paths an endpoint is willing to maintain and thereby also limits the associated path resources. Furthermore, as connection IDs have to be issued by both endpoints for the same path ID before an endpoint can open a path, each endpoint could also control the per-path resource usage by only issuing connection IDs for a limited number of paths. However, using the maximum path ID limit in initial_max_path_id or the MAX_PATH_ID frame is preferred.

initial_max_path_idまたはMAX_PATH_IDフレームにおける最大パスID制限は、エンドポイントが維持してもよいとするパスの数を制限し、それにより関連するパスリソースも制限します。さらに、エンドポイントがパスを開く前に、同じパスIDに対して両方のエンドポイントがコネクションIDを発行しなければならないため、各エンドポイントは、限られた数のパスに対してのみコネクションIDを発行することで、パスごとのリソース使用量を制御することもできます。ただし、initial_max_path_idまたはMAX_PATH_IDフレームにおける最大パスID制限の使用が望ましいです。

To avoid unnecessary resource usage that could be exploited in a resource exhaustion attack, endpoints SHOULD allocate additional path resources, such as, e.g., for packet number handling, only after path validation has successfully completed.

リソース枯渇攻撃に悪用される可能性のある不要なリソース使用を避けるため、エンドポイントは、パケット番号の処理など、追加のパスリソースを、パス検証が正常に完了した後にのみ割り当てるべきです (SHOULD)。

7.2. Denial of Service with Multiple Paths
7.2. 複数パスによるサービス拒否

Path validation as specified in Section 8.2 of [QUIC-TRANSPORT] for migration is used unchanged for path initiation in this extension. Further, the multipath extension allows for the creation of multiple paths, which means that in addition to the security considerations on source address spoofing outlined in Section 21.5.4 of [QUIC-TRANSPORT], there is a risk of amplified denial-of-service attacks through simultaneous opening or migration of multiple paths. For example, an attacker could set or spoof the 4-tuples used in multiple paths so that packets sent by the server would travel through common network paths in an attempt to overwhelm a target.

マイグレーションのために [QUIC-TRANSPORT] のセクション8.2で規定されているパス検証は、本拡張におけるパスの開始にも変更なしで使用されます。さらに、マルチパス拡張は複数のパスの作成を可能にするため、[QUIC-TRANSPORT] のセクション21.5.4で概説されている送信元アドレス詐称に関するセキュリティ上の考慮事項に加えて、複数のパスを同時に開く、またはマイグレーションすることによって、増幅されたサービス拒否攻撃が行われるリスクがあります。たとえば、攻撃者は、複数のパスで使用される4タプルを設定または詐称し、サーバが送信したパケットが共通のネットワーク経路を通って、標的を圧倒しようとすることができます。

[QUIC-TRANSPORT] only allows the use of one path and the number of concurrent path validation attempts is limited by the number of issued connection IDs. This extension allows for multiple open paths that could in theory be migrated all at the same time, still limited by the number of issued connection IDs for each path. Further, multiple paths could be initialized simultaneously, limited by the maximum number of allowed paths.

[QUIC-TRANSPORT] は1つのパスの使用のみを許可しており、同時に行われるパス検証の試行回数は、発行されたコネクションIDの数によって制限されます。本拡張は複数のオープンなパスを許可し、それらは理論上すべて同時にマイグレーションできますが、各パスに対して発行されたコネクションIDの数によって、やはり制限されます。さらに、複数のパスを同時に初期化できますが、許可されるパスの最大数によって制限されます。

Therefore, endpoints are advised to keep the maximum number of paths small and might consider additional measures to limit the number of concurrent path validation processes, e.g., by pacing them out or limiting the number of path initiation attempts over a certain time period.

したがって、エンドポイントには、パスの最大数を小さく保つことが推奨されます。また、同時に行われるパス検証処理の数を制限するための追加の対策を検討してもよいでしょう。たとえば、パス検証処理の間隔を空けて実行する、または一定期間内のパス開始の試行回数を制限するといった対策です。

However, the use of multipath does not change the anti-amplification limits as specified in Section 8 of [QUIC-TRANSPORT]. The attacker would need to send a separate challenge on each path used in the attack, and the amplification limits would apply to the amount of data sent by the server on that path. The attacker could get the same effect by opening many QUIC connections and conducting the attack on each of them without negotiating the multipath option.

しかし、マルチパスの使用は、[QUIC-TRANSPORT] のセクション8で規定されているアンチ増幅制限を変更しません。攻撃者は攻撃に使用する各パスで個別にチャレンジを送信する必要があり、アンチ増幅制限は、そのパス上でサーバが送信するデータ量に適用されます。攻撃者は、マルチパスオプションをネゴシエートせずに多数のQUICコネクションを開き、それぞれで攻撃を行うことでも、同じ効果を得ることができます。

7.3. Cryptographic Handshake and AEAD Nonce
7.3. 暗号ハンドシェイクとAEADノンス

The multipath extension as specified in this document is only enabled after a successful handshake when both endpoints indicate support for this extension. All new frames defined in this extension are only used in 1-RTT packets.

本文書で規定するマルチパス拡張は、ハンドシェイクが成功し、両方のエンドポイントが本拡張のサポートを示した後にのみ有効になります。本拡張で定義されるすべての新しいフレームは、1-RTTパケットでのみ使用されます。

As the handshake is not changed by this extension, the transport security mechanisms as specified in [QUIC-TLS], such as encryption key exchange and peer authentication, remain unchanged. As such, the security considerations in [QUIC-TLS] apply unaltered.

ハンドシェイクは本拡張によって変更されないため、暗号鍵交換やピア認証など、[QUIC-TLS] で規定されているトランスポートのセキュリティ機構は変更されません。したがって、[QUIC-TLS] のセキュリティに関する考慮事項はそのまま適用されます。

The limits as discussed on Appendix B of [QUIC-TLS] apply to the total number of packets sent on all paths, not each path separately.

[QUIC-TLS] の付録Bで議論されている制限は、各パスに個別にではなく、すべてのパスで送信されたパケットの総数に適用されます。

This specification changes the AEAD nonce calculation by including the path ID as part of the calculation (see Section 2.4). To ensure unique nonces, path IDs are limited to 32 bits and cannot be reused for another path of the same connection.

本仕様は、パスIDを計算の一部として含めることで、AEADノンスの計算を変更します (セクション2.4を参照)。ノンスの一意性を確保するため、パスIDは32ビットに制限され、同じコネクションの別のパスに再利用することはできません。
