Abstract

要旨

This document updates RFCs 7521, 7522, 7523, and 9126 with respect to the treatment of audience values in OAuth 2.0 Client Assertion Authentication and Assertion-based Authorization Grants to address a security vulnerability identified in the previous requirements for those audience values in multiple OAuth 2.0 specifications.

本文書は、複数のOAuth 2.0仕様においてオーディエンス値に関する従来の要件に見つかったセキュリティ上の脆弱性に対処するため、OAuth 2.0クライアントアサーション認証およびアサーションベースの認可グラントにおけるオーディエンス値の扱いに関して、RFC 7521、7522、7523、9126を更新します。

1. Introduction

1. はじめに

Multiple OAuth 2.0 specifications use tokens (also known as "assertions") that are sent to authorization servers. These tokens contain audience value(s) that identify the intended recipient(s). When the token is a JSON Web Token (JWT) [RFC7519], the audience value(s) are contained in the "aud" (audience) claim.

複数のOAuth 2.0仕様では、認可サーバーに送信されるトークン (「アサーション」とも呼ばれます) を使用します。これらのトークンには、意図された受信者を識別するオーディエンス値が含まれます。トークンがJSON Web Token (JWT) [RFC7519] の場合、オーディエンス値は "aud" (オーディエンス) クレームに含まれます。

When performing a security analysis of a pre-final version of the OpenID Federation specification [OpenID.Federation], University of Stuttgart security researchers Pedram Hosseyni, Dr. Ralf Küsters, and Tim Würtele discovered a vulnerability affecting multiple OpenID and OAuth specifications caused by ambiguities in the audience values of tokens sent to authorization servers. The vulnerability was disclosed to the OAuth Working Group in an interim meeting in January 2025 called for that purpose and a description of the vulnerability [private_key_jwt.Disclosure] was provided. A paper they published describing the attack is [Audience.Injection].

シュトゥットガルト大学のセキュリティ研究者であるPedram Hosseyni、Dr. Ralf Küsters、Tim Würtele は、OpenID Federation仕様 [OpenID.Federation] の最終版前の版のセキュリティ分析を行った際に、認可サーバーに送信されるトークンのオーディエンス値の曖昧さに起因する、複数のOpenID仕様およびOAuth仕様に影響する脆弱性を発見しました。この脆弱性は、2025年1月にその目的で招集された臨時会合でOAuthワーキンググループに開示され、脆弱性の説明 [private_key_jwt.Disclosure] が提供されました。この攻撃を説明する、彼らが発表した論文は [Audience.Injection] です。

This specification updates the affected OAuth specifications to address the security vulnerability that was identified. Specifically, it eliminates former choices in the audience values of tokens sent to OAuth 2.0 authorization servers. Section 3.3 of [RFC8414] requires that the client having retrieved the metadata validates the returned issuer value. Other endpoint values of the metadata cannot be directly validated and, if used as the audience when sent to a different endpoint, can open an attack vector.

本仕様は、特定されたセキュリティ上の脆弱性に対処するため、影響を受けるOAuth仕様を更新します。具体的には、OAuth 2.0認可サーバーに送信されるトークンのオーディエンス値について、従来あった選択肢を排除します。[RFC8414] の第3.3節は、メタデータを取得したクライアントが、返された issuer の値を検証することを要求しています。メタデータのその他のエンドポイント値は直接検証することができず、別のエンドポイントに送信される際のオーディエンスとして使用されると、攻撃ベクトルとなる可能性があります。

A general description of the updates made is to require that the issuer identifier URL of the authorization server, as defined in [RFC8414], be used as the sole value of the audience of the JWT client authentication assertion. Furthermore, the authorization server rejects any JWT client authentication assertion that does not contain its own issuer identifier as the sole audience value. An explicit type for the JWT client authentication assertion, as defined in [RFC8725], is also defined to facilitate distinguishing between tokens produced in accordance with specifications published prior to these updates and those incorporating them. Specific updates made to each affected specification follow.

更新内容の概要は、[RFC8414] で定義される認可サーバーの発行者識別子URLを、JWTクライアント認証アサーションのオーディエンスの唯一の値として使用することを要求する、というものです。さらに、認可サーバーは、自身の発行者識別子を唯一のオーディエンス値として含まないJWTクライアント認証アサーションを拒否します。また、これらの更新より前に公開された仕様に従って生成されたトークンと、更新を取り入れたトークンを区別しやすくするため、[RFC8725] で定義される、JWTクライアント認証アサーションの明示的な型も定義されます。影響を受ける各仕様に対する個別の更新を以下に示します。

4. Updates to RFC 7523

4. RFC 7523の更新

This section updates "JSON Web Token (JWT) Profile for OAuth 2.0 Client Authentication and Authorization Grants" [RFC7523] to tighten its audience requirements.

本セクションは、オーディエンスに関する要件を厳格化するため、"JSON Web Token (JWT) Profile for OAuth 2.0 Client Authentication and Authorization Grants" [RFC7523] を更新します。

OLD:

OLD:

The JWT MUST contain an "aud" (audience) claim containing a value that identifies the authorization server as an intended audience. The token endpoint URL of the authorization server MAY be used as a value for an "aud" element to identify the authorization server as an intended audience of the JWT. The authorization server MUST reject any JWT that does not contain its own identity as the intended audience. 6. Operational Considerations

6. 運用上の考慮事項

Changes in this specification affect interoperability between clients and authorization servers that implement different versions. In particular, the resulting compatibility is not entirely symmetric. A client implementing this specification will interoperate with both authorization servers conforming to the updates herein as well as authorization servers implementing earlier versions. However, some clients implementing earlier versions may not interoperate with authorization servers that strictly enforce the updated requirements in this specification. Deployments upgrading to this specification should consider this asymmetry when planning rollouts or migrations, as it may be necessary to ensure that clients are updated before, or in coordination with, authorization servers that enforce the updated behavior.

この仕様の変更は、異なるバージョンを実装するクライアントと認可サーバーとの間の相互運用性に影響します。特に、結果として得られる互換性は完全に対称ではありません。この仕様を実装するクライアントは、ここでの更新に準拠する認可サーバーとも、以前のバージョンを実装する認可サーバーとも相互運用できます。しかし、以前のバージョンを実装する一部のクライアントは、この仕様の更新された要件を厳格に強制する認可サーバーとは相互運用できない場合があります。この仕様へアップグレードする展開では、ロールアウトや移行を計画する際にこの非対称性を考慮すべきです。更新された動作を強制する認可サーバーより前に、またはそれと連携して、クライアントが更新されていることを確実にする必要がある場合があるためです。
