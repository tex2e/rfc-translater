1. Introduction
1. はじめに

[RFC10073] defines a collection of signature algorithms, referred to as Composite ML-DSA, which combine ML-DSA [FIPS.204] with RSASSA-PKCS1-v1.5 [RFC8017], RSASSA-PSS [RFC8017], ECDSA (Section 6 of [FIPS.186-5]), Ed25519 [RFC8410], and Ed448 [RFC8410]. This document acts as a companion to [RFC10073] by providing conventions for using Composite ML-DSA algorithms within the Cryptographic Message Syntax (CMS) [RFC5652].

[RFC10073] は、Composite ML-DSA と呼ばれる署名アルゴリズム群を定義しています。これらは、ML-DSA [FIPS.204] を RSASSA-PKCS1-v1.5 [RFC8017]、RSASSA-PSS [RFC8017]、ECDSA ([FIPS.186-5] の第6節)、Ed25519 [RFC8410]、Ed448 [RFC8410] と組み合わせたものです。本文書は [RFC10073] の補足文書として、暗号メッセージ構文 (CMS) [RFC5652] の中で Composite ML-DSA アルゴリズムを使用するための規約を提供します。

1.1. ASN.1

CMS values are generated using ASN.1 [X.680], using the Basic Encoding Rules (BER) and the Distinguished Encoding Rules (DER) [X.690].

3. Signed-Data Conventions
3. Signed-Data の規約
3.1. Pre-Hashing
3.1. プリハッシュ

[RFC5652] specifies that digital signatures for CMS are produced using a digest of the message to be signed and the signer's private key. At the time [RFC5652] was published, all signature algorithms supported in the CMS required a message digest to be calculated externally to that algorithm, which would then be supplied to the algorithm implementation when calculating and verifying signatures. Since then, EdDSA [RFC8032] and ML-DSA [FIPS.204] have also been standardized, and these algorithms support both a "pure" and a "pre-hash" mode, although their use in CMS has only been defined for "pure" mode.

[RFC5652] は、CMS のデジタル署名が、署名対象メッセージのダイジェストと署名者の秘密鍵を用いて生成されることを規定しています。[RFC5652] が発行された時点では、CMS でサポートされていたすべての署名アルゴリズムは、そのアルゴリズムの外部でメッセージダイジェストを計算する必要があり、そのダイジェストが署名の計算および検証時にアルゴリズムの実装へ渡されました。その後、EdDSA [RFC8032] と ML-DSA [FIPS.204] も標準化され、これらのアルゴリズムは "pure" モードと "pre-hash" モードの両方をサポートしますが、CMS での使用は "pure" モードについてのみ定義されています。

Composite ML-DSA only provides a "pre-hash" mode. Unlike RSA and ECDSA, each Composite ML-DSA algorithm is defined to be used with a single digest algorithm, which is identified in the Composite ML-DSA algorithm name. For example, id-MLDSA87-ECDSA-P521-SHA512 uses SHA-512 as its pre-hash digest algorithm.

Composite ML-DSA は "pre-hash" モードのみを提供します。RSA や ECDSA とは異なり、各 Composite ML-DSA アルゴリズムは単一のダイジェストアルゴリズムとともに使用されるよう定義されており、そのダイジェストアルゴリズムは Composite ML-DSA アルゴリズム名で識別されます。例えば、id-MLDSA87-ECDSA-P521-SHA512 は、プリハッシュのダイジェストアルゴリズムとして SHA-512 を使用します。

When Composite ML-DSA is used in CMS, the digest algorithm used by CMS SHALL be the same pre-hash digest algorithm used by the Composite ML-DSA algorithm. A Composite ML-DSA algorithm might use additional digest algorithms internally, e.g., in the case of id-MLDSA87-ECDSA-P384-SHA512, the ECDSA component uses SHA-384. These internal digest algorithms are irrelevant to Composite ML-DSA's use in CMS.

CMS で Composite ML-DSA を使用する場合、CMS が使用するダイジェストアルゴリズムは、Composite ML-DSA アルゴリズムが使用するプリハッシュのダイジェストアルゴリズムと同一でなければなりません (SHALL)。Composite ML-DSA アルゴリズムは、内部で追加のダイジェストアルゴリズムを使用する場合があります。例えば id-MLDSA87-ECDSA-P384-SHA512 の場合、ECDSA コンポーネントは SHA-384 を使用します。これらの内部ダイジェストアルゴリズムは、CMS における Composite ML-DSA の使用には無関係です。

3.3. Signature Generation and Verification
3.3. 署名の生成と検証

[RFC5652] describes the two methods that are used to calculate and verify signatures in the CMS. One method is used when signed attributes are present in the signedAttrs field of the relevant SignerInfo, and another is used when signed attributes are absent. Use of signed attributes is preferred, but the conventions for the signed-data content type without signed attributes are also described below for completeness.

[RFC5652] は、CMS で署名を計算および検証するために使用される2つの方法を記述しています。一方は、該当する SignerInfo の signedAttrs フィールドに署名属性が存在する場合に使用され、もう一方は署名属性が存在しない場合に使用されます。署名属性の使用が望ましいですが、署名属性を持たない signed-data コンテンツタイプの規約についても、完全を期すため以下に記述します。

When signed attributes are absent, Composite ML-DSA signatures are computed over the content of the signed-data. As described in Section 5.4 of [RFC5652], the "content" of a signed-data is the value of the encapContentInfo eContent OCTET STRING. The tag and length octets are not included.

署名属性が存在しない場合、Composite ML-DSA 署名は signed-data のコンテンツに対して計算されます。[RFC5652] の第5.4節に記載されているとおり、signed-data の「コンテンツ」とは、encapContentInfo の eContent OCTET STRING の値です。タグおよび長さのオクテットは含まれません。

When signed attributes are included, Composite ML-DSA signatures are computed over the complete DER encoding of the SignedAttrs value contained in the SignerInfo's signedAttrs field. As described in Section 5.4 of [RFC5652], this encoding includes the tag and length octets, but an EXPLICIT SET OF tag is used rather than the IMPLICIT [0] tag that appears in the final message. At a minimum, the signedAttrs field MUST include a content-type attribute and a message-digest attribute. The message-digest attribute contains a hash of the content of the signed-data, where the content is as described for the case with absent signed attributes above. Recalculation of the hash value by the recipient is an important step in signature verification.

署名属性が含まれる場合、Composite ML-DSA 署名は、SignerInfo の signedAttrs フィールドに含まれる SignedAttrs 値の完全な DER エンコードに対して計算されます。[RFC5652] の第5.4節に記載されているとおり、このエンコードにはタグおよび長さのオクテットが含まれますが、最終的なメッセージに現れる IMPLICIT [0] タグではなく、EXPLICIT SET OF タグが使用されます。signedAttrs フィールドには、少なくとも content-type 属性と message-digest 属性を含めなければなりません (MUST)。message-digest 属性には signed-data のコンテンツのハッシュが含まれ、そのコンテンツは、上記の署名属性が存在しない場合について記述したものと同じです。受信者によるハッシュ値の再計算は、署名検証における重要なステップです。

Composite ML-DSA has a context string input that can be used to ensure that different signatures are generated for different application contexts. When using Composite ML-DSA as specified in this document, the context string is set to the empty string.

Composite ML-DSA には、異なるアプリケーションコンテキストごとに異なる署名が生成されるようにするために使用できるコンテキスト文字列の入力があります。本文書で規定するとおりに Composite ML-DSA を使用する場合、コンテキスト文字列は空文字列に設定されます。

5. Security Considerations
5. セキュリティに関する考慮事項

All security considerations from [RFC10073] apply.

[RFC10073] のセキュリティに関する考慮事項はすべて適用されます。

Security of the Composite ML-DSA private key is critical. Compromise of the private key will enable an adversary to forge arbitrary signatures.

Composite ML-DSA の秘密鍵のセキュリティは極めて重要です。秘密鍵が漏えいすると、攻撃者が任意の署名を偽造できるようになります。

Composite ML-DSA depends on high-quality random numbers that are suitable for use in cryptography. The use of inadequate pseudorandom number generators (PRNGs) to generate such values can significantly undermine the security properties offered by a cryptographic algorithm. For instance, an attacker may find it much easier to reproduce the PRNG environment that produced any private keys, searching the resulting small set of possibilities, rather than brute-force searching the whole key space. The generation of random numbers of a sufficient level of quality for use in cryptography is difficult; see Section 3.6.1 of [FIPS.204] for some additional information.

Composite ML-DSA は、暗号用途に適した高品質の乱数に依存しています。不十分な擬似乱数生成器 (PRNG) を使ってそのような値を生成すると、暗号アルゴリズムが提供するセキュリティ特性が大幅に損なわれる可能性があります。たとえば攻撃者は、鍵空間全体を総当たりで探索するよりも、秘密鍵を生成した PRNG の環境を再現し、その結果得られる小さな候補集合を探索するほうがはるかに容易だと気付くかもしれません。暗号用途に十分な品質の乱数を生成することは困難です。追加情報については [FIPS.204] のセクション 3.6.1 を参照してください。

To avoid algorithm substitution attacks, the CMSAlgorithmProtection attribute defined in [RFC6211] SHOULD be included in signed attributes.

アルゴリズム置換攻撃を避けるため、[RFC6211] で定義される CMSAlgorithmProtection 属性を署名属性に含めるべきです (SHOULD)。

Section 3.4 specifies that the SignerInfo digestAlgorithm field MUST contain the Composite ML-DSA algorithm's pre-hash algorithm. If the digestAlgorithm and pre-hash algorithm don't match, the verifier SHOULD reject the message as invalid CMS, but for backwards compatibility or interoperability reasons, it MAY verify the signature using the pre-hash algorithm. If these algorithms don't match, this implies that the signer may have passed an incorrect digest value to the Composite ML-DSA signing algorithm and the resulting signature would not be valid for the data being signed. This is a general issue with CMS, where a SignerInfo's digestAlgorithm field might not correspond to the digest required by the SignerInfo's signatureAlgorithm field.

セクション 3.4 は、SignerInfo の digestAlgorithm フィールドに Composite ML-DSA アルゴリズムのプリハッシュアルゴリズムを含めなければならない (MUST) と規定しています。digestAlgorithm とプリハッシュアルゴリズムが一致しない場合、検証者はそのメッセージを不正な CMS として拒否すべきです (SHOULD)。ただし、後方互換性や相互運用性のために、プリハッシュアルゴリズムを使用して署名を検証してもよい (MAY) とされています。これらのアルゴリズムが一致しない場合、署名者が Composite ML-DSA 署名アルゴリズムに誤ったダイジェスト値を渡した可能性があり、その結果得られた署名は署名対象のデータに対して有効ではないことを意味します。これは CMS 全般に見られる問題であり、SignerInfo の digestAlgorithm フィールドが、SignerInfo の signatureAlgorithm フィールドが必要とするダイジェストに対応していない場合があります。

ECDSA, EdDSA, and RSA signatures are relatively small compared to ML-DSA signatures, and thus compared to Composite ML-DSA signatures as well. On the other hand, Composite ML-DSA signatures are not that much larger than ML-DSA signatures. When moving from ECDSA, EdDSA, or RSA to Composite ML-DSA (or ML-DSA), the resulting increased message sizes could stress size-constrained processing pipelines.

ECDSA、EdDSA、RSA の署名は ML-DSA の署名に比べて比較的小さく、したがって Composite ML-DSA の署名と比べても小さくなります。一方、Composite ML-DSA の署名は ML-DSA の署名よりそれほど大きくはありません。ECDSA、EdDSA、または RSA から Composite ML-DSA (または ML-DSA) に移行すると、メッセージサイズが増加し、サイズに制約のある処理パイプラインに負荷がかかる可能性があります。

ECDSA (with curve secp256r1) and Ed25519 have very fast signing operations compared to ML-DSA (and thus Composite ML-DSA). Implementations that rely on this fast signing should be aware of potential denial-of-service issues arising from the slower signing times.

ECDSA (曲線 secp256r1) と Ed25519 は、ML-DSA (したがって Composite ML-DSA) と比べて署名操作が非常に高速です。この高速な署名に依存する実装は、署名時間が長くなることで生じ得るサービス拒否の問題に注意すべきです。
