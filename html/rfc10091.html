Extension Registry for the Extensible Provisioning Protocol

拡張プロビジョニングプロトコル (EPP) の拡張レジストリ

Abstract

要約

The Extensible Provisioning Protocol (EPP) includes features to add functionality by extending the protocol. It does not, however, describe how those extensions are maintained. This document describes a procedure for the registration and management of extensions to EPP, and it specifies a format for an IANA registry to record those extensions. This document obsoletes RFC 7451.

拡張プロビジョニングプロトコル (EPP) には、プロトコルを拡張することで機能を追加する仕組みが含まれています。しかし、それらの拡張をどのように維持管理するかは記述されていません。本文書は、EPPの拡張の登録と管理の手順を説明し、それらの拡張を記録するIANAレジストリの形式を規定します。本文書はRFC 7451を廃止します。

1. Introduction

1. はじめに

Domain name registries implement a variety of operational and business models. The differences in these models make it impossible to develop a "one size fits all" provisioning protocol; the Extensible Provisioning Protocol [STD69] was designed to focus on a minimal set of common functionality with built-in extension capabilities that allow new features to be specified on an "as needed" basis. Guidelines for extending EPP are documented in [RFC3735] (or its future replacement).

ドメイン名レジストリは、さまざまな運用モデルやビジネスモデルを実装しています。これらのモデルの違いにより、「万能型」のプロビジョニングプロトコルを開発することは不可能です。拡張プロビジョニングプロトコル [STD69] は、共通機能の最小限の集合に焦点を当て、新しい機能を「必要に応じて」規定できる拡張機能を組み込む形で設計されました。EPPを拡張するためのガイドラインは、[RFC3735] (またはその将来の置き換え文書) に記載されています。

[STD69] and [RFC3735] do not describe how extension development can be managed and coordinated. This has led to a situation in which server operators can develop different extensions to address similar needs, such as the provisioning of Value Added Tax (VAT) information. Clients then need to support multiple extensions that serve similar purposes, and interoperability suffers as a result.

[STD69] と [RFC3735] は、拡張の開発をどのように管理・調整できるかを記述していません。このため、サーバ運用者が、付加価値税 (VAT) 情報のプロビジョニングなど、類似のニーズに対応するために異なる拡張を開発する事態が生じています。その結果、クライアントは類似の目的を持つ複数の拡張をサポートする必要があり、相互運用性が損なわれています。

[RFC7451] filled that gap by defining the "Extensions for the Extensible Provisioning Protocol (EPP)" IANA registry [IANA-REG] to help manage and coordinate the development of EPP extensions.

[RFC7451] は、EPP拡張の開発の管理と調整を支援するために、「Extensions for the Extensible Provisioning Protocol (EPP)」IANAレジストリ [IANA-REG] を定義することで、その空白を埋めました。

This document addresses issues that were identified with [RFC7451] over time. Refer to Section 1.1 for more details.

本文書は、[RFC7451] に関して時間の経過とともに特定された問題に対処します。詳細はセクション1.1を参照してください。

2. Extension Specification and Registration Procedure

2. 拡張の仕様と登録手順

This section describes the format of the Extensions for the Extensible Provisioning Protocol (EPP) IANA registry [IANA-REG] and the procedures used to populate and manage registry entries.

本セクションでは、Extensions for the Extensible Provisioning Protocol (EPP) IANAレジストリ [IANA-REG] の形式と、レジストリエントリの登録・管理に使用される手順を説明します。

2.1. Extension Specification

2.1. 拡張の仕様

This registry uses the "Specification Required" policy described in [RFC8126]. Note that Section 2.1 of [RFC3735] (or its future replacement) provides specific guidelines for documenting EPP extensions.

本レジストリは、[RFC8126] に記載されている「Specification Required」ポリシーを使用します。なお、[RFC3735] (またはその将来の置き換え文書) のセクション2.1は、EPP拡張を文書化するための具体的なガイドラインを提供しています。

The "Specification Required" policy requires review by a designated expert. Section 5 of [RFC8126] describes the role of designated experts and the function they perform. For this registry, acceptable specifications include RFC documents and proprietary specifications that meet the "permanent and readily available" requirement described in Section 4.6 of [RFC8126]. An English language version of the extension specification MUST be referenced from the registry, though non-English versions of the specification may also be provided. Internet-Draft documents are not acceptable specifications for future registrations. Early allocations [RFC7120] do not apply to the Extensions for the EPP IANA registry [IANA-REG].

「Specification Required」ポリシーでは、指定エキスパートによるレビューが必要です。[RFC8126] のセクション5は、指定エキスパートの役割と、その果たす機能を説明しています。本レジストリにおいて受け入れられる仕様には、RFC文書、および [RFC8126] のセクション4.6に記載されている「permanent and readily available」(恒久的かつ容易に入手可能) の要件を満たす独自の仕様が含まれます。拡張仕様の英語版をレジストリから参照しなければなりません (MUST)。ただし、仕様の英語以外の版も併せて提供してもかまいません。インターネットドラフト文書は、今後の登録における仕様として受け入れられません。Early allocations [RFC7120] は、Extensions for the EPP IANAレジストリ [IANA-REG] には適用されません。

2.1.1. Designated Expert Evaluation Criteria

2.1.1. 指定エキスパートの評価基準

Section 5.2 of [RFC8126] describes the role of designated experts. This section describes how the practices described in [RFC8126] are applied for evaluation of EPP extension registration requests.

[RFC8126] のセクション5.2は、指定エキスパートの役割を説明しています。本セクションでは、[RFC8126] に記載されている慣行が、EPP拡張の登録要求の評価にどのように適用されるかを説明します。

The IESG should appoint a primary designated expert and a small number of individuals (perhaps 3 - 5) to serve as backup designated experts as described in Section 5.2 of [RFC8126]. The primary designated expert is responsible for conducting all reviews requested by IANA. The secondary designated experts are responsible for conducting reviews as a simple majority, consensus-based group if the primary designated expert is unavailable. In cases where a registration decision could be perceived as creating a conflict of interest for a particular Designated Expert, that Expert MUST defer to the judgment of the other Experts. The designated experts MUST use the existing regext mailing list (regext@ietf.org) or its successor for public discussion of registration requests.

IESGは、[RFC8126] のセクション5.2に記載されているとおり、主担当の指定エキスパート1名と、副担当の指定エキスパートを務める少数 (3〜5名程度) の個人を任命すべきです。主担当の指定エキスパートは、IANAから依頼されたすべてのレビューを実施する責任を負います。副担当の指定エキスパートは、主担当の指定エキスパートが対応できない場合に、単純多数決によるコンセンサスベースのグループとしてレビューを実施する責任を負います。登録の決定が特定の指定エキスパートにとって利益相反を生じるものと受け取られかねない場合、そのエキスパートは他のエキスパートの判断に委ねなければなりません (MUST)。指定エキスパートは、登録要求に関する公開の議論には、既存のregextメーリングリスト (regext@ietf.org) またはその後継を使用しなければなりません (MUST)。

Extensions should be evaluated for architectural soundness using the guidelines described in [RFC3735] (or its future replacement), including the Security Considerations section of that document. Expert evaluation should explicitly include consideration of the privacy consequences of proposed extensions, and, at a minimum, ensure that any privacy considerations are fully documented in the relevant specification(s).

拡張は、[RFC3735] (またはその将来の置き換え文書) に記載されているガイドライン (当該文書のSecurity Considerationsセクションを含む) を用いて、アーキテクチャ上の健全性について評価されるべきです。エキスパートによる評価には、提案された拡張がプライバシーに及ぼす影響の検討を明示的に含め、少なくとも、プライバシーに関する考慮事項が関連する仕様に完全に文書化されていることを確認すべきです。

URIs proposed in extensions (XML namespace and schema registration requests are commonly found in EPP extensions) should be evaluated for both syntactic and semantic correctness. XML schemas, XML schema URIs, and XML namespace URIs defined in the extension specification MUST be registered in the "IETF XML Registry" using the procedures described in [RFC3688]. IETF namespaces MUST be reserved for specifications published in the IETF Stream. Non-IETF namespaces MUST be used for non-IETF specifications (which includes RFC documents produced by all non-IETF streams); the designated experts may need to work with a registrant to identify URIs that can be added to the "IETF XML Registry". Extensions and any normative references necessary to implement the extensions MUST NOT be denoted with "work in progress" or any similar description. Issues discovered during the evaluation MUST be shared with, and can be corrected by, the registrant until the designated experts explicitly decide to accept or reject the registration request.

拡張で提案されるURI (EPP拡張には、XMLの名前空間とスキーマの登録要求が一般的に含まれます) は、構文と意味の両面で正しいかどうかを評価すべきです。拡張仕様で定義されるXMLスキーマ、XMLスキーマのURI、およびXML名前空間のURIは、[RFC3688] に記載されている手順を使用して、「IETF XML Registry」に登録されなければなりません (MUST)。IETFの名前空間は、IETFストリームで発行される仕様のために予約されなければなりません (MUST)。IETF以外の仕様 (IETF以外のすべてのストリームが作成するRFC文書を含む) には、IETF以外の名前空間を使用しなければなりません (MUST)。指定エキスパートは、「IETF XML Registry」に追加できるURIを特定するために、登録者と協力する必要が生じる場合があります。拡張、および拡張の実装に必要な規範的参照は、「work in progress」やそれに類する記述で示してはなりません (MUST NOT)。評価中に発見された問題は、指定エキスパートが登録要求を受理または却下することを明示的に決定するまで、登録者と共有されなければならず (MUST)、登録者によって修正することができます。

Designated experts should be permissive in their evaluation of requests to register extensions that have been implemented and deployed by at least one registry/registrar or server/client pair. This implies that it may indeed be possible to register multiple extensions that provide the same functionality. Requests to register extensions that have not been deployed should be evaluated with a goal of reducing functional duplication. A potential registrant who submits a request to register a new, undeployed extension that includes similar functionality to an existing, registered extension should be made aware of the existing extension. The registrant should be asked to reconsider their request given the existence of a similar extension. Should they decline to do so, perceived similarity SHOULD NOT be a sufficient reason for rejection as long as all other requirements are met.

指定エキスパートは、少なくとも1組のレジストリ/レジストラ、またはサーバ/クライアントによって実装・展開されている拡張の登録要求の評価においては、寛容であるべきです。これは、同じ機能を提供する複数の拡張を実際に登録できる場合があることを意味します。展開されていない拡張の登録要求は、機能の重複を減らすことを目標として評価されるべきです。既存の登録済み拡張と類似の機能を含む、展開されていない新しい拡張の登録要求を提出する潜在的な登録者には、既存の拡張の存在を知らせるべきです。登録者には、類似の拡張が存在することを踏まえて、要求を再考するよう求めるべきです。登録者がそれを断った場合でも、他のすべての要件が満たされている限り、類似していると認められることは、却下の十分な理由とすべきではありません (SHOULD NOT)。

2.2. Registration Procedure

2.2. 登録手順

The registry contains information describing each registered extension. Registry entries are created and managed by sending forms to IANA that describe the extension and the operation to be performed on the registry entry.

レジストリには、登録された各拡張を説明する情報が含まれます。レジストリエントリは、拡張とレジストリエントリに対して実行する操作を記述したフォームをIANAに送ることで、作成・管理されます。

2.2.1. Required Information

2.2.1. 必要な情報

Name of Extension:

Name of Extension (拡張の名前):

A case-insensitive, ASCII text string that contains the name of the extension specification and does not overlap with an existing registered extension. Non-ASCII representations of the extension name can be included in the "Notes" described below.

拡張の仕様の名前を含み、既存の登録済み拡張と重複しない、大文字と小文字を区別しない ASCII テキスト文字列です。拡張名の非 ASCII 表記は、後述の「Notes」に含めることができます。

Document Status:

Document Status (文書ステータス):

The document status of the specification document. For RFCs, the possible set of values includes "Standards Track", "Informational", "Experimental", "Historic", and "BCP" as described in Sections 4 and 5 of [RFC2026]. For documents that are not RFCs, this will always be "Other".

仕様文書の文書ステータスです。RFC の場合、取りうる値の集合には、[RFC2026] のセクション 4 および 5 に記載されている "Standards Track"、"Informational"、"Experimental"、"Historic"、"BCP" が含まれます。RFC ではない文書の場合、値は常に "Other" となります。

Reference:

Reference (参照):

A permanent, publicly available reference to the specification of this extension as described in Section 2.1.1.

セクション 2.1.1 に記載されているとおり、この拡張の仕様への、恒久的で一般に入手可能な参照です。

Registrant Name and Email Address:

Registrant Name and Email Address (登録者の名前とメールアドレス):

The name and email address of the entity that is responsible for managing the registry entry. If the extension is registered by an IETF Stream RFC, this can simply be listed as "IETF, <iesg@ietf.org>".

レジストリエントリの管理に責任を持つ主体の名前とメールアドレスです。拡張が IETF ストリームの RFC によって登録される場合は、単に "IETF, <iesg@ietf.org>" と記載できます。

TLDs:

TLDs (トップレベルドメイン):

A text string containing the top-level domain name (or domain names), including the preceding ".", for which the extension has been specified (e.g., ".org"). If there are multiple TLDs, they are given as a list of domain names separated by commas, (e.g. ".com", ".net"). Internationalized Domain Name (IDN) TLDs MUST be specified in A-label [RFC5890] format. If the extension is not associated with a specific top-level domain, the case-insensitive text string "Any" can be used to indicate that. If the extension is not associated with domain name processing, the case-insensitive text string "N/A" (Not Applicable) can be used to indicate that.

拡張が規定されている対象のトップレベルドメイン名(複数可) を、先頭の "." を含めて記載したテキスト文字列です(例: ".org")。複数の TLD がある場合は、ドメイン名をカンマで区切った一覧として指定します(例: ".com", ".net")。国際化ドメイン名 (IDN) の TLD は、A-label [RFC5890] 形式で指定しなければなりません (MUST)。拡張が特定のトップレベルドメインに関連付けられていない場合は、大文字と小文字を区別しないテキスト文字列 "Any" を使ってそれを示すことができます。拡張がドメイン名の処理に関連付けられていない場合は、大文字と小文字を区別しないテキスト文字列 "N/A" (Not Applicable、該当なし) を使ってそれを示すことができます。

IPR Disclosure:

IPR Disclosure (IPR開示):

A pointer to any Intellectual Property Rights (IPR) disclosure document(s) related to this extension, or "None" may be used if there are no such disclosures. This can be an IPR disclosure filed with the IETF in accordance with BCP 79 [BCP79] if the extension is part of an IETF Contribution, or it can be other IPR disclosure documents identifying the claimed intellectual property rights and terms of use for extensions that are not part of an IETF Contribution.

この拡張に関連する知的財産権 (IPR) 開示文書へのポインタです。そのような開示がない場合は "None" を使ってもかまいません。拡張が IETF Contribution の一部である場合は、BCP 79 [BCP79] に従って IETF に提出された IPR 開示とすることができます。拡張が IETF Contribution の一部ではない場合は、主張されている知的財産権と使用条件を特定する、その他の IPR 開示文書とすることができます。

Status:

Status (ステータス):

Either "Active" or "Inactive". The "Active" status is used for extensions that are currently implemented and in use. The "Inactive" status is used for extensions that are not implemented or are otherwise not being used. "Inactive" can also be used for extensions for which a reference specification becomes unavailable as described in Section 2.2.4.

"Active" または "Inactive" のいずれかです。"Active" ステータスは、現在実装され使用されている拡張に使用します。"Inactive" ステータスは、実装されていない、またはその他の理由で使用されていない拡張に使用します。セクション 2.2.4 に記載されているとおり、参照仕様が入手できなくなった拡張にも "Inactive" を使用できます。

Notes: Either "None" or other text that describes optional notes to be included with the registered extension. If the Status value is being changed, text MUST be included to describe the rationale for the status change.

Notes (備考): "None" か、登録済み拡張に付加する任意の備考を記述したその他のテキストのいずれかです。Status の値を変更する場合は、ステータス変更の根拠を記述したテキストを含めなければなりません (MUST)。

2.2.3. Registration Processing

2.2.3. 登録の処理

Registrants should send each registration form to IANA with a single record for incorporation into the registry (see <https://www.iana.org/assignments/epp-extensions>). Send the form via email to <iana@iana.org> or complete the online form. The subject line MUST indicate the type of request by including one of the following:

登録者は、レジストリに組み込むために、各登録フォームを1件のレコードとして IANA に送付すべきです（<https://www.iana.org/assignments/epp-extensions> を参照）。フォームは <iana@iana.org> 宛てのメールで送付するか、オンラインフォームに記入して送付してください。件名には、要求の種類を示す次のいずれかを含めなければなりません (MUST)。

INSERT:

INSERT:

indicates insertion of a new record,

新規レコードの挿入を示します。

MODIFY:

MODIFY:

indicates replacement of an existing record,

既存レコードの置換を示します。

DEACTIVATE:

DEACTIVATE:

indicates deactivation of an existing record, or

既存レコードの無効化を示します。

REMOVE:

REMOVE:

indicates removal of an existing record.

既存レコードの削除を示します。

Removal of registrations created through IETF consensus MUST be approved by the IESG using the IESG Approval process described in Section 4.10 of [RFC8126]. Registrations not created through IETF consensus can be removed or deactivated with the approval of the IESG, or at the request of the original registrant, in consultation with or at the request of the designated experts.

IETFコンセンサスによって作成された登録の削除は、[RFC8126] のセクション4.10に記載されている IESG Approval プロセスにより、IESG によって承認されなければなりません (MUST)。IETFコンセンサスによらずに作成された登録は、IESG の承認を得て、または元の登録者の要求により、指定エキスパートとの協議のうえ、もしくは指定エキスパートの要求により、削除または無効化できます。

On receipt of a registration request, IANA will initiate review by the designated expert(s), who will evaluate the request using the criteria in Section 2.1.1 in consultation with the current working group mailing list focused on the development of EPP extensions, if such a working group exists.

登録要求を受領すると、IANA は指定エキスパートによる審査を開始します。指定エキスパートは、セクション2.1.1の基準を用いて要求を評価します。その際、EPP拡張の開発に特化した作業部会のメーリングリストが現在存在する場合は、それと協議して評価を行います。

2.2.4. Updating Registry Entries

2.2.4. レジストリエントリの更新

When submitting changes to existing registry entries, include text in the "Notes" field of the registration form describing the change. Under normal circumstances, registry entries are only to be updated by the registrant. If the registrant becomes unavailable or is otherwise unresponsive, a designated expert can submit a registration form to IANA to update the registrant information. Entries can change state from "Active" to "Inactive" and back again as long as state-change requests conform to the processing requirements identified in this document. In addition to entries that become "Inactive" due to a lack of implementation, entries for which a specification becomes consistently unavailable over time should be marked "Inactive" by the designated expert until the specification again becomes reliably available.

既存のレジストリエントリへの変更を提出するときは、登録フォームの「Notes」フィールドに変更内容を説明するテキストを含めます。通常の状況では、レジストリエントリは登録者のみが更新するものとされています。登録者が連絡不能になった場合、またはそれ以外の理由で応答しない場合、指定エキスパートは、登録者情報を更新するための登録フォームをIANAに提出できます。エントリは、状態変更要求が本文書で示す処理要件に適合している限り、「Active」から「Inactive」へ、またその逆へと状態を変更できます。実装の不足によって「Inactive」になるエントリに加えて、仕様が時間の経過とともに継続的に入手できなくなったエントリは、その仕様が再び確実に入手できるようになるまで、指定エキスパートによって「Inactive」とされるべきです。

3. IANA Considerations

3. IANAの考慮事項

Section 2 provides IANA registration considerations. These considerations are not repeated here.

セクション2でIANAの登録に関する考慮事項を示しています。これらの考慮事項はここでは繰り返しません。

IANA has created the "Extensions for the Extensible Provisioning Protocol (EPP)" registry [IANA-REG] to manage EPP extensions, described in Section 2. In the registry, IANA has replaced the reference to [RFC7451] with a reference to this RFC and added a note to explain that the early allocation policy defined in [RFC7120] does not apply. IANA has also changed the "Document Status" of all non-RFC documents from "Informational" to "Other".

IANAは、セクション2で説明した拡張プロビジョニングプロトコル (EPP) の拡張を管理するために、「Extensions for the Extensible Provisioning Protocol (EPP)」レジストリ [IANA-REG] を作成しました。このレジストリでは、IANAは [RFC7451] への参照を本RFCへの参照に置き換え、[RFC7120] で定義された早期割り当てポリシーは適用されない旨を説明する注記を追加しました。IANAはまた、RFC以外のすべての文書の「Document Status」を「Informational」から「Other」に変更しました。

4. Security Considerations

4. セキュリティに関する考慮事項

This document introduces no new security considerations to EPP. However, extensions should be evaluated according to the Security Considerations of [RFC3735] (or its future replacement) and [STD69].

本文書は、EPPに新たなセキュリティ上の考慮事項を導入しません。ただし、拡張は、[RFC3735] (またはその将来の後継文書) および [STD69] のセキュリティに関する考慮事項に従って評価されるべきです。

5. Operational Considerations

5. 運用上の考慮事項

The updates defined in this document are meant to enhance the guidance for reviewing EPP extensions (e.g., avoid non-IETF specifications squatting on IETF XML namespaces) and thus allow for better interoperability.

本文書で定義する更新は、EPP拡張をレビューするためのガイダンスを強化し (例: IETF以外の仕様がIETFのXML名前空間を不正に占有することの回避)、それによってより良い相互運用性を可能にすることを意図しています。

Section 2 includes provisions for modifying and deleting existing registration entries by registrants. Such requests may have operational implications on other entities that deploy those extensions. Note that the registry does not include a history mechanism and there is no way to track deleted entries once they have been removed.

セクション2には、登録者による既存の登録エントリの変更および削除に関する規定が含まれています。このような要求は、それらの拡張を展開している他のエンティティに運用上の影響を与える可能性があります。レジストリには履歴の仕組みがなく、削除されたエントリは、いったん削除されると追跡する方法がないことに注意してください。

Section 3 updates the content of "Document Status" to be compliant with the guidance in Section 2. The update does not impact the extension itself or induce any operational issues.

セクション3は、「Document Status」の内容を、セクション2のガイダンスに適合するよう更新します。この更新は、拡張自体に影響を与えず、運用上の問題も引き起こしません。
