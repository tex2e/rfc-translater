## 2026-08-02時点の所見

**E001 が 0 でも識別子が全て正しいわけではありません。** 自動判定できない分は
W009 として別に計上しています（1,423件）。指標を良く見せないための分離です。

W009 は原文内で同じ綴りが複数の表記で現れるケースです。SMIやC APIの慣習で
以下のように併存します。

```
natInterfaceEntry OBJECT-TYPE SYNTAX NatInterfaceEntry ...
CMSG_DATA() ... what is called the cmsg_data[] member ...
```

訳文には壊れた表記が1つしかないため、どちらに復元すべきか機械的には決定できません。
誤修正を出さないため自動変換の対象外とし、人手またはAIの判断に委ねています。

**W006 の残り 3,443 件は機械変換できない見出しです。** 内訳:

- サ変動詞でないもの — 「オプションを含めます」「曖昧性を乱します」
  （含める・乱すは五段/下一段動詞。体言化に語彙判断が要る）
- 主題の「は」を含む文 — 「パディングフレームは輻輳ウィンドウを消費します」
  （体言止めにすると「Xは〜の消費」となり非文になるため除外）
- 「〜です」「〜できます」で終わるもの — 「共通の語彙が必要です」
  （「共通の語彙の必要性」のような書き換えは意味理解が必要）
- 主語マーカー「が」が述語を失うもの — 「同等のアルゴリズムが許可されています」
  （「〜が許可」は体言止めではなく係り先のない断片になるため変換しない）

### E002 の誤検知について（重要）

当初 E002 は 365 件でしたが、**うち 40 件は linter の誤検知**でした。
原因は2つで、いずれも修正済みです。

1. **`MUST not` のような小文字表記を見落としていた。** RFC本文では
   `MUST NOT` が `MUST not` と書かれることがあります。これを「MUST（必須）」と
   誤認し、訳文の「〜してはなりません」を誤訳として報告していました。
2. **肯定形キーワード + 原文の否定表現を考慮していなかった。**
   `MUST be absent` / `MUST signal X but not execute Y` のような文では、
   訳文が「〜してはなりません」になるのが正しい訳です。

この種の誤検知は、`MUST/SHALL/SHOULD` に対して訳文が禁止・非推奨相当だった
55件のうち **47件（85%）** を占めていました。

**E002 は自動修正してはいけません。** 「MUST reject」を「受け入れてはなりません」と
訳すような正しい言い換えが存在するため、置換先は文ごとに読んで決める必要があります。
残る 325 件は人手またはAIレビューの対象です。

## RFC2119キーワード注釈の初回集計 (E014 / E015 / W011, 2026-09-28)

RFCページで規範キーワードを色分け表示するようにしたところ、訳文に `(MUST)` などの
併記がない箇所は強調されず、欠陥が画面上で目立つようになった。これを機械的に
拾うため、段落ごとに「原文のキーワード」と「訳文の注釈」を種類・個数で照合する。
対象は RFC 2119 / RFC 8174 / BCP 14 を参照する文書だけ（表示の強調と同じ基準）。

| コード | 件数 | 重み | 内容 |
|---|---|---|---|
| E015 | 436 | 10.0 | 原文にないキーワードの注釈がある（規範性の付加） |
| E014 | 7,749 | 1.0 | 注釈が原文のキーワードより少ない（付け漏れ） |
| W011 | 107,142 | 0.1 | 原文にキーワードがあるのに注釈が1つもない |

- **E015 は意味の誤りである。** 原文が小文字の `should` / `is required to`
  などの箇所に `(SHOULD)` / `(MUST)` が付いており、原文にない規範性を足している。
  目視した標本ではいずれも実際の欠陥だった。E002 と同じ重みにしている。
- **W003（強度未表現）が239件しかないのに W011 が10万件あるのは矛盾ではない。**
  言い回し（「〜しなければなりません」）で強度は表現できているが、原語の併記が
  ないという状態が大半で、意味の誤りより表記の欠落である。
- **既知の誤検知**: 原文の引用符付きキーワード（`'REQUIRED'` など）は定型文・用語説明の
  言及として数えないが、訳文側で注釈が付いている場合は E015 になる（66件）。
- キーワード1個・注釈1個で種類だけ違うものは E002（注釈不一致）の担当とし、二重計上しない。

- **句点のない段落末は検査しない。** 箇条書きの断片などで誤検出が増えるため。
- **初回集計の全1,054段落を訳し直し、W015・W016 とも0件にした (2026-10-27)。** 段落全体を英語原文から
  再翻訳し、編集した段落に lint の指摘が残らないことを確認した。副次的に E014 が1件、W011 が65件減った。

## 捏造・欠落と用語集の初回集計 (W013 / W014, 2026-09-30)

| コード | 件数 | 内容 |
|---|---|---|
| W013 | 1,192 | 原文の数値や識別子が訳文から大量に消えている（捏造・切り詰めの疑い） |
| W014 | 5,527 | 用語集で禁止している訳語・既知の誤訳語（混雑 4,134、侵入 821、渋滞 488 など） |

- **W013 はLLMによる一括再翻訳の事故を捕まえるために作った。** 430499938 などの一括コミットで、
  同じRFCの別の箇所の内容で訳文を捏造したり、段落の後半を落としたりした訳が見つかった
  （#262, #263）。こうした訳文では原文の数値や識別子が消える。
- **判定条件は精度を優先して絞っている。** 「アンカー（数値・識別子・参照）の6割が消えた」だけだと
  main で約6.9万件になり、その大半は識別子が訳されてしまっただけの段落だった（RED→赤い など。
  これも誤りだが別問題）。そこで「数値が2個以上（または全部）消えた」か「訳文が原文の1/4未満で
  アンカーの6割が消えた」に限った。#262 で人手判定した段落では、正しい訳への誤検出は0件。
  main の無作為抽出では、前者は10件中8件、後者は10件中10件が実際の欠陥だった。誤検出の典型は
  「150 million → 1億5,000万」のような数値の単位換算。
- **W013 が0でも捏造がないとは言えない。** 数値や識別子を含まない段落の捏造は検出できない。
- **W014 は原文にその語があるときだけ検査する。** 原文に congestion がない段落の「混雑」は対象外。
  ingress の「侵入」は、原文が intrusion 等を述べている段落では除外する。
